The Dynamics 365 / Dataverse SDK is a good tour of design patterns. Knowing them helps you understand *why* the platform works the way it does, and gives you concrete answers in an interview for a Dynamics role.

## The event pipeline: Chain of Responsibility

When a record is created or updated, the message passes through stages: **PreValidation → PreOperation → main operation → PostOperation**. Plug-ins are registered on these stages with an execution order. Each one does its part and lets the message continue, or stops the whole operation by throwing `InvalidPluginExecutionException`. That's a pipeline of handlers, just like ASP.NET Core middleware.

## IServiceProvider: Service Locator

`IPlugin.Execute(IServiceProvider serviceProvider)` gives you a box you ask for services:

```csharp
var context = (IPluginExecutionContext)serviceProvider.GetService(typeof(IPluginExecutionContext));
var factory = (IOrganizationServiceFactory)serviceProvider.GetService(typeof(IOrganizationServiceFactory));
var tracing = (ITracingService)serviceProvider.GetService(typeof(ITracingService));
```

This is the **Service Locator** pattern. It's fine at the edge of the plug-in, but in application code it's considered an anti-pattern, because dependencies are hidden inside method bodies. The usual fix: get the services **once**, at the top of `Execute`, and pass them into your own classes through constructors (DI by hand).

## IOrganizationServiceFactory: Factory

`factory.CreateOrganizationService(context.UserId)` creates a service that runs as a given user (or as SYSTEM with `null`). You don't know the concrete class you get back; the factory decides.

## OrganizationRequest and Execute: Command

```csharp
service.Execute(new SetStateRequest { EntityMoniker = account.ToEntityReference(), State = new OptionSetValue(1), Status = new OptionSetValue(2) });
```

Every operation is a **request object**. Because actions are objects, they can be batched in `ExecuteMultipleRequest` or run as one transaction in `ExecuteTransactionRequest`.

## A PluginBase class: Template Method

Most teams write a base class once:

```csharp
public abstract class PluginBase : IPlugin
{
    public void Execute(IServiceProvider serviceProvider)    // the fixed plan
    {
        var local = new LocalContext(serviceProvider);       // get context, services, tracing
        try
        {
            ExecuteCore(local);                               // the one step each plug-in fills in
        }
        catch (InvalidPluginExecutionException) { throw; }
        catch (Exception e)
        {
            local.Trace(e.ToString());
            throw new InvalidPluginExecutionException("Unexpected error, see the trace log", e);
        }
    }

    protected abstract void ExecuteCore(LocalContext local);
}
```

## Early-bound classes: Proxy-like wrappers

Classes generated by `pac modelbuilder` (`Account`, `Contact`) wrap the generic `Entity` and its attribute dictionary with typed properties: `account.Name` instead of `entity.GetAttributeValue<string>("name")`.

## Pre and Post images: Memento

A **PreImage** is a snapshot of the record before the operation; a **PostImage** is a snapshot after. A plug-in compares them to see what really changed.

## Repository and testable plug-ins

Put data access behind an interface (`IAccountRepository` that uses `IOrganizationService` inside). The business logic gets the repository through its constructor, and unit tests pass a fake or use FakeXrmEasy, without a real Dataverse.

## Remember

In an interview for a Dynamics role, the strongest answer ties patterns to the platform: "the plug-in pipeline is Chain of Responsibility, `Execute` with request objects is Command, our `PluginBase` is Template Method, and we inject repositories to unit-test plug-ins".
