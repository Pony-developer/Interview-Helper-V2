**Простими словами:** Singleton гарантує, що клас має **лише один об'єкт**, і кожен, кому він потрібен, отримує **саме цей об'єкт**.

## Картинка з життя

У країні одночасно один президент. Хто б не спитав «хто президент?», відповідь та сама, і ніхто не може просто призначити другого.

## Проблема

Деякі речі мають існувати в одному екземплярі: конфігурація застосунку, записувач логів, кеш. Якби кожен клас робив `new Configuration()`, кожен читав би файл знову й міг отримати різні значення.

## На C#

```csharp
public sealed class AppConfig
{
    // Lazy<T> створює об'єкт під час першого звернення і з коробки потокобезпечний
    private static readonly Lazy<AppConfig> instance = new Lazy<AppConfig>(() => new AppConfig());

    public static AppConfig Instance { get { return instance.Value; } }

    public string ApiUrl { get; private set; }

    private AppConfig()                 // private: ніхто ззовні не викличе new AppConfig()
    {
        ApiUrl = "https://api.example.com";
    }
}

// Будь-де в коді:
var url = AppConfig.Instance.ApiUrl;
```

Три складники: **приватний конструктор**, **статичне поле** з єдиним екземпляром і **статична властивість**, щоб до нього дістатися. `sealed` не дає підкласу створити ще один «різновид» екземпляра.

## Коли застосовувати, а коли ні

- **Пасує:** для чогось справді глобального й без стану або лише для читання: конфігурація, логер.
- **Шкодить:** це **замаскований глобальний стан**. До нього може дістатися будь-який код, тож із конструктора класу не видно, що клас від нього залежить, а в тестах його важко замінити підробкою. Змінювані singleton-и ще й переносять стан між тестами.
- **Сучасна альтернатива:** зареєструвати клас як **singleton у DI-контейнері** (`services.AddSingleton<IAppConfig, AppConfig>()`). Екземпляр так само один, але класи отримують його через конструктор, а тести можуть передати підробку.

## Запам'ятайте

На співбесіді покажіть обидва боки: «Singleton гарантує один екземпляр через приватний конструктор і статичний доступ; `Lazy<T>` робить його потокобезпечним. Але він приховує залежності й заважає тестуванню, тож у сучасному .NET я віддаю перевагу singleton-життєвому циклу в DI».
