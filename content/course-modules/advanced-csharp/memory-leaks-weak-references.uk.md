## Витоки у світі зі збирачем сміття

GC не може зібрати те, що досі досяжне. **Витік керованої пам'яті** — це об'єкт, який вам більше не потрібен, але на який досі посилається щось довгоживуче. Пам'ять стабільно росте, доки процес не сповільниться чи не вичерпає її.

## Звичні підозрювані

**1. Підписки на події.** Видавець тримає посилання на кожного підписника через делегат.

```csharp
public class PriceTicker { public static event EventHandler? Tick; }

public class PriceWidget
{
    public PriceWidget() => PriceTicker.Tick += OnTick;    // статичний видавець тримає живим кожен віджет
    private void OnTick(object? s, EventArgs e) { }
    // виправлення: реалізувати IDisposable і відписатися: PriceTicker.Tick -= OnTick;
}
```

**2. Статичні колекції та кеші, що лише ростуть.** `static Dictionary` як кеш без політики витіснення. Використовуйте `MemoryCache` з обмеженням розміру й терміном дії або обмежений LRU.

**3. Таймери.** `System.Timers.Timer` чи `System.Threading.Timer` тримає ціль свого колбеку. Незвільнений таймер тримає живим власника (і продовжує спрацьовувати).

**4. Захоплені змінні.** Довгоживуча лямбда (збережена в полі чи статично) захоплює великий об'єкт або `this`.

**5. Довгоживучі DI-області.** Отримання scoped/transient disposable-сервісів з кореневого контейнера в ASP.NET Core тримає їх до зупинки застосунку.

**6. Некерована пам'ять.** Нативні алокації (`Marshal.AllocHGlobal`, нативні бібліотеки, незвільнені bitmap) взагалі не видно в статистиці керованої купи.

## Пошук витоків

- Стежте за трендом: `dotnet-counters monitor` (розмір купи GC, кількість збирань gen 2) або метрики застосунку.
- Зробіть два дампи пам'яті з інтервалом (`dotnet-gcdump collect`, діагностичні інструменти Visual Studio) і порівняйте кількість об'єктів: те, що постійно росте, — підозрюване.
- Пройдіть **шлях до кореня** у переглядачі дампу: він точно показує, яке статичне поле чи подія тримає об'єкт живим.

## Слабкі посилання

`WeakReference<T>` посилається на об'єкт, **не тримаючи його живим**. Якщо на ціль більше ніщо не посилається, GC може її зібрати, і слабке посилання тоді нічого не поверне.

```csharp
var cacheEntry = new WeakReference<byte[]>(LoadLargeImage());

if (cacheEntry.TryGetTarget(out byte[]? image))
    Show(image);                          // досі живий
else
    cacheEntry.SetTarget(image = LoadLargeImage());   // зібрано: завантажити знову
```

Застосування:

- **кеші**, що мають повертати пам'ять під тиском (хоча слабкі посилання очищаються на *будь-якому* збиранні, часто надто охоче; `MemoryCache` з обмеженнями зазвичай кращий);
- **патерни слабких подій**: видавець тримає підписників слабко, тож забута відписка не спричиняє витоку (`WeakEventManager` у WPF);
- **відстеження об'єктів без володіння**, наприклад діагностика, що рахує живі екземпляри.

`ConditionalWeakTable<TKey, TValue>` прикріплює дані до об'єкта, не тримаючи ключ живим: коли ключ зібрано, запис зникає. Так додають «властивості» до об'єктів, які вам не належать.

## Що сказати на співбесіді

- Керований витік = непотрібні об'єкти досі досяжні: події, статичні кеші, таймери, замикання.
- Діагностуйте, порівнюючи знімки купи й проходячи шлях до кореня.
- `WeakReference<T>` і `ConditionalWeakTable` посилаються на об'єкти, не подовжуючи їхнього життя.
