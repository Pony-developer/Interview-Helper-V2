## Запит — це рецепт, а не результат

Більшість операторів запиту не виконуються, коли їх викликають. Вони повертають об'єкт-**декоратор**, що пам'ятає своє джерело й лямбду. Робота відбувається лише тоді, коли хтось **перелічує** результат.

```csharp
var numbers = new List<int> { 1, 2 };
IEnumerable<int> query = numbers.Select(n => n * 10);   // ще нічого не обчислено
numbers.Add(3);
foreach (int n in query) Console.Write(n + " ");        // 10 20 30: бачить доданий елемент
```

Оператори, що повертають **одне значення** чи **матеріалізовану колекцію**, виконуються одразу: `Count`, `First`, `Sum`, `Any`, `Max`, `ToList`, `ToArray`, `ToDictionary`, `ToHashSet`.

## Як працює конвеєр

Ланцюжок на кшталт `source.Where(...).Select(...).Take(2)` будує вкладені декоратори. Коли `foreach` просить елемент у найзовнішнього (`Take`), той просить `Select`, той — `Where`, а `Where` тягне з джерела. Елементи йдуть **по одному** через увесь ланцюжок: нічого не буферизується, а `Take(2)` перестає тягнути після двох елементів, навіть із нескінченного джерела.

Винятки з потоковості: `OrderBy`, `GroupBy`, `Reverse` і оператори множин мусять **буферизувати** вхід, перш ніж видати перший елемент (не можна знати найменший, не побачивши всіх). Вони все одно відкладені, але не ліниві поелементно.

## Повторне обчислення

Кожне перелічення виконує запит заново:

```csharp
var expensive = orders.Where(o => IsSuspicious(o));   // IsSuspicious звертається до веб-сервісу
Console.WriteLine(expensive.Count());   // викликає сервіс для кожного замовлення
foreach (var o in expensive) Flag(o);   // ... і ще раз
```

Виправлення: матеріалізуйте один раз через `ToList()` чи `ToArray()`, коли результати потрібні більше одного разу, потрібен стабільний знімок, або джерело повільне чи віддалене.

## Захоплені змінні

Лямбди захоплюють змінні, а запит виконується пізніше, тож бачить значення змінної на момент **перелічення**:

```csharp
int limit = 10;
var small = numbers.Where(n => n < limit);
limit = 2;
small.ToList();          // використає limit = 2
```

Класична помилка: побудова фільтрів у циклі `for`, де кожна лямбда захоплює ту саму змінну циклу (див. лекцію про замикання).

## Чим відкладене виконання добре

- Запити можна **складати** покроково без проміжних списків.
- Нескінченні чи дуже великі джерела працюють, бо витягується лише потрібне.
- Для `IQueryable` увесь складений запит можна перекласти в **один** SQL-запит наприкінці.

## Чим кусається

- Побічні ефекти в лямбдах (логування, лічильники) спрацьовують у несподіваний час, можливо, кілька разів.
- Винятки з'являються під час перелічення, далеко від місця, де написано запит.
- Джерело звільнено зарано: якщо повернути запит над `DbContext` чи файлом, які звільнять до перелічення, буде `ObjectDisposedException`.

```csharp
IEnumerable<string> ReadLines()
{
    using var reader = File.OpenText("data.txt");
    return reader.ReadToEnd().Split('\n').Where(l => l.Length > 0);   // нормально: ReadToEnd уже виконався
}
```

## Що сказати на співбесіді

- Більшість операторів — відкладені декоратори; скалярні результати й перетворення `To*` — негайні.
- Елементи йдуть по одному, крім буферизувальних операторів на кшталт `OrderBy` і `GroupBy`.
- Кожне перелічення заново виконує запит; за потреби матеріалізуйте через `ToList`.
