## Статичне проти динамічного зв'язування

Зазвичай компілятор **зв'язує** кожне звертання до члена під час компіляції: вирішує, на який метод посилається `x.Foo()`, і відмовляється компілювати, якщо такого немає. З `dynamic` зв'язування відкладається до часу виконання.

```csharp
dynamic d = "hello";
Console.WriteLine(d.ToUpper());   // зв'язується під час виконання з string.ToUpper → HELLO
Console.WriteLine(d.Length);      // 5
d.Fly();                          // компілюється; під час виконання кидає RuntimeBinderException
```

Для компілятора `dynamic` означає «будь-який тип, будь-який член». Насправді змінна — це `object` плюс позначка в метаданих «тут використовувати динамічне зв'язування».

## Як це працює

**Dynamic Language Runtime** (DLR) працює поверх CLR. Для кожного місця динамічного виклику компілятор генерує **об'єкт місця виклику** (call site). Під час першого виклику зв'язувач дивиться на тип під час виконання, з'ясовує, що означає член, і кешує скомпільоване правило. Наступного разу, коли прийде той самий тип, виконається закешоване правило, тож повторні виклики досить швидкі. Перший виклик для кожного типу дорогий.

## Власне зв'язування

Об'єкт може сам керувати своїм динамічним зв'язуванням, реалізувавши `IDynamicMetaObjectProvider`, — зазвичай через наслідування `DynamicObject` або використання `ExpandoObject`:

```csharp
dynamic bag = new ExpandoObject();
bag.Name = "Ann";                          // члени створюються на льоту
bag.Greet = (Func<string>)(() => "Hi " + bag.Name);
Console.WriteLine(bag.Greet());            // Hi Ann

public class JsonBag : DynamicObject
{
    private readonly Dictionary<string, object?> _values = new();
    public override bool TryGetMember(GetMemberBinder binder, out object? result)
        => _values.TryGetValue(binder.Name, out result);
    public override bool TrySetMember(SetMemberBinder binder, object? value)
    { _values[binder.Name] = value; return true; }
}
```

## Мовне зв'язування: уніфікація чисел і перевантаження

Коли об'єкт — звичайний .NET-об'єкт, зв'язувач застосовує **правила C#** до справжніх типів під час виконання:

```csharp
static dynamic Mean(dynamic x, dynamic y) => (x + y) / 2;
Console.WriteLine(Mean(3, 5));        // 4  (int)
Console.WriteLine(Mean(3.0, 4.5));    // 3.75 (double)
```

Один метод, схожий на узагальнений, працює для будь-якого числового типу. (Сьогодні generic math у .NET 7 робить це статично.)

Вибір перевантаження теж відбувається під час виконання, за **справжніми** типами динамічних аргументів. Це дає дешеву форму **множинної диспетчеризації**:

```csharp
void Handle(Circle c) => ...;
void Handle(Square s) => ...;
foreach (Shape s in shapes) Handle((dynamic)s);   // обирає перевантаження за справжнім типом
```

## Обмеження та ціна

- Немає перевірки під час компіляції, IntelliSense і підтримки рефакторингу: одруківки стають помилками під час виконання.
- Методи розширення не знаходяться (вони залежать від директив `using`, яких під час виконання не існує).
- Виклики через `dynamic` повільніші, а перший виклик для кожного типу — набагато повільніший.
- Результати динамічних виразів самі `dynamic`, тож «нетипізована» зона розростається; повертайтеся до статичного типу якомога раніше.

## Коли це виправдано

- COM interop (автоматизація Office), де типи визначені нечітко.
- Взаємодія з динамічними мовами (IronPython) чи динамічними даними (JSON без схеми, хоча `JsonNode`/`JsonElement` часто кращі).
- Заміна великого блоку коду на рефлексії читабельним кодом, коли продуктивність не критична.

## Що сказати на співбесіді

- `dynamic` відкладає зв'язування членів до часу виконання; помилки стають `RuntimeBinderException`.
- DLR кешує правила зв'язування для кожного місця виклику й типу.
- `ExpandoObject` і `DynamicObject` дозволяють об'єктам визначати власні члени під час виконання.
- Використовуйте ощадливо; віддавайте перевагу статичним типам, узагальненням чи інтерфейсам.
