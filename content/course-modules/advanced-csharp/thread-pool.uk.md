## Повторне використання потоків

Створення потоку коштує від десятків до сотень мікросекунд і близько 1 МБ зарезервованого стеку. **Пул потоків** тримає набір готових потоків і роздає їм короткі робочі елементи, тож ціна запуску сплачується один раз.

```csharp
ThreadPool.QueueUserWorkItem(_ => Console.WriteLine("on a pool thread"));
Task.Run(() => Compute());                         // звичний спосіб: Task.Run ставить у пул
Console.WriteLine(Thread.CurrentThread.IsThreadPoolThread);
```

Потоки пулу — **фонові**. Їхні ім'я, пріоритет і культуру не варто змінювати (або треба відновлювати), бо наступний робочий елемент отримає той самий потік.

## Хто користується пулом

Майже все асинхронне: `Task.Run`, колбеки таймерів, `Parallel.For`, PLINQ, продовження після `await` в ASP.NET Core і консольних застосунках, колбеки завершення I/O.

## Як пул обирає свій розмір

- Він починає з **мінімальної** кількості потоків (за замовчуванням — по одному на ядро), доступних одразу.
- Коли всі зайняті, а робота стоїть у черзі, алгоритм **hill-climbing** поступово додає потоки (приблизно один-два на секунду понад мінімум), вимірюючи, чи покращується пропускна здатність.
- Простійні потоки понад мінімум через якийсь час завершуються.

Є два види потоків пулу: **робочі** (для ваших робочих елементів) та **потоки завершення I/O** (для колбеків асинхронного I/O у Windows).

## Голодування пулу потоків

Повільне зростання навмисне: воно не дає створити сотні потоків на сплески CPU-роботи. Але якщо робочі елементи **блокуються** (синхронне I/O, `.Result` на задачі, `Thread.Sleep`), кожен займає потік, черга росте, а пул додає потоки надто повільно, щоб устигати. Симптоми: запити тривають секунди при низькому навантаженні CPU, тайм-аути під навантаженням, потім раптове відновлення.

Типова причина в ASP.NET Core — **sync-over-async**:

```csharp
public IActionResult Get() => Ok(_client.GetStringAsync(url).Result);   // блокує потік пулу на кожен запит
public async Task<IActionResult> Get() => Ok(await _client.GetStringAsync(url));   // звільняє потік на час очікування
```

Виправлення в порядку переваги:

1. зробити код асинхронним до самого низу;
2. справді блокуючу довготривалу роботу перенести в окремий потік (`TaskCreationOptions.LongRunning`);
3. як тимчасовий захід — підняти мінімум: `ThreadPool.SetMinThreads(...)`.

Діагностуйте через `dotnet-counters` (`ThreadPool Queue Length`, `ThreadPool Thread Count`) або `dotnet-stack` (багато потоків, що застрягли в `.Result`/`Wait`).

## Гарантувати виконання в пулі

Коли треба гарантувати, що код виконається не в поточному потоці (наприклад, щоб UI лишався чуйним під час важких обчислень), використовуйте `await Task.Run(() => HeavyCalculation())`. Не обгортайте в `Task.Run` асинхронні методи, обмежені I/O: їм не потрібен потік, поки вони чекають.

## Що сказати на співбесіді

- Пул повторно використовує фонові потоки для коротких робочих елементів; `Task.Run` — звичайна точка входу.
- Понад мінімум він росте повільно, тож блокування потоків пулу спричиняє голодування.
- Уникайте sync-over-async (`.Result`, `.Wait()`) на серверах; асинхронність — до самого низу.
