## Виходимо за межі страхувальної сітки

C# підтримує сирі вказівники всередині `unsafe`-коду. Дозвіл треба дати двічі: позначити код `unsafe` і дозволити це в проєкті (`<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`).

```csharp
unsafe static void Fill(int* p, int count, int value)
{
    for (int i = 0; i < count; i++) p[i] = value;   // без перевірки меж
}
```

Оператори вказівників:

| Оператор | Значення |
| --- | --- |
| `&x` | адреса `x` |
| `*p` | значення, на яке вказує `p` |
| `p->Field` | доступ до члена через вказівник (те саме, що `(*p).Field`) |
| `p[i]` | те саме, що `*(p + i)` |
| `p + n`, `p++` | арифметика вказівників в одиницях розміру цільового типу |

Вказівники можуть вказувати лише на **некеровані** типи: примітиви, enum, вказівники та структури, що містять лише такі типи (без посилань).

## fixed: закріплення керованої пам'яті

Збирач сміття ущільнює купу, переміщуючи об'єкти. Щоб узяти вказівник на щось у купі, це треба **закріпити**, щоб воно не рухалося, поки ви користуєтеся вказівником:

```csharp
byte[] buffer = new byte[1024];
unsafe
{
    fixed (byte* p = buffer)          // закріплює масив на час блоку
    {
        for (int i = 0; i < buffer.Length; i++) p[i] = 0xFF;
    }
}
fixed (char* c = "text") { }          // працює й для рядків
```

Тримайте блоки `fixed` короткими: закріплені об'єкти заважають ущільненню купи.

## stackalloc

```csharp
unsafe
{
    int* numbers = stackalloc int[100];   // 100 int у стеку: жодного GC
}

Span<int> safe = stackalloc int[100];     // C# 7.2+: unsafe не потрібен, якщо присвоїти Span
```

Пам'ять стеку звільняється автоматично, коли метод повертається. Її мало (зазвичай 1 МБ на потік), тож використовуйте лише для невеликих обмежених буферів.

## Буфери фіксованого розміру

```csharp
unsafe struct PacketHeader
{
    public fixed byte Magic[4];   // вбудований масив усередині структури
    public int Length;
}
```

Корисно, коли треба відтворити розкладку нативної структури.

## Вказівники на функції (C# 9)

```csharp
unsafe
{
    delegate*<int, int, int> add = &Add;   // сирий вказівник на статичний метод, без алокації делегата
    Console.WriteLine(add(2, 3));
}
static int Add(int a, int b) => a + b;
```

Використовуються у високопродуктивному interop, щоб напряму викликати нативні функції.

## void* і перетворення

`void*` вказує на нетипізовану пам'ять; перед розіменуванням приведіть його до типізованого вказівника. Вказівники перетворюються на `IntPtr`/`nint` і назад — так їх передають в API для interop.

## Навіщо (і навіщо ні)

Причини для unsafe-коду:

- взаємодія з нативними бібліотеками, що приймають вказівники;
- вичавлювання останніх крапель продуктивності в щільних циклах (обробка зображень, парсери, серіалізатори).

Причини уникати:

- немає перевірки меж: помилки тихо псують пам'ять;
- збірка позначається як неверифікована;
- у сучасному C# **`Span<T>`, `stackalloc` у спани, `ref`-повернення, `MemoryMarshal` і `Unsafe`** дають схожу швидкість із безпекою. Беріться спершу за них.

## Що сказати на співбесіді

- `unsafe` + `AllowUnsafeBlocks`; вказівники лише на некеровані типи.
- `fixed` закріплює об'єкти в купі, щоб GC їх не переміщував.
- `stackalloc` виділяє пам'ять у стеку; присвойте результат `Span<T>`, щоб обійтися без `unsafe`.
- Віддавайте перевагу спанам; вказівники — для interop і виміряних гарячих місць.
