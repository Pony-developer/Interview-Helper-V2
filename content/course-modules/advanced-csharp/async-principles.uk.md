## Синхронне проти асинхронного

- **Синхронна** операція виконує роботу до повернення до викликача.
- **Асинхронна** операція може повернутися **раніше**, ніж робота завершена, віддавши щось (задачу), що завершиться пізніше.

Асинхронність — про те, щоб не **чекати без діла**. Це не те саме, що паралелізм: асинхронний код може використовувати лише один потік.

## Два види роботи

| | Обмежена I/O | Обмежена CPU |
| --- | --- | --- |
| На що йде час | на очікування диска, мережі чи бази даних | на обчислення |
| Асинхронне рішення | справжні асинхронні API (`ReadAsync`, `GetAsync`, `ToListAsync`): **жоден потік** не чекає | `Task.Run`, щоб забрати роботу з поточного потоку (UI), або `Parallel`/PLINQ, щоб задіяти більше ядер |
| Масштабується за рахунок | звільнення потоків під час очікувань | додавання ядер |

Ключова думка: під час справжнього асинхронного I/O **жоден потік не заблокований**. ОС завершує операцію (через порти завершення I/O у Windows, epoll у Linux), а рантайм планує продовження в потоці пулу. Серверу, що обробляє 10 000 одночасних запитів, кожен з яких чекає 200 мс на базу, не потрібно 10 000 потоків.

## Грубозерниста проти дрібнозернистої конкурентності

До async/await, щоб не блокуватися, всю синхронну операцію запускали у фоновому потоці (**грубозернисто**): просто, але кожна операція, що чекає, тримала потік, а оновлення UI з нього вимагало маршалінгу.

Асинхронні функції дають **дрібнозернисту** конкурентність: сам метод написаний послідовно, а кожен `await` — точка, де він може призупинитися, не тримаючи потік. Потік UI лишається чуйним, а продовження повертаються в нього автоматично.

## Чому важливий потік UI

Десктопні та мобільні UI-фреймворки мають один потік UI, що обробляє цикл повідомлень. Довга синхронна операція в ньому заморожує вікно. З async:

```csharp
private async void LoadButton_Click(object sender, RoutedEventArgs e)
{
    StatusText.Text = "Loading...";
    string data = await _client.GetStringAsync(url);   // потік UI вільний під час завантаження
    StatusText.Text = $"{data.Length} chars";          // знову в потоці UI: можна чіпати елементи керування
}
```

## Async до самого верху

Асинхронність «заразна», і так задумано: щойно низ ланцюжка викликів асинхронний (мережа, база), кожен викликач угору ланцюжком теж має бути асинхронним, аж до фреймворку (дія ASP.NET Core, обробник UI-події, `async Task Main`). Блокування десь посередині (`.Result`, `.Wait()`) викидає всі переваги й запрошує взаємоблокування та голодування пулу потоків.

## Коли async не вартий того

- Чиста робота CPU на сервері: `async` додає накладних витрат, нічого не звільняючи; просто обчислюйте (чи паралельте).
- Дуже гарячі, переважно синхронні шляхи: розгляньте `ValueTask` чи синхронний швидкий шлях.
- Природно синхронний код без I/O: не робіть його «асинхронним» у бібліотеці, обгортаючи в `Task.Run» («фальшивий async»); нехай вирішує викликач.

## Що сказати на співбесіді

- Async = не блокуватися під час очікування; це не те саме, що паралельно.
- Робота, обмежена I/O, використовує справжні асинхронні API і жодного потоку під час очікування; робота, обмежена CPU, потребує потоків (`Task.Run`, `Parallel`).
- Async до самого верху; уникайте sync-over-async.
