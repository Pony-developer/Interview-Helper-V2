## Що означає «потокобезпечний»

Тип потокобезпечний, якщо він поводиться коректно, коли ним користуються з кількох потоків одночасно, без додаткової синхронізації з боку викликачів. Стратегії, від найпростішої до найскладнішої:

1. **Не ділитися**: дайте кожному потоку власні дані (локальні змінні, об'єкти на кожен запит).
2. **Ділитися лише незмінними даними**: незмінні об'єкти (record з `init`, `ImmutableList<T>`, рядки) можуть читати скільки завгодно потоків без блокувань.
3. **Використовувати потокобезпечні будівельні блоки**: `ConcurrentDictionary`, `Channel<T>`, `Lazy<T>`, `Interlocked`.
4. **Блокувати** кожен доступ до змінного спільного стану.
5. **Код без блокувань** з `Interlocked` і бар'єрами пам'яті: найшвидший і найважчий для правильної реалізації.

## Потокобезпечність у BCL

- **Статичні** члени більшості типів BCL потокобезпечні; члени **екземпляра** загалом ні.
- `List<T>`, `Dictionary<K,V>`: безпечні для одночасного **читання**, лише якщо ніхто не пише.
- `HttpClient`, `Random.Shared`, колекції `ConcurrentX`, `ILogger`: створені для одночасного використання.
- Перелічувати колекцію, поки інший потік її змінює, небезпечно, навіть якщо кожна зміна під блокуванням. Блокуйте все перелічення або перелічуйте знімок (`ToArray()` під блокуванням).

Атомарності окремих операцій недостатньо: `if (!dict.ContainsKey(k)) dict.Add(k, v)` — **гонка «перевірити, потім діяти»** навіть з потокобезпечним словником. Використовуйте атомарні складені методи: `ConcurrentDictionary.GetOrAdd`, `TryAdd`, `AddOrUpdate`.

## Interlocked: атомарні операції

```csharp
Interlocked.Increment(ref _count);
Interlocked.Add(ref _total, amount);
long snapshot = Interlocked.Read(ref _bigCounter);        // атомарне 64-бітне читання на 32-бітних платформах
string? old = Interlocked.Exchange(ref _current, "new");

// цикл compare-and-swap: будівельний блок алгоритмів без блокувань
int initial, computed;
do
{
    initial = _max;
    computed = Math.Max(initial, candidate);
} while (Interlocked.CompareExchange(ref _max, computed, initial) != initial);
```

Вони реалізовані однією інструкцією процесора й включають повний бар'єр пам'яті.

## Модель пам'яті, volatile і бар'єри

Компілятори, JIT і процесори можуть **переставляти** читання й записи та кешувати значення в регістрах, доки один потік цього не помічає. Інший потік може побачити дивні результати:

```csharp
bool _ready; int _value;

// потік 1
_value = 42;
_ready = true;

// потік 2
if (_ready) Console.WriteLine(_value);   // теоретично може надрукувати 0 без бар'єра
```

Виправлення:

- `volatile bool _ready;` дає прапорцю семантику acquire/release (читання не переносяться перед ним, записи — після), чого досить для простих прапорців;
- `Volatile.Read` / `Volatile.Write` роблять те саме для окремого доступу;
- операції `Interlocked` і `lock` мають повні бар'єри;
- `Thread.MemoryBarrier()` — явний повний бар'єр.

`volatile` **не** робить `count++` атомарним; він лише впорядковує доступи до пам'яті. На практиці використовуйте `lock` чи типи вищого рівня, якщо тільки не пишете низькорівневу інфраструктуру.

## Незмінність як стратегія

```csharp
private ImmutableDictionary<string, decimal> _prices = ImmutableDictionary<string, decimal>.Empty;

public decimal? Price(string sku) => _prices.TryGetValue(sku, out var p) ? p : null;   // читачам не потрібен lock

public void SetPrice(string sku, decimal price) =>
    ImmutableInterlocked.AddOrUpdate(ref _prices, sku, price, (_, _) => price);   // атомарна заміна для писачів
```

Читачі завжди бачать узгоджений знімок; писачі атомарно публікують нову версію.

## Що сказати на співбесіді

- Спершу не діліться, потім незмінність, потім потокобезпечні типи, потім блокування; код без блокувань — наостанок.
- Послідовності «перевірити, потім діяти» потребують атомарних складених операцій або lock.
- `Interlocked` = атомарні операції з бар'єрами; `volatile` = впорядкування, а не атомарність.
