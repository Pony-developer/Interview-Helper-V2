## Що таке фіналізатор

Фіналізатор (синтаксис C# `~ClassName()`, що перевизначає `Object.Finalize`) виконується **перед** тим, як GC забере пам'ять об'єкта. Це останній шанс прибрати **некеровані** ресурси, якщо користувач забув викликати `Dispose`.

```csharp
public class NativeBuffer : IDisposable
{
    private IntPtr _ptr = Marshal.AllocHGlobal(1024);

    ~NativeBuffer() => Free();                 // страхувальна сітка

    public void Dispose()
    {
        Free();
        GC.SuppressFinalize(this);             // прибирання зроблено: пропустити фіналізатор
    }

    private void Free()
    {
        if (_ptr != IntPtr.Zero) { Marshal.FreeHGlobal(_ptr); _ptr = IntPtr.Zero; }
    }
}
```

## Як працює фіналізація

1. Коли виділяється об'єкт із фіналізатором, рантайм реєструє його в **черзі фіналізації**.
2. Коли GC виявляє, що об'єкт недосяжний, він його **не** забирає; він переносить його в **f-reachable queue**, яка є коренем, тож об'єкт (і все, на що він посилається) переживає це збирання й **переводиться** в старше покоління.
3. Окремий **потік фіналізатора** виконує фіналізатори з цієї черги.
4. Лише **пізніше** збирання справді забирає пам'ять.

Наслідки:

- Об'єкти з фіналізаторами коштують щонайменше одного зайвого збирання й живуть довше: **не додавайте непотрібних фіналізаторів**.
- Фіналізатори виконуються в **непередбачуваний** час, у непередбачуваному порядку, в іншому потоці.
- Під час фіналізатора об'єкти, на які він посилається, могли вже бути фіналізовані. Не чіпайте інших керованих об'єктів.
- Виняток, кинутий з фіналізатора, **обвалює процес**.
- Під час завершення процесу .NET Core взагалі не гарантує виконання фіналізаторів.

## Правила написання

- Лише якщо ваш клас **напряму** володіє некерованим ресурсом (дескриптор `IntPtr`, нативна пам'ять).
- Тримайте його коротким, швидким і без винятків.
- Завжди в парі з `Dispose` + `GC.SuppressFinalize(this)`.
- Ніколи не блокуйте (жодних lock чи очікувань): один потік фіналізатора обслуговує весь процес.

## Віддавайте перевагу SafeHandle

У сучасному .NET фіналізатори майже ніколи не пишуть. Натомість обгорніть нативний дескриптор у підклас `SafeHandle`:

```csharp
sealed class FileMappingHandle : SafeHandleZeroOrMinusOneIsInvalid
{
    public FileMappingHandle() : base(ownsHandle: true) { }
    protected override bool ReleaseHandle() => CloseHandle(handle);

    [DllImport("kernel32", SetLastError = true)]
    private static extern bool CloseHandle(IntPtr h);
}
```

`SafeHandle` уже має надійний критичний фіналізатор, захищає від гонок з повторним використанням дескрипторів і розуміється маршалінгом P/Invoke. Ваш клас тоді просто тримає поле `SafeHandle` і реалізує звичайний `Dispose`, що його звільняє.

## Воскресіння

Фіналізатор може зберегти `this` у статичному полі, знову зробивши об'єкт досяжним («воскресіння»). Це працює, але фіналізатор вдруге не виконається, якщо не викликати `GC.ReRegisterForFinalize(this)`. Це курйоз, що зрідка використовується для пулів об'єктів; у звичайному коді уникайте.

## Що сказати на співбесіді

- Фіналізатори — страхувальна сітка для некерованих ресурсів, виконуються в потоці фіналізатора в невідомий час.
- Вони подовжують життя об'єктів і коштують продуктивності; пригнічуйте їх у `Dispose`.
- Замість власних фіналізаторів використовуйте `SafeHandle`.
