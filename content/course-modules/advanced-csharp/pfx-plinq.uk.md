## Навіщо паралельне програмування

Тактові частоти процесорів перестали рости багато років тому; натомість машини отримали більше ядер. Код, що працює в одному потоці, використовує одне ядро. **Parallel Framework (PFX)** допомагає розподілити роботу, **обмежену CPU**, по всіх ядрах:

| Шар | API | Стиль |
| --- | --- | --- |
| Паралелізм даних | PLINQ (`AsParallel`), `Parallel.For`/`ForEach` | та сама операція над багатьма елементами |
| Паралелізм задач | `Task`, `Parallel.Invoke`, `Task.WhenAll` | різні операції одночасно |
| Координація | конкурентні колекції, `BlockingCollection`, `Channel<T>` | виробники та споживачі |

Паралелізм — **не** інструмент для роботи, обмеженої I/O (очікування HTTP чи бази): для неї є async.

## Закон Амдала одним реченням

Якщо 20% роботи принципово послідовні, жодна кількість ядер не прискорить її більш ніж у 5 разів. До того ж поділ роботи, планування й злиття результатів коштують часу, тож крихітні навантаження часто стають **повільнішими** при паралелізації. Вимірюйте.

## PLINQ

Додайте `.AsParallel()` до запиту LINQ to Objects, і наступні оператори виконуватимуться в кількох потоках:

```csharp
int primeCount = Enumerable.Range(1, 5_000_000)
    .AsParallel()
    .Where(IsPrime)
    .Count();

var thumbnails = photos
    .AsParallel()
    .WithDegreeOfParallelism(4)                 // обмежити кількість потоків
    .WithCancellation(ct)
    .Select(p => CreateThumbnail(p))
    .ToList();
```

Що відбувається: PLINQ **розбиває** вхід на частини, виконує запит у кількох потоках і **зливає** результати.

Що варто знати:

- **Порядок за замовчуванням не зберігається**. `AsOrdered()` повертає його (додаткова ціна); `AsUnordered()` пізніше в запиті знову від нього відмовляється.
- **Побічні ефекти** в лямбдах мають бути потокобезпечними: жодного `list.Add` усередині `Select`.
- Деякі оператори змушують до послідовного виконання чи буферизації; `ForAll(action)` виконує дію паралельно, не зливаючи результати назад в один потік.
- Результати повертаються через буфер злиття; `WithMergeOptions(ParallelMergeOptions.NotBuffered)` видає їх раніше.
- Винятки збираються в `AggregateException`.
- PLINQ — для даних у пам'яті; до запитів EF Core він не має жодного стосунку.

## Коли PLINQ допомагає

Добре: дорогі обчислення для кожного елемента (обробка зображень, розбір, симуляції, хешування) над багатьма елементами.
Погано: дешеві операції на кшталт `x * 2` над невеликими списками (накладні витрати переважають), усе, що обмежене I/O, запити, де важливий порядок результату, а `AsOrdered` забули.

## Що сказати на співбесіді

- PFX = PLINQ + `Parallel` + задачі + конкурентні колекції, для роботи, обмеженої CPU.
- `AsParallel()` розбиває, виконує в багатьох потоках і зливає; порядок губиться без `AsOrdered()`.
- Паралелізм має накладні витрати; вимірюйте, а для I/O беріть async (не PLINQ).
