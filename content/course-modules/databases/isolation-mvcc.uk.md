Ізоляція визначає, що бачить транзакція, поки одночасно виконуються інші. Ідеальна ізоляція (ніби транзакції виконуються одна за одною) дорога, тож SQL визначає **рівні**, що дозволяють певні аномалії в обмін на швидкість.

## Феномени читання

| Феномен | Що стається |
|---|---|
| **Брудне читання** | T1 читає зміну, яку T2 ще не зафіксувала; T2 відкочується, і T1 використала дані, яких ніколи не існувало |
| **Неповторюване читання** | T1 читає рядок двічі й отримує різні значення, бо T2 між читаннями оновила й зафіксувала його |
| **Фантомне читання** | T1 двічі виконує той самий `WHERE` і отримує різні набори рядків, бо T2 вставила відповідний рядок |
| **Аномалія серіалізації** | Результат паралельних транзакцій неможливий за жодного послідовного порядку |

А ще одна аномалія постійно болить застосункам: **втрачене оновлення**. Дві транзакції читають `balance = 100`, обидві обчислюють `100 + 10` у коді застосунку й записують `110`. Одне поповнення втрачено.

## Рівні ізоляції в PostgreSQL

| Рівень | Брудне читання | Неповторюване читання | Фантоми | Аномалія серіалізації |
|---|---|---|---|---|
| Read Uncommitted | Неможливе в PG* | Можливе | Можливі | Можлива |
| **Read Committed** (типовий) | Ні | Можливе | Можливі | Можлива |
| Repeatable Read | Ні | Ні | Ні в PG** | Можлива |
| Serializable | Ні | Ні | Ні | Ні |

\* PostgreSQL виконує Read Uncommitted як Read Committed.
\*\* Стандарт SQL дозволяє фантоми на Repeatable Read; реалізація знімків у PostgreSQL їх не допускає.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
…
COMMIT;
```

- **Read Committed**: кожна **інструкція** бачить знімок, зроблений на її початку. Два `SELECT` в одній транзакції можуть бачити різні дані. Підходить для більшості OLTP-роботи, якщо оновлення написано обережно.
- **Repeatable Read**: уся **транзакція** бачить один знімок, зроблений на її першій інструкції. Чудово для узгоджених звітів. Якщо вона спробує оновити рядок, який інша транзакція змінила після знімка, вона впаде з «could not serialize access due to concurrent update».
- **Serializable**: PostgreSQL відстежує залежності читання/запису (Serializable Snapshot Isolation) і скасовує транзакцію, якщо результат міг би відрізнятися від певного послідовного порядку. Правильно за побудовою, але застосунок **мусить повторювати** транзакції, що падають із SQLSTATE `40001`.

## MVCC: як це робить PostgreSQL

PostgreSQL використовує **багатоверсійне керування паралельністю** (MVCC). `UPDATE` не перезаписує рядок; він записує **нову версію** й позначає стару як застарілу. Кожна версія рядка несе id транзакцій, що її створила (`xmin`) і зробила застарілою (`xmax`), а кожен запит має **знімок**, який визначає, які версії йому видно.

Наслідки, які варто знати для співбесід:

- **Читачі ніколи не блокують записувачів, а записувачі — читачів.** Довгий звіт не зупиняє оформлення замовлень. Чекають одне на одного лише два записувачі **того самого рядка**.
- `UPDATE` фактично є вставкою плюс видаленням, тож у таблицях, які часто оновлюють, накопичуються **мертві кортежі**. **VACUUM** (його автоматично запускає autovacuum) звільняє їх; якщо він не встигає, таблиці й індекси **роздуваються**. Довга транзакція заважає прибрати все, що новіше за її знімок.
- Id транзакцій 32-бітні, тож VACUUM має ще й «заморожувати» старі рядки, щоб запобігти **переповненню лічильника транзакцій** (wraparound) — відомій причині аварій, коли autovacuum вимкнено або заблоковано.
- **HOT-оновлення** (heap-only tuples): якщо жоден індексований стовпець не змінюється, а на сторінці є місце, нова версія залишається на тій самій сторінці, і індекси оновлювати не треба. Це одна з причин не індексувати стовпці, які часто змінюються.

## Як уникнути втраченого оновлення

На Read Committed оберіть один зі способів:

```sql
-- 1. Нехай обчислює база: одна атомарна інструкція
UPDATE accounts SET balance = balance + 10 WHERE id = 1;

-- 2. Песимістично: заблокувати рядок, поки думаєте
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- інші чекають тут
UPDATE accounts SET balance = 110 WHERE id = 1;
COMMIT;

-- 3. Оптимістично: виявити конфлікт через стовпець версії (наступна лекція)
UPDATE accounts SET balance = 110, version = version + 1 WHERE id = 1 AND version = 7;

-- 4. Виконати транзакцію на Repeatable Read чи Serializable і повторювати за 40001
```
