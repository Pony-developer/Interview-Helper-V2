Тепер ви знаєте обидва світи: PostgreSQL як реляційну (SQL) базу і MongoDB як документну (NoSQL). Цей слайд ставить їх поруч. Пам'ятайте, що «NoSQL» охоплює дуже різні системи; там, де таблиця каже NoSQL, вона здебільшого описує документні сховища на кшталт MongoDB.

## Велике порівняння

| Аспект | SQL (PostgreSQL) | NoSQL (MongoDB) |
|---|---|---|
| **Модель даних** | Таблиці з рядків і стовпців; зв'язки через ключі | Колекції JSON-подібних документів із вкладеними об'єктами та масивами |
| **Схема** | Оголошується заздалегідь (**schema-on-write**); зміни — через міграції | Гнучка (**schema-on-read**); необов'язкова валідація через `$jsonSchema` |
| **Зв'язки** | Нормалізовано; зовнішні ключі гарантують цілісність; з'єднання дешеві й центральні | Вкладення або посилання; `$lookup` є, але це не головний інструмент; зовнішніх ключів немає |
| **Мова запитів** | SQL: декларативна стандартна мова для довільних запитань | API запитів і конвеєр агрегації (JSON); специфічні для MongoDB |
| **Транзакції** | Повний ACID для будь-яких рядків і таблиць, стандартний спосіб роботи | Атомарність на рівні документа; ACID на кілька документів з 4.0, використовують ощадливо |
| **Узгодженість** | Сильна за замовчуванням | Налаштовувана (write і read concern); сильна з налаштуваннями majority |
| **Масштабування** | Спершу вгору; репліки для читання; масштабування записів ушир потребує інструментів партиціювання (Citus) або NewSQL | Ушир за задумом: набори реплік і вбудований шардинг |
| **Правила цілісності** | `NOT NULL`, `UNIQUE`, `CHECK`, зовнішні ключі, тригери | Унікальні індекси та валідація схеми; решта — у застосунку |
| **Типові сильні сторони** | Складні запити, звітність, гроші, склад, усе з багатьма зв'язками й інваріантами | Записи, які читають і пишуть цілком; структури, що швидко змінюються чи різняться; великі навантаження з масштабуванням ушир |
| **Типові болі** | Міграції схеми на величезних таблицях; масштабування записів понад один primary | Природно реляційні дані; інваріанти між документами; довільна аналітика |

## Ті самі дані, дві форми

```sql
-- SQL: три нормалізовані таблиці, з'єднані під час читання
SELECT o.id, c.name, p.name, oi.quantity
FROM orders o
JOIN customers c    ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p     ON p.id = oi.product_id
WHERE o.id = 1;
```

```js
// MongoDB: один документ у формі екрана, що його показує
db.orders.findOne({ _id: 1 })
// { _id: 1, customer: { _id: 1, name: "Olena Koval" },
//   items: [ { productId: 1, name: "SQL Basics", quantity: 2 }, … ] }
```

SQL-варіант відповідає на **будь-яке** запитання про замовлення, клієнтів і товари, зокрема на ті, про які ще ніхто не подумав. Варіант MongoDB відповідає на **це** запитання одним читанням без з'єднань і легко розподіляється між шардами за id замовлення. Це і є головний компроміс: **гнучкість запитів** проти **відповідності одному шаблону доступу**.

## Схема: хто її забезпечує?

Обидві системи мають схему. Питання в тому, де вона живе:

- У PostgreSQL її забезпечує база. Погані дані не потраплять усередину, а кожен сервіс і скрипт бачить ті самі правила. Ціна — міграції.
- У MongoDB її забезпечує застосунок (плюс необов'язкова валідація). Нове поле не потребує міграції, а документи різних «версій» можуть співіснувати. Ціна — кожен читач мусить обробляти кожну форму, яку будь-коли було записано.

## Узгодженість і масштаб

PostgreSQL дає сильну узгодженість і ACID усюди та масштабується **вгору** дуже далеко: один сучасний сервер обробляє десятки тисяч транзакцій за секунду й багато терабайтів, а репліки додають потужності для читання. MongoDB створено для масштабування **вшир**: шардинг — вбудована можливість, а узгодженість налаштовують для кожної операції.

Розрив скоротився з обох боків. MongoDB додала транзакції на кілька документів, валідацію схеми, `$lookup` і write concern majority за замовчуванням. PostgreSQL додав `jsonb` з GIN-індексами, тож добре зберігає й документи, а розподілені SQL-системи (CockroachDB, YugabyteDB, Spanner, Citus) пропонують SQL з горизонтальним масштабуванням.

## Міфи, яких варто уникати на співбесіді

- «У NoSQL немає схеми»: є неявна.
- «NoSQL не вміє в транзакції»: MongoDB, DynamoDB та інші вміють.
- «SQL-бази не масштабуються»: вони дуже далеко масштабуються вгору, а з правильними інструментами — і вшир; більшість продуктів ніколи не переростає один добре налаштований PostgreSQL.
- «NoSQL швидший»: він швидший **для того шаблону доступу, під який його змодельовано**; для довільних і реляційних запитів він часто повільніший.
- «JSON означає MongoDB»: `jsonb` у PostgreSQL покриває багато документних сценаріїв, зберігаючи SQL і транзакції.

Наступна лекція перетворює це порівняння на процес ухвалення рішення.
