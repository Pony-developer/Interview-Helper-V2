Every column has a type, and choosing it well prevents bugs that no application code can fully catch.

## Numbers

| Type | Range / precision | Use for |
|---|---|---|
| `smallint` | ±32 767 | Small codes |
| `integer` (`int`) | ±2.1 billion | Most counts and ids |
| `bigint` | ±9.2 × 10¹⁸ | Ids of big or fast-growing tables, counters |
| `numeric(p, s)` | Exact, up to `p` digits, `s` after the point | **Money**, anything that must add up exactly |
| `real`, `double precision` | Floating point, approximate | Measurements, science, ML features |

Floating point cannot represent most decimal fractions exactly:

```sql
SELECT 0.1::double precision + 0.2 = 0.3;   -- false
SELECT 0.1::numeric + 0.2 = 0.3;            -- true
```

So prices go into `numeric`, never `float`. Some teams store money as an integer number of cents (`bigint`), which is also exact.

## Text

`text`, `varchar(n)` and `char(n)` exist. In PostgreSQL, `text` and `varchar` are stored the same way and are equally fast; `varchar(n)` only adds a length check. `char(n)` pads with spaces and is almost never what you want. A common modern style is `text` plus a `CHECK (length(name) <= 100)` where a limit matters.

## Booleans

`boolean` holds `true`, `false` or `NULL`. Input accepts `'t'`, `'yes'`, `'1'`, `'on'` and their opposites.

## Date and time

| Type | Example | Notes |
|---|---|---|
| `date` | `2024-06-01` | Calendar date |
| `time` | `14:30:00` | Time of day, rarely useful alone |
| `timestamp` | `2024-06-01 14:30:00` | **Without** time zone: a wall-clock reading |
| `timestamptz` | `2024-06-01 14:30:00+03` | An absolute **moment**; stored in UTC, displayed in the session's `TimeZone` |
| `interval` | `3 days 04:00:00` | A duration |

Use `timestamptz` for "when did this happen": `created_at`, `paid_at`. A plain `timestamp` loses the information about which zone it was in, and the classic bug follows when servers in different zones write to it. Despite the name, `timestamptz` does not store the zone; it converts to UTC on the way in and back to the session zone on the way out.

```sql
SELECT now(),                                  -- current timestamptz
       now() - interval '7 days',              -- a week ago
       date_trunc('month', now()),             -- start of this month
       '2024-06-01'::date + 30;                -- date arithmetic in days
```

## Identifiers

- `integer GENERATED ALWAYS AS IDENTITY` (or `bigint …`) is the modern standard auto-increment column. The older `serial` does the same with an implicit sequence, but identity is the recommended way.
- `uuid` stores 128-bit ids such as `0b9e…`. They can be generated by the application, which helps in distributed systems and hides how many rows you have. `gen_random_uuid()` creates a random UUID v4; PostgreSQL 18 adds `uuidv7()`, which is time-ordered and therefore friendlier to indexes.

Sequences never roll back: if an insert fails or its transaction is rolled back, the number it took is gone, so ids may have **gaps**. Never rely on ids being consecutive.

## Structured types

- **Arrays**: `text[]`, `integer[]`. `ARRAY['a', 'b']`, `tags[1]` (arrays are 1-based), `'sql' = ANY(tags)`.
- **`jsonb`**: binary JSON with indexing and rich operators; a whole lecture covers it later. Prefer `jsonb` over `json` (the latter stores the raw text).
- **Enums**: `CREATE TYPE order_status AS ENUM ('new', 'paid', 'shipped');`. Compact and type-safe, but adding values requires `ALTER TYPE` and removing them is hard, so many teams use `text` plus `CHECK (status IN (…))`, as the shop database does.
- **Ranges**: `int4range`, `tstzrange`, `daterange`; with an exclusion constraint they can forbid overlapping bookings.

## Casting

`'2024-06-01'::date`, `CAST(price AS integer)`, `42::text`. A failed cast is an error: `'abc'::integer` fails with `invalid input syntax for type integer`.
