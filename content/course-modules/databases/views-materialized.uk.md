## Представлення

**Представлення** (view) — це іменований збережений запит, яким можна користуватися як таблицею:

```sql
CREATE VIEW order_totals AS
SELECT o.id AS order_id, c.name AS customer, o.status,
       sum(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN customers c    ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, c.name, o.status;

SELECT * FROM order_totals WHERE total > 100;
```

Представлення **не зберігає даних**. Щоразу, коли його використовують, PostgreSQL підставляє його запит у ваш і планує все разом, тож фільтр на представленні все одно може використовувати індекси базових таблиць.

Навіщо представлення:

- **Повторне використання**: логіка з'єднань і агрегатів живе в одному місці.
- **Стабільний інтерфейс**: застосунок читає `order_totals`; таблиці під ним можна перебудувати, зберігши стовпці представлення.
- **Безпека**: надайте доступ до представлення, що показує частину стовпців чи рядків, а не до таблиць. (Поєднуйте з `security_barrier` або використовуйте політики row-level security.)

`CREATE OR REPLACE VIEW` змінює представлення, якщо ви лише додаєте стовпці в кінець. Прості представлення (одна таблиця, без агрегатів) навіть **оновлювані**: `UPDATE active_customers SET …` записує в базову таблицю.

## Матеріалізовані представлення

**Матеріалізоване представлення** виконує запит один раз і **зберігає результат**, як таблицю:

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT o.ordered_at AS day, sum(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status <> 'cancelled'
GROUP BY o.ordered_at;

CREATE UNIQUE INDEX ON daily_revenue (day);

REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;
```

- Читати його так само швидко, як невелику таблицю, і його можна індексувати.
- Дані — це **знімок**: вони не змінюються, коли змінюються базові таблиці. Його треба `REFRESH`, зазвичай за розкладом (cron, `pg_cron`) або після пакетного завантаження.
- Звичайний `REFRESH` блокує читачів на час виконання; `REFRESH … CONCURRENTLY` — ні, але потребує унікального індексу й працює повільніше.

Типове застосування: дашборди й звіти над великими даними, де «до 5 хвилин давнини» прийнятно. Це денормалізація з вбудованим способом перебудувати копію.

| | Представлення | Матеріалізоване представлення |
|---|---|---|
| Зберігає дані | Ні | Так |
| Завжди актуальне | Так | Лише після `REFRESH` |
| Швидкість читання | Як у запиту під ним | Як у таблиці |
| Індекси | Лише на базових таблицях | На самому представленні |

## Тимчасові таблиці та CTE

Для результату, потрібного кілька разів **в одній сесії**, є ще `CREATE TEMP TABLE … AS SELECT …`; таблиця зникає наприкінці сесії. В межах однієї інструкції цю роль виконує CTE.

## Інші об'єкти, які варто знати

- **Послідовності**: генератори чисел за identity-стовпцями. `nextval('seq')`, `currval`, `setval`.
- **Схеми**: простори імен для впорядкування об'єктів і прав.
- **Ролі та права**: `CREATE ROLE reporting; GRANT SELECT ON order_totals TO reporting;`. Застосунки мають під'єднуватися під роллю лише з потрібними правами, ніколи не як суперкористувач.
- **Row-level security**: `ALTER TABLE orders ENABLE ROW LEVEL SECURITY; CREATE POLICY own_orders ON orders USING (customer_id = current_setting('app.customer_id')::int);`. Кожен запит автоматично бачить лише ті рядки, які дозволяє політика. На цьому побудовано Supabase.
