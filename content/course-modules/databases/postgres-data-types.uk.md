Кожен стовпець має тип, і вдалий вибір запобігає помилкам, які жоден код застосунку повністю не впіймає.

## Числа

| Тип | Діапазон / точність | Для чого |
|---|---|---|
| `smallint` | ±32 767 | Невеликі коди |
| `integer` (`int`) | ±2,1 мільярда | Більшість лічильників та id |
| `bigint` | ±9,2 × 10¹⁸ | Id великих чи швидко зростаючих таблиць, лічильники |
| `numeric(p, s)` | Точний, до `p` цифр, з них `s` після коми | **Гроші**, усе, що має сходитися точно |
| `real`, `double precision` | Рухома кома, наближено | Вимірювання, наука, ознаки для ML |

Рухома кома не може точно зобразити більшість десяткових дробів:

```sql
SELECT 0.1::double precision + 0.2 = 0.3;   -- false
SELECT 0.1::numeric + 0.2 = 0.3;            -- true
```

Тож ціни зберігають у `numeric`, ніколи не у `float`. Деякі команди зберігають гроші як ціле число копійок (`bigint`), що теж точно.

## Текст

Є `text`, `varchar(n)` і `char(n)`. У PostgreSQL `text` і `varchar` зберігаються однаково й однаково швидкі; `varchar(n)` лише додає перевірку довжини. `char(n)` доповнює пробілами, і це майже ніколи не те, що потрібно. Поширений сучасний стиль — `text` плюс `CHECK (length(name) <= 100)` там, де обмеження справді важливе.

## Логічний тип

`boolean` містить `true`, `false` або `NULL`. На вході приймаються `'t'`, `'yes'`, `'1'`, `'on'` та їхні протилежності.

## Дата й час

| Тип | Приклад | Примітки |
|---|---|---|
| `date` | `2024-06-01` | Календарна дата |
| `time` | `14:30:00` | Час доби, сам по собі рідко корисний |
| `timestamp` | `2024-06-01 14:30:00` | **Без** часового поясу: показ настінного годинника |
| `timestamptz` | `2024-06-01 14:30:00+03` | Абсолютний **момент**; зберігається в UTC, показується в `TimeZone` сесії |
| `interval` | `3 days 04:00:00` | Тривалість |

Для «коли це сталося» використовуйте `timestamptz`: `created_at`, `paid_at`. Звичайний `timestamp` втрачає інформацію про пояс, і класична помилка виникає, коли в нього пишуть сервери з різних поясів. Попри назву, `timestamptz` не зберігає пояс: на вході він перетворює час у UTC, а на виході — назад у пояс сесії.

```sql
SELECT now(),                                  -- поточний timestamptz
       now() - interval '7 days',              -- тиждень тому
       date_trunc('month', now()),             -- початок поточного місяця
       '2024-06-01'::date + 30;                -- арифметика дат у днях
```

## Ідентифікатори

- `integer GENERATED ALWAYS AS IDENTITY` (або `bigint …`) — сучасний стандартний автоінкрементний стовпець. Старіший `serial` робить те саме з неявною послідовністю, але рекомендований спосіб — identity.
- `uuid` зберігає 128-бітні id на кшталт `0b9e…`. Їх може генерувати застосунок, що допомагає в розподілених системах і приховує, скільки у вас рядків. `gen_random_uuid()` створює випадковий UUID v4; PostgreSQL 18 додає `uuidv7()`, упорядкований за часом і тому дружніший до індексів.

Послідовності ніколи не відкочуються: якщо вставка не вдалася чи її транзакцію відкотили, взятий номер пропадає, тож в id можуть бути **пропуски**. Ніколи не покладайтеся на те, що id ідуть підряд.

## Структуровані типи

- **Масиви**: `text[]`, `integer[]`. `ARRAY['a', 'b']`, `tags[1]` (масиви нумеруються з 1), `'sql' = ANY(tags)`.
- **`jsonb`**: двійковий JSON з індексами й багатьма операторами; йому присвячено окрему лекцію. Обирайте `jsonb`, а не `json` (останній зберігає сирий текст).
- **Переліки (enum)**: `CREATE TYPE order_status AS ENUM ('new', 'paid', 'shipped');`. Компактно й типобезпечно, але додавання значень потребує `ALTER TYPE`, а видалення складне, тому багато команд використовує `text` плюс `CHECK (status IN (…))`, як у базі магазину.
- **Діапазони**: `int4range`, `tstzrange`, `daterange`; з обмеженням-виключенням вони можуть заборонити бронювання, що перетинаються.

## Перетворення типів

`'2024-06-01'::date`, `CAST(price AS integer)`, `42::text`. Невдале перетворення — це помилка: `'abc'::integer` падає з `invalid input syntax for type integer`.
