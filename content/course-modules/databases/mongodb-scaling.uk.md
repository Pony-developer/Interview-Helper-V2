## Індекси

Індекси MongoDB — це B-дерева, як і в PostgreSQL, і та сама інтуїція працює: без індексу запит — це **сканування колекції** (`COLLSCAN`).

```js
db.products.createIndex({ category: 1, price: -1 })          // складений
db.users.createIndex({ email: 1 }, { unique: true })         // унікальний
db.products.createIndex({ tags: 1 })                         // multikey: запис на кожен елемент масиву
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })   // TTL: автовидалення
db.orders.createIndex({ status: 1 }, { partialFilterExpression: { status: "new" } })
db.articles.createIndex({ title: "text", body: "text" })     // повнотекстовий
db.places.createIndex({ location: "2dsphere" })              // геозапити
```

**Правило ESR** для складених індексів: спершу поля **рівності** (Equality), потім поля **сортування** (Sort), потім поля **діапазону** (Range). Для `find({ status: "A", qty: { $gt: 5 } }).sort({ date: -1 })` індекс — `{ status: 1, date: -1, qty: 1 }`. Це та сама логіка найлівішого префікса, що й у SQL.

`explain("executionStats")` показує обраний план, `totalKeysExamined`, `totalDocsExamined` і `nReturned`. Здоровий запит переглядає приблизно стільки документів, скільки повертає.

## Набори реплік: доступність

**Набір реплік** (replica set) — група серверів `mongod` з тими самими даними: один **primary** приймає записи, **secondary** реплікують його журнал операцій (oplog). Якщо primary падає, решта членів **обирає** новий primary за кілька секунд, і драйвери автоматично перепідключаються. Три члени (або два плюс арбітр) — мінімум для автоматичного перемикання, бо виборам потрібна більшість.

Два налаштування керують компромісом узгодженість/затримка з лекції про CAP:

- **Write concern**: коли запис підтверджується? `w: 1` — коли його має primary (швидко, але перемикання може його відкотити); `w: "majority"` — коли його має більшість членів (переживає перемикання, типово з MongoDB 5.0). `j: true` чекає запису в журнал на диску.
- **Read preference і read concern**: читати з `primary` (актуальні дані) чи з `secondary` (розподіляє навантаження, може трохи відставати); `readConcern: "majority"` повертає лише дані, які не можуть бути відкочені.

Із записами більшістю, читаннями більшістю та читанням із primary ви отримуєте сильну узгодженість для окремих документів. Сесії з **причинною узгодженістю** (causal consistency) дозволяють «читати власні записи» з secondary.

## Шардинг: масштабування вшир

Коли один набір реплік не вміщує даних чи навантаження записів, **шардинг** розбиває колекцію між кількома наборами реплік (шардами). Клієнти працюють із маршрутизаторами `mongos`, які за **ключем шардингу** надсилають кожен запит на потрібні шарди. Конфігураційні сервери зберігають, який діапазон ключів де лежить; балансувальник переносить чанки між шардами, вирівнюючи навантаження.

**Ключ шардингу** — найважливіше (а в старих версіях ще й незворотне) рішення:

| Властивість | Чому |
|---|---|
| **Висока кардинальність** | Досить різних значень, щоб розбити на багато чанків |
| **Рівномірний розподіл** | Жодне значення не тримає більшість даних |
| **Не монотонно зростаючий** для шардингу за діапазонами | Інакше всі вставки йдуть в останній чанк: **гарячий шард** |
| **Відповідає основним запитам** | Запити з ключем шардингу йдуть на один шард; без нього — **scatter-gather** по всіх шардах |

Варіанти: ключі за **діапазонами** (добре для запитів діапазонів), **хешовані** ключі (рівномірні записи, але запити діапазонів зачіпають усі шарди) або **складені** ключі на кшталт `{ customerId: 1, orderDate: 1 }`, що тримають дані одного клієнта разом і розподіляють клієнтів між шардами.

## Транзакції

Операції з одним документом завжди атомарні. З MongoDB 4.0 (набори реплік) і 4.2 (шардовані кластери) є й **ACID-транзакції на кілька документів**:

```js
const session = client.startSession();
await session.withTransaction(async () => {
  await accounts.updateOne({ _id: 1 }, { $inc: { balance: -100 } }, { session });
  await accounts.updateOne({ _id: 2 }, { $inc: { balance: 100 } }, { session });
});
```

Вони працюють, але коштують дорожче, ніж у реляційній базі (особливо між шардами), мають часові обмеження (типово 60 секунд) і мають бути винятком. Якщо більшість операцій потребує транзакції, то або модель має більше вкладати, або задачі краще підходить реляційна база.

## Change streams

`collection.watch()` транслює вставки, оновлення й видалення в реальному часі (на основі oplog). На цьому будують інвалідацію кешів, синхронізацію пошукових індексів і інтеграції на подіях, подібно до логічної реплікації / CDC (Debezium) у PostgreSQL.

## Відповідники в PostgreSQL

| MongoDB | PostgreSQL |
|---|---|
| Набір реплік з автоматичним перемиканням | Потокова реплікація + менеджер перемикання (Patroni) або керований сервіс |
| Write concern `majority` | `synchronous_commit` із синхронними резервними серверами |
| Шардинг | Партиціювання на одному вузлі; розширення Citus або NewSQL-система для масштабування вшир |
| TTL-індекс | `DELETE` за розкладом або видалення часових партицій |
| Change streams | Логічна реплікація, `LISTEN/NOTIFY`, CDC-інструменти |

Вбудоване горизонтальне масштабування залишається одним із найсильніших аргументів MongoDB; PostgreSQL масштабується вгору дуже далеко на одній машині, а для масштабування записів ушир потребує додаткових інструментів.
