`EXPLAIN` показує **план**, який PostgreSQL обрав для запиту: які таблиці він читає, як, у якому порядку й якими алгоритмами з'єднання. Це перший інструмент для будь-якої проблеми «цей запит повільний».

## EXPLAIN

```sql
EXPLAIN
SELECT c.name, o.id
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.city = 'Kyiv';
```

```text
Hash Join  (cost=1.09..2.24 rows=2 width=36)
  Hash Cond: (o.customer_id = c.id)
  ->  Seq Scan on orders o  (cost=0.00..1.08 rows=8 width=8)
  ->  Hash  (cost=1.07..1.07 rows=2 width=36)
        ->  Seq Scan on customers c  (cost=0.00..1.07 rows=2 width=36)
              Filter: (city = 'Kyiv'::text)
```

Як це читати:

- Це **дерево**. Читайте від найглибше вкладених вузлів угору: кожен вузол отримує рядки від дочірніх і передає рядки батьківському. Тут клієнти з Києва скануються й хешуються, замовлення скануються й перевіряються за хешем.
- `cost=1.09..2.24`: оцінена вартість отримання першого рядка й усіх рядків в абстрактних одиницях (приблизно «читання сторінок»). Корисна лише для порівняння планів.
- `rows=2`: **оцінена** кількість рядків. `width`: середній розмір рядка в байтах.
- `Filter`: умова, яку перевіряють для кожного рядка після читання. `Index Cond`: умова, за якою шукають в індексі.

## EXPLAIN ANALYZE

`EXPLAIN ANALYZE` **виконує** запит і додає те, що сталося насправді:

```text
Index Scan using orders_customer_id_idx on orders  (cost=0.29..8.31 rows=1 width=16)
                                                   (actual time=0.020..0.025 rows=3 loops=1)
  Index Cond: (customer_id = 42)
Planning Time: 0.110 ms
Execution Time: 0.050 ms
```

- `actual time=0.020..0.025`: мілісекунди до першого й останнього рядка, **на один цикл**.
- `rows=3 loops=1`: справжні рядки на цикл. У nested loop множте на `loops`.
- Додайте `BUFFERS`, щоб побачити, скільки сторінок прийшло з пам'яті (`shared hit`), а скільки з диска (`read`). Починаючи з PostgreSQL 18, `EXPLAIN ANALYZE` показує буфери за замовчуванням.

Обережно: `EXPLAIN ANALYZE` для `UPDATE` чи `DELETE` справді змінює дані. Обгортайте його в `BEGIN; … ROLLBACK;`.

## На що дивитися

1. **Оцінені проти справжніх рядків.** Якщо планувальник очікував 10 рядків, а отримав 100 000, кожне рішення над цим вузлом може бути хибним (nested loop, обраний для «10 рядків»). Виправте статистику: `ANALYZE`, вища ціль статистики або розширена статистика для корельованих стовпців.
2. **Seq Scan великої таблиці з вибірковим Filter**, де `Rows Removed by Filter` обчислюється мільйонами: бракує індексу.
3. **Sort** з `Sort Method: external merge  Disk: …`: сортування вилилося на диск; допоможе індекс під `ORDER BY` або більше `work_mem`.
4. **Nested Loop з великим `loops`** над Seq Scan: бракує індексу на стовпці з'єднання внутрішнього боку.
5. Куди йде **час**: знайдіть вузол, чий справжній час становить найбільшу частку загального.

## Типи вузлів, які ви зустрінете

| Вузол | Значення |
|---|---|
| `Seq Scan` | Прочитати всю таблицю |
| `Index Scan` / `Index Only Scan` | Пошук через індекс (і купу / без купи) |
| `Bitmap Index Scan` → `Bitmap Heap Scan` | Зібрати збіги з індексу, потім читати сторінки по порядку |
| `Nested Loop`, `Hash Join`, `Merge Join` | Алгоритми з'єднання |
| `Sort`, `Incremental Sort` | Сортування |
| `HashAggregate`, `GroupAggregate` | `GROUP BY` |
| `Limit` | Зупинитися після n рядків; з індексом під `ORDER BY` сканування нижче зупиняється рано |

## Параметри

- `EXPLAIN (COSTS OFF)` приховує числа: зручно для порівняння форми планів, і саме так зроблено в практиці цього модуля.
- `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` видає JSON для візуалізаторів на кшталт explain.dalibo.com.

## Ширше за один запит

- `pg_stat_statements` (розширення) збирає статистику для кожної форми запиту: загальний час, кількість викликів, середній час. Починайте оптимізацію з його верхніх рядків, а не з припущень.
- `auto_explain` автоматично записує в журнал плани повільних запитів.
- Часто виправлення — не індекс, а сам запит: брати менше стовпців, уникати N+1 запитів з ORM, пагінувати за ключем замість `OFFSET`.
