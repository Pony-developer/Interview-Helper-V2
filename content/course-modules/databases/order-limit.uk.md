Рядки в таблиці не мають порядку. Якщо порядок результату важливий, а для всього, що бачить користувач, він майже завжди важливий, скажіть про це через `ORDER BY`.

## ORDER BY

```sql
SELECT name, price FROM products ORDER BY price;          -- за зростанням (ASC — типово)
SELECT name, price FROM products ORDER BY price DESC;     -- за спаданням
SELECT name, city  FROM customers ORDER BY city, name;    -- за містом, а в межах міста — за іменем
```

- Кожен ключ має власний напрямок: `ORDER BY category_id ASC, price DESC`.
- Сортувати можна за виразом або псевдонімом із `SELECT`: `ORDER BY price * stock DESC`, `ORDER BY sale_price`.
- `ORDER BY 2` сортує за другим стовпцем `SELECT`. Це працює, але тихо ламається, коли хтось переставить стовпці.

## Куди потрапляють NULL?

У PostgreSQL `NULL` вважається **більшим** за будь-яке значення: він іде останнім при `ASC` і першим при `DESC`. Змінити це можна через `NULLS FIRST` / `NULLS LAST`:

```sql
SELECT name, city FROM customers ORDER BY city NULLS FIRST;
SELECT name, city FROM customers ORDER BY city DESC NULLS LAST;
```

Інші бази поводяться інакше (MySQL і SQL Server ставлять `NULL` першим при `ASC`), тож явність робить запит переносним.

## Зробіть порядок унікальним

Якщо два рядки мають однаковий ключ сортування, їхній взаємний порядок **не визначено**, і він може змінюватися між запусками, особливо після оновлень таблиці. Для звіту це не страшно, але ламає пагінацію: рядок може з'явитися на двох сторінках або на жодній. Додайте останнім ключем унікальний стовпець:

```sql
SELECT id, name, price FROM products ORDER BY price DESC, id;
```

## LIMIT і OFFSET

```sql
SELECT name, price FROM products ORDER BY price DESC LIMIT 3;            -- перші 3
SELECT name, price FROM products ORDER BY price DESC LIMIT 3 OFFSET 3;   -- рядки 4–6
```

Стандартний запис, який теж підтримує PostgreSQL: `OFFSET 3 ROWS FETCH FIRST 3 ROWS ONLY`. `FETCH FIRST 3 ROWS WITH TIES` повертає ще й рядки, що мають той самий ключ, що й останній.

`LIMIT` без `ORDER BY` повертає «якісь» рядки, а це рідко те, що потрібно.

## Номери сторінок: пагінація через OFFSET

Сторінка `n` (від 1) розміром `size` — це `LIMIT size OFFSET (n - 1) * size`. Це просто й дозволяє перейти на будь-яку сторінку, але:

- **кожна наступна сторінка повільніша**: `OFFSET 100000` змушує базу знайти й викинути 100 000 рядків;
- **це нестабільно**: якщо рядок вставили чи видалили, поки користувач читає, наступні сторінки зсуваються, і рядок показується двічі або пропускається.

## Пагінація за ключем (курсором)

Замість «пропусти N рядків» запам'ятайте останній рядок, який побачив користувач, і попросіть рядки після нього:

```sql
-- перша сторінка
SELECT id, name, price FROM products ORDER BY price DESC, id DESC LIMIT 3;

-- наступна сторінка: останній рядок попередньої мав ціну 48.50 та id 2
SELECT id, name, price FROM products
WHERE (price, id) < (48.50, 2)
ORDER BY price DESC, id DESC
LIMIT 3;
```

Порівняння рядків `(price, id) < (48.50, 2)` означає «ціна менша, або ціна така сама, а id менший», що збігається з порядком сортування, коли обидва ключі йдуть в одному напрямку. З індексом по `(price, id)` кожна сторінка коштує однаково, хоч як глибоко гортає користувач. Ціна цього — неможливість перейти одразу на 57-му сторінку. Тому стрічки та нескінченне прокручування (і більшість публічних API — як параметр `cursor`) використовують пагінацію за ключем, а адмінські таблиці з номерами сторінок — `OFFSET`.
