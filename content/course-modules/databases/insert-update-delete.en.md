Three statements change data: `INSERT` adds rows, `UPDATE` changes them and `DELETE` removes them.

## INSERT

```sql
-- one row; always list the columns
INSERT INTO customers (id, name, email, city, created_at)
VALUES (7, 'Bohdana Lysenko', 'bohdana@example.com', 'Dnipro', current_date);

-- several rows in one statement: much faster than one INSERT per row
INSERT INTO categories (id, name)
VALUES (5, 'Toys'), (6, 'Music');

-- the result of a query
INSERT INTO archived_orders (id, customer_id, status, ordered_at)
SELECT id, customer_id, status, ordered_at
FROM orders
WHERE ordered_at < '2024-07-01';
```

- Columns you leave out get their `DEFAULT`, or `NULL` if there is none.
- `DEFAULT` can be written explicitly: `VALUES (DEFAULT, 'x')`.
- An identity column declared `GENERATED ALWAYS` refuses explicit values unless you write `OVERRIDING SYSTEM VALUE`; `GENERATED BY DEFAULT` accepts them.
- For bulk loads of thousands of rows, `COPY` (or `\copy` in psql) is far faster than `INSERT`.

## UPDATE

```sql
UPDATE products
SET price = price * 0.9,
    stock = stock + 5
WHERE category_id = 3;
```

All expressions on the right see the **old** row, so `SET a = b, b = a` swaps two columns.

Update from another table with `FROM` (a PostgreSQL extension; the standard way is a subquery):

```sql
-- mark orders of customers from Odesa as cancelled
UPDATE orders AS o
SET status = 'cancelled'
FROM customers AS c
WHERE c.id = o.customer_id
  AND c.city = 'Odesa';
```

## DELETE

```sql
DELETE FROM orders WHERE status = 'cancelled';

-- delete with a condition on another table
DELETE FROM order_items AS oi
USING orders AS o
WHERE o.id = oi.order_id AND o.status = 'cancelled';
```

## Forgetting WHERE

`UPDATE products SET price = 0;` and `DELETE FROM orders;` are valid statements that affect **every** row. Habits that save careers:

- write the `WHERE` first, or run the same condition as a `SELECT count(*)` before the change;
- in a console, open a transaction (`BEGIN`), make the change, check the result, then `COMMIT` or `ROLLBACK`;
- `psql` reports `UPDATE 1000000`: read that number.

## Soft delete

Many systems never `DELETE` business rows. They add `deleted_at timestamptz` and set it instead, so data can be restored and audited. The cost: every query must remember `WHERE deleted_at IS NULL`, unique constraints must become partial (`UNIQUE … WHERE deleted_at IS NULL`), and the table keeps growing. A view or row-level security can hide the deleted rows.

## Batching big changes

One `UPDATE` of 50 million rows holds locks on all of them until it commits, bloats the table and produces a huge amount of write-ahead log for replicas to catch up on. Large backfills are done in batches:

```sql
UPDATE products SET sku = 'P-' || id
WHERE id IN (SELECT id FROM products WHERE sku IS NULL LIMIT 5000);
-- repeat until it updates 0 rows
```
