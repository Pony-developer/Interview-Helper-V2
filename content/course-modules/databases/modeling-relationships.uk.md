## Від вимог до таблиць

Практичний спосіб спроєктувати схему:

1. Перелічіть **сутності** (іменники): клієнт, товар, замовлення, категорія, тег.
2. Перелічіть їхні **атрибути** й вирішіть, які обов'язкові (`NOT NULL`) та унікальні.
3. Знайдіть **зв'язки** та їхню кратність («один клієнт має багато замовлень»).
4. Додайте обмеження для бізнес-правил: `CHECK`, `UNIQUE`, зовнішні ключі.
5. Подумайте про основні запити й додайте для них індекси.

Діаграма «сутність-зв'язок» (ER) малює саме це: прямокутники для таблиць, лінії для зовнішніх ключів, а «воронячі лапки» позначають бік «багатьох».

## Один-до-багатьох

Найпоширеніший зв'язок. Зовнішній ключ ставлять на бік «багатьох»:

```sql
CREATE TABLE orders (
    id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id integer NOT NULL REFERENCES customers (id)
);
CREATE INDEX ON orders (customer_id);   -- зовнішні ключі не індексуються автоматично
```

`NOT NULL` робить зв'язок обов'язковим (замовлення мусить мати клієнта); без нього він необов'язковий.

## Багато-до-багатьох

Товар може мати багато тегів, а тег може бути на багатьох товарах. Жоден бік не може тримати один зовнішній ключ, тож пари зберігає **проміжна таблиця** (її ще називають таблицею зв'язку чи асоціативною):

```sql
CREATE TABLE product_tags (
    product_id integer NOT NULL REFERENCES products (id) ON DELETE CASCADE,
    tag_id     integer NOT NULL REFERENCES tags (id) ON DELETE CASCADE,
    PRIMARY KEY (product_id, tag_id)          -- кожна пара не більше одного разу
);
CREATE INDEX ON product_tags (tag_id);         -- індекс PK покриває пошук за product_id
```

Складений первинний ключ не дає дублювати пари й обслуговує пошук за `product_id`; другий індекс обслуговує «усі товари з цим тегом». Проміжна таблиця може містити атрибути самого зв'язку: `order_items` — це проміжна таблиця між замовленнями й товарами з `quantity` та `unit_price`.

## Один-до-одного

Користувач і його профіль, замовлення та його доставка. Або спільний первинний ключ, або **унікальний** зовнішній ключ з одного боку:

```sql
CREATE TABLE user_profiles (
    user_id integer PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
    bio     text,
    avatar  text
);
```

Розділення один-до-одного корисне, коли додаткові стовпці великі, рідко читаються, необов'язкові або мають інші права доступу.

## Ієрархії

Дерево в одній таблиці використовує зовнішній ключ на саму себе (**список суміжності**): `employees.manager_id → employees.id`, `categories.parent_id → categories.id`. Запитують його рекурсивними CTE. Альтернативи для дерев, які переважно читають: **матеріалізований шлях** (`'1.4.17'`, у PostgreSQL є навіть тип `ltree`) або **таблиця замикання**, що зберігає кожну пару предок–нащадок.

## Ключі: сурогатні чи природні

- **Природний ключ** походить із предметної області: email, ISBN, код країни.
- **Сурогатний ключ** не має змісту: identity-число або UUID.

Більшість таблиць має сурогатний первинний ключ, бо природні значення змінюються (люди міняють email), а зміна первинного ключа мала б каскадно пройти всіма таблицями, що на нього посилаються. Природний ключ залиште як обмеження `UNIQUE`, щоб бізнес-правило все одно перевірялося.

`bigint` identity чи `uuid`: identity-значення малі, швидкі й упорядковані, але видають, скільки у вас рядків, і їх має генерувати база. UUID можна генерувати будь-де, їх безпечно показувати й поєднувати між системами, але вони більші; випадкові UUID v4 розкидають вставки по всьому індексу, тому сучасний вибір — упорядкований за часом **UUID v7**.

## Поліморфні дані

Товари різних видів мають різні атрибути. Варіанти:

| Дизайн | Ідея | Компроміс |
|---|---|---|
| Одна таблиця, стовпці з NULL | `pages`, `resolution`, `color`… | Багато NULL, але просто |
| Таблиця на тип | `books`, `monitors` зі спільним `products.id` | Чисто, але більше з'єднань і таблиць |
| Стовпець `jsonb` | Спільні стовпці + `attributes jsonb` | Гнучко й індексується; слабша валідація |
| Сутність–атрибут–значення | Рядки `(product_id, attribute, value)` | Дуже гнучко, болісно запитувати й типізувати: зазвичай антипатерн |

У PostgreSQL «реляційні стовпці для того, за чим фільтруєте й з'єднуєте, `jsonb` для довгого хвоста» — сильний вибір за замовчуванням. Це вже півдороги до документної бази, з якої починається NoSQL-частина курсу.
