«Яку базу ви б тут використали?» — стандартне запитання з проєктування систем. Сильна відповідь — це не улюблений продукт, а коротке міркування від вимог до вибору, разом із тим, чим ви жертвуєте.

## Що спитати насамперед

1. **Яка форма даних?** Багато сутностей зі зв'язками й правилами (реляційна), самодостатні агрегати (документи), чистий пошук за ключем (ключ-значення), зв'язки важливіші за сутності (граф), вимірювання, які лише дописуються (часові ряди).
2. **Як їх читатимуть і записуватимуть?** Відомі стабільні шаблони доступу на користь моделі, побудованої під них; довільні запитання й звітність — на користь SQL.
3. **Що ніколи не має зламатися?** Гроші, залишки, бронювання, права доступу: потрібні ACID-транзакції та обмеження.
4. **Скільки і як швидко?** Тисячі записів за секунду легко вміщує один PostgreSQL; мільйони за секунду в кількох регіонах — інша задача.
5. **Узгодженість проти доступності**: чи може користувач ненадовго бачити застарілі дані? Чи мають записи тривати під час розділення мережі?
6. **Команда й експлуатація**: що знає команда, що доступне як керований сервіс, що ви зможете зарезервувати, моніторити й відновити о третій ночі?

## Вибір за замовчуванням для типових сценаріїв

| Сценарій | Добрий вибір за замовчуванням | Чому |
|---|---|---|
| Типовий веб/мобільний бекенд, SaaS, e-commerce | **PostgreSQL** (або MySQL) | Реляційні дані, транзакції, гнучкі запити; `jsonb` для різнорідних частин |
| Гроші, облік, склад, бронювання | **Реляційна** | ACID, обмеження, аудит |
| Контент різної структури, каталоги, CMS, профілі | **MongoDB** або PostgreSQL + `jsonb` | Читання цілих документів, форми, що змінюються |
| Кеш, сесії, ліміти частоти, рейтинги, черги | **Redis** | Швидкість у пам'яті, TTL, структури даних |
| Величезні навантаження на запис, кілька регіонів, відомі запити | **Cassandra / ScyllaDB**, DynamoDB | Лінійне горизонтальне масштабування, висока доступність |
| Повнотекстовий пошук, дослідження логів | **Elasticsearch / OpenSearch** (або повнотекстовий пошук PostgreSQL для невеликих випадків) | Інвертовані індекси, ранжування за релевантністю |
| Метрики та IoT | База **часових рядів** (TimescaleDB, InfluxDB, ClickHouse) | Стиснення, партиціювання за часом, проріджування |
| Аналітика над великою історією | **Стовпцеве сховище / warehouse** (ClickHouse, BigQuery, Snowflake) | Швидко сканує мільярди рядків |
| Соціальні графи, шахрайські мережі, рекомендації | **Графова база** (Neo4j) | Багатокрокові обходи |
| Семантичний пошук для AI | **pgvector** у PostgreSQL або векторна база | Пошук найближчих сусідів серед ембедингів |

«Починайте з PostgreSQL, якщо немає конкретної причини інакше» — обґрунтований вибір за замовчуванням для нового продукту: він досить добре покриває реляційні дані, документи (`jsonb`), повнотекстовий пошук, геодані (PostGIS), черги (`SKIP LOCKED`) і вектори (pgvector), щоб відкласти додавання інших систем, доки потреба не стане реальною.

## Polyglot persistence

Реальні системи часто поєднують кілька сховищ, кожне для того, що воно робить найкраще:

```text
                 ┌──────────────┐
  API ──────────►│  PostgreSQL  │  замовлення, платежі, користувачі (джерело правди)
   │             └──────┬───────┘
   │                    │ change data capture / outbox
   │      ┌─────────────┼──────────────┬───────────────┐
   ▼      ▼             ▼              ▼               ▼
 Redis  Elasticsearch  ClickHouse    MongoDB        S3
 кеш    пошук товарів   аналітика     стрічка подій  файли
```

Кожна додаткова база додає експлуатаційної роботи, ще один спосіб відмови і питання **синхронізації копій**. Використовуйте одну систему як **джерело правди** й надійно поширюйте зміни: транзакційний **патерн outbox** (записати подію в таблицю outbox у тій самій транзакції, обробник її публікує) або **change data capture** (Debezium, що читає WAL). Уникайте «подвійних записів» з коду застосунку у дві бази без транзакції між ними.

## Відповідь у стилі співбесіди

> «Для сервісу замовлень я обрав би PostgreSQL: замовлення, платежі та залишки потребують транзакцій і обмежень, а бізнес захоче довільних звітів. Атрибути товарів залежать від категорії, тож каталог тримає основні стовпці типізованими, а решту кладе в стовпець `jsonb` з GIN-індексом. Гарячі сторінки товарів і сесії йдуть через Redis з коротким TTL. Якщо пошуку потрібні релевантність і фасети, я додав би OpenSearch, що наповнюється через change data capture. Шардинг чи NoSQL-сховище я розглядав би лише для конкретного компонента, як-от стрічки активності з дуже високим обсягом записів, і лише коли вимірювання покажуть, що одного primary PostgreSQL замало».

Вона називає вимоги, обирає варіанти за замовчуванням, пояснює компроміси й каже, коли рішення змінилося б. Саме це хочуть почути інтерв'юери.
