У SQL спершу нормалізують, а запити з'єднують частини. У MongoDB головне правило протилежне: **проєктуйте під те, як застосунок читає й записує дані**. «Дані, до яких звертаються разом, мають зберігатися разом».

## Вкладати чи посилатися?

**Вкладення** кладе пов'язані дані всередину батьківського документа:

```js
// замовлення з позиціями та знімком адреси доставки
{
  _id: 1001,
  customerId: 42,
  status: "shipped",
  items: [
    { productId: 1, name: "SQL Basics", quantity: 2, price: 25.0 },
    { productId: 4, name: "Wireless Mouse", quantity: 1, price: 19.99 }
  ],
  shipping: { city: "Kyiv", street: "Khreshchatyk 1" }
}
```

Одне читання повертає все замовлення, а його зміна — одна атомарна операція.

**Посилання** зберігає id, як зовнішній ключ:

```js
{ _id: 42, name: "Olena Koval", email: "olena@example.com" }     // customers
{ _id: 1001, customerId: 42, status: "shipped", … }              // orders
```

| Вкладайте, коли | Посилайтеся, коли |
|---|---|
| Дочірні дані належать батьку й читаються разом із ним (позиції замовлення, адреси) | Пов'язана сутність незалежна й має власне життя (клієнти, товари) |
| Зв'язок «один-до-кількох» | «Один-до-багатьох» з **необмеженим** зростанням (перегляди сторінок користувача, допис зі 100 000 коментарів) |
| Вкладені дані рідко змінюються або потрібен саме знімок | Дані спільні для багатьох батьків і часто оновлюються |
| Потрібні атомарні оновлення батька й дочірніх даних | Документ наближався б до межі 16 МБ |

**Необмежений масив** — класичний антипатерн MongoDB: документ, що росте вічно, дедалі повільніше читається, записується й індексується, а зрештою впирається в межу розміру.

## Дублювання — це інструмент

У замовленні вище `name` і `price` товару скопійовано в позицію. Для ціни це правильний знімок (точно як `order_items.unit_price` у SQL). Для назви це свідома денормалізація: список замовлень не потребує lookup, ціною оновлення копій у разі перейменування товару (або згоди з тим, що старі замовлення показують стару назву).

Перед дублюванням поставте два запитання: як часто змінюється джерело і наскільки погано, якщо копія застаріє?

## Поширені шаблони

| Шаблон | Ідея | Приклад |
|---|---|---|
| **Subset** (підмножина) | Вкладати лише найуживанішу частину, на решту посилатися | Товар із 10 найновішими відгуками всередині; усі відгуки — в колекції `reviews` |
| **Extended reference** (розширене посилання) | Копіювати кілька полів, які завжди показують поряд з id | `customer: { _id, name }` у кожному замовленні |
| **Bucket** (кошик) | Групувати багато дрібних записів у документи за часовими вікнами | Один документ на датчик на годину з масивом вимірювань |
| **Computed** (обчислене) | Зберігати попередньо обчислені значення, оновлювані під час запису | `ratingCount` і `ratingAvg` у товарі |
| **Polymorphic** (поліморфний) | Різні форми в одній колекції з полем `type` | Товари різних видів у `products` |
| **Schema versioning** (версії схеми) | Поле `schemaVersion`; ліниво мігрувати під час читання | Розвиток документів без простою |

## Багато-до-багатьох

Студенти й курси: або масив id курсів у кожному студенті (та/або id студентів у кожному курсі), або окрема колекція `enrollments`, коли зв'язок має власні дані (оцінка, дата) чи сильно росте. Масив посилань із multikey-індексом добре відповідає і на «курси студента», і на «студенти курсу».

## Валідація схеми

«Без схеми» насправді означає «схема живе в застосунку». Важливі частини можна вимагати в базі:

```js
db.createCollection("orders", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["customerId", "status", "items"],
    properties: {
      status: { enum: ["new", "paid", "shipped", "cancelled"] },
      items:  { bsonType: "array", minItems: 1 }
    }
  } }
})
```

Унікальність забезпечують унікальні індекси. Зовнішніх ключів немає: посилальна цілісність — відповідальність застосунку, і це одна з реальних цін цієї моделі.

## Погляд із боку SQL

Моделювання замовлення як одного документа близьке до рядка PostgreSQL зі стовпцем `jsonb items`, а «розширене посилання» — це денормалізований стовпець. Різниця — у відправній точці: SQL починає з нормалізації й денормалізує там, де це показують вимірювання; MongoDB починає зі шаблонів доступу й нормалізує (посилається) там, де цього вимагає зростання чи спільне використання.
