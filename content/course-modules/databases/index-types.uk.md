## Складені індекси та порядок стовпців

Індекс може охоплювати кілька стовпців. B-tree по `(user_id, created_at)` сортує спершу за `user_id`, а в межах одного користувача — за `created_at`, як телефонна книга, відсортована за прізвищем, а потім за ім'ям.

Звідси правило **найлівішого префікса**:

| Запит | Чи добре використовує `(user_id, created_at)`? |
|---|---|
| `WHERE user_id = 42` | Так |
| `WHERE user_id = 42 AND created_at > '2024-06-01'` | Так: один суцільний діапазон |
| `WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10` | Так, ідеально: прочитати діапазон користувача у зворотному напрямку й зупинитися після 10 |
| `WHERE created_at > '2024-06-01'` | Погано: дати розкидані між усіма користувачами |

Поради щодо порядку стовпців:

1. Спершу стовпці, які порівнюють через `=`, потім стовпець для діапазону чи `ORDER BY`.
2. Серед стовпців рівності порядок менш важливий; першим ставте той, що потрібен і іншим запитам, щоб індекс обслуговував і їх.

Індекс по `(a, b)` обслуговує й запити лише по `a`, тож окремий індекс по `a` зазвичай зайвий.

(PostgreSQL 18 додав **skip scan**, який може використати складений індекс навіть без умови на перший стовпець, коли той має мало різних значень. Це допомагає, але проєктувати індекси довкола найлівішого префікса — усе ще правило.)

## Покривальні індекси

Якщо індекс містить усі стовпці, потрібні запиту, PostgreSQL може відповісти лише з індексу (**Index Only Scan**). `INCLUDE` додає стовпці-навантаження, що зберігаються, але не є частиною ключа:

```sql
CREATE INDEX orders_customer_idx ON orders (customer_id) INCLUDE (status, ordered_at);
```

## Часткові індекси

Індекс може охоплювати лише ті рядки, які ви запитуєте:

```sql
-- шукають лише необроблені завдання
CREATE INDEX jobs_pending_idx ON jobs (created_at) WHERE status = 'pending';

-- унікальність лише серед активних рядків (з м'яким видаленням)
CREATE UNIQUE INDEX users_email_active_key ON users (email) WHERE deleted_at IS NULL;
```

Часткові індекси менші й дешевші в підтримці. Щоб такий індекс використовувався, `WHERE` запиту має випливати з умови індексу.

## Індекси за виразами

Проіндексуйте результат виразу, і запити з тим самим виразом зможуть ним скористатися:

```sql
CREATE INDEX customers_email_lower_idx ON customers (lower(email));
SELECT * FROM customers WHERE lower(email) = 'olena@example.com';   -- використовує його

CREATE INDEX orders_day_idx ON orders ((ordered_at::date));         -- зверніть увагу на подвійні дужки
```

## Інші типи індексів

| Тип | Для чого | Приклад |
|---|---|---|
| **B-tree** | Рівність, діапазони, сортування: типовий | `WHERE price < 100 ORDER BY price` |
| **Hash** | Лише рівність | Рідко кращий за B-tree |
| **GIN** (узагальнений інвертований індекс) | Значення, що містять багато елементів: масиви, `jsonb`, повнотекстовий пошук | `tags @> ARRAY['sql']`, `doc @> '{"color":"red"}'`, `tsv @@ to_tsquery('postgres')` |
| **GiST** | Геометричні дані, діапазони, пошук найближчих сусідів; обмеження-виключення | PostGIS, `during && tstzrange(…)` |
| **SP-GiST** | Незбалансовано розбиті дані: квадродерева, префікси | Діапазони IP, телефонні префікси |
| **BRIN** (індекс діапазонів блоків) | Величезні таблиці, значення яких іде за фізичним порядком (журнали лише з дописуванням, часові ряди) | `created_at` у журналі на мільярд рядків: крихітний індекс |

Розширення додають більше: `pg_trgm` з GIN дає швидкий `LIKE '%abc%'` і нечіткий пошук, а `pgvector` додає індекси HNSW та IVFFlat для пошуку схожих AI-ембедингів.

## Вибір індексів на співбесіді

Добра відповідь іде від запиту до індексу, а не навпаки:

1. Які запити повільні чи часті? (`pg_stat_statements` показує найважчі.)
2. За чим вони фільтрують, з'єднують і сортують?
3. Спершу стовпці рівності, потім стовпець діапазону/сортування; подумайте про `INCLUDE` для index-only scan і частковий індекс для гарячої підмножини.
4. Перевірте план через `EXPLAIN ANALYZE` і пам'ятайте про ціну запису.
