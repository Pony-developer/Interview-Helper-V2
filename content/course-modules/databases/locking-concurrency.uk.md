MVCC прибирає більшість конфліктів між читачами й записувачами, але дві транзакції, що змінюють **ті самі** дані, усе одно потребують координації. PostgreSQL забезпечує її блокуваннями.

## Блокування рядків

Кожен `UPDATE` і `DELETE` блокує рядки, які змінює, до кінця транзакції. Друга транзакція, що намагається змінити той самий рядок, **чекає**; коли перша фіксується, друга заново перевіряє рядок (на Read Committed) і продовжує.

Рядки можна явно блокувати під час читання:

| Конструкція | Застосування |
|---|---|
| `FOR UPDATE` | «Я збираюся змінити цей рядок»: блокує інші `FOR UPDATE`, `UPDATE` і `DELETE` |
| `FOR NO KEY UPDATE` | Як `FOR UPDATE`, але дозволяє іншим вставляти рядки, що на нього посилаються (це бере звичайний `UPDATE`) |
| `FOR SHARE` | «Нехай ніхто це не змінює, поки я працюю»: блокує записувачів, дозволяє інші `FOR SHARE` |
| `NOWAIT` | Одразу впасти замість очікування |
| `SKIP LOCKED` | Пропустити вже заблоковані рядки |

## Черга завдань із SKIP LOCKED

Кілька обробників беруть завдання з однієї таблиці; кожен має отримати інше завдання, і ніхто не має чекати:

```sql
BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;          -- інші обробники пропускають цей рядок, а не чекають

UPDATE jobs SET status = 'running' WHERE id = $1;
COMMIT;
```

Цей шаблон перетворює PostgreSQL на надійну чергу, і на ньому побудовані бібліотеки на кшталт Graphile Worker, Oban і pg-boss.

## Блокування таблиць

DDL бере блокування на рівні таблиці. `ALTER TABLE` зазвичай бере `ACCESS EXCLUSIVE`, що конфліктує з усім, навіть із `SELECT`. Небезпека — у черзі: якщо довга транзакція читає таблицю, `ALTER` чекає, а кожен новий запит чекає за `ALTER`. Використовуйте `SET lock_timeout = '5s'` у міграціях і повторюйте спробу.

## Взаємоблокування

```text
T1: UPDATE accounts … WHERE id = 1;    -- блокує рядок 1
T2: UPDATE accounts … WHERE id = 2;    -- блокує рядок 2
T1: UPDATE accounts … WHERE id = 2;    -- чекає на T2
T2: UPDATE accounts … WHERE id = 1;    -- чекає на T1: цикл!
```

PostgreSQL виявляє цикл (через `deadlock_timeout`, типово 1 секунду) і скасовує одну з транзакцій з «deadlock detected» (SQLSTATE `40P01`). Застосунок має її повторити. Щоб взаємоблокування траплялися рідко:

- блокуйте рядки в **однаковому порядку**, напр. у переказі завжди спершу менший id рахунку;
- робіть транзакції короткими;
- блокуйте все потрібне одразу (`SELECT … WHERE id IN (1, 2) ORDER BY id FOR UPDATE`).

## Оптимістичне блокування

Песимістичне блокування тримає блокування, поки користувач думає, а це не працює для веб-форми, відкритої десять хвилин. **Оптимістичне** блокування припускає, що конфлікти рідкісні, і виявляє їх під час запису через стовпець версії:

```sql
-- користувач завантажив документ у версії 3
UPDATE documents
SET body = 'new text', version = version + 1
WHERE id = 1 AND version = 3
RETURNING version;
```

- Повернувся один рядок: збереження вдалося, нова версія — 4.
- **Жодного рядка**: хтось зберіг між тим. Покажіть «документ змінив хтось інший», перезавантажте, об'єднайте зміни й спробуйте ще раз.

Перевірка й запис — одна атомарна інструкція, тож два одночасні збереження не можуть обидва вдатися. У HTTP та сама ідея вбудована: заголовок `ETag` і `If-Match` з відповіддю `412 Precondition Failed` у разі конфлікту. ORM теж це підтримують (`@Version` у JPA, `[ConcurrencyCheck]`/row version в Entity Framework).

## Рекомендаційні блокування

`pg_advisory_lock(key)` блокує довільне число, яке щось означає для вашого застосунку, а не для бази: «нічний звіт запускає лише один екземпляр», «клієнта 42 обробляє лише один обробник». `pg_try_advisory_lock` повертає `false` замість очікування, а `pg_advisory_xact_lock` звільняється автоматично наприкінці транзакції.

## Як обрати

| Ситуація | Підхід |
|---|---|
| Збільшити лічильник, зменшити залишок | Один атомарний `UPDATE … SET x = x + 1` (з умовою у `WHERE`) |
| Прочитати-змінити-записати в межах одного запиту | `SELECT … FOR UPDATE` |
| Користувач редагує хвилинами | Оптимістичне блокування з версією |
| Багато обробників, одна черга | `FOR UPDATE SKIP LOCKED` |
| Складні інваріанти між рядками | Ізоляція Serializable з повторами |
