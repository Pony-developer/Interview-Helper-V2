Більшість продакшн-інцидентів із плагінами спричиняє та сама жменька помилок. Інтерв'юери їх обожнюють, бо вони показують, чи запускали ви плагіни під навантаженням.

## Спільний стан

Екземпляр плагіна кешується й повторно використовується, можливо, кількома потоками одночасно.

```csharp
public class BadPlugin : IPlugin
{
    private Entity target;          // спільний для всіх запитів!
    private IOrganizationService service;

    public void Execute(IServiceProvider sp) { /* заповнює поля, потім використовує їх */ }
}
```

Два збереження в ту саму мить перезаписують поля одне одного. Тримайте все, що стосується запиту, у локальних змінних, передавайте параметрами й вважайте клас таким, що не має стану. Статичні кеші можливі, але мають бути потокобезпечними й не містити даних конкретного користувача.

## Нескінченні цикли

PostOperation-плагін на Update `account`, що викликає `service.Update` для того самого акаунта, знову запускає сам себе. Платформа зрештою зупиняє його помилкою нескінченного циклу, змарнувавши час і блокування. Виправлення, від кращого:

1. Задавати значення на **PreOperation** у Target: жодного додаткового Update, жодного нового конвеєра.
2. Використовувати **filtering attributes**, щоб крок спрацьовував лише тоді, коли змінюються стовпці, які він читає, і стежити, щоб він сам їх не записував.
3. Оновлювати лише тоді, коли значення справді змінюється.
4. В крайньому разі перевіряти `context.Depth`. Це грубо: так блокуються й легітимні оновлення, що приходять з іншого плагіна чи flow.

## Забагато роботи в транзакції

Синхронний плагін тримає блокування бази, поки виконується. Кожен повільний виклик у ньому сповільнює кожне збереження цієї таблиці й під навантаженням спричиняє блокування та взаємоблокування (deadlocks).

- Не викликайте повільні зовнішні сервіси синхронно. Використовуйте **асинхронний** крок, **service endpoint** (Azure Service Bus, Event Hubs, webhook) або flow.
- Отримуйте лише потрібні стовпці (`new ColumnSet("name")`, ніколи `new ColumnSet(true)`).
- Використовуйте **образи** замість отримання запису, що саме зберігається.
- Робіть один запит із фільтром замість `Retrieve` у циклі.
- Пам'ятайте про **2-хвилинний** тайм-аут пісочниці: довга пакетна робота не для плагіна.

## Припущення, що в Target є всі стовпці

На Update Target містить лише змінені стовпці. Код на кшталт `target.GetAttributeValue<Money>("creditlimit")` повертає `null`, коли користувач змінив лише телефон, і правило мовчки вважає ліміт нулем. Поєднуйте Target із pre-image, щоб бачити повну картину.

## Виконання не від того користувача

`CreateOrganizationService(null)` працює від імені SYSTEM і обходить безпеку. Іноді це потрібно (записати аудит, якого користувач не може торкатися), але якщо робити так усюди, користувачі змінюватимуть дані, на які не мають прав. Типово використовуйте `context.UserId`, а виклики від SYSTEM робіть свідомо й вузько.

## Проковтнуті винятки

```csharp
try { DoWork(); } catch (Exception) { }   // збереження проходить, а робота зроблена наполовину
```

Або обробіть помилку як слід, або дайте їй зупинити транзакцію через `InvalidPluginExecutionException` зі зрозумілим повідомленням. Тихі збої перетворюються на проблеми якості даних, які знаходять через місяці.

## Зашиті значення

GUID команд, черг чи валют відрізняються між середовищами. Читайте їх за назвою чи альтернативним ключем, зі змінної середовища або з конфігурації кроку, але ніколи з константи.

## Асинхронні плагіни не безкоштовні

Асинхронні кроки проходять через чергу асинхронного сервісу. Тисячі таких кроків (наприклад, під час імпорту даних) затримують усе інше в цій черзі, включно з flow і системними завданнями. Для масових завантажень подумайте про вимкнення необов'язкових кроків або обробку пакетами.

## На співбесіді

- Поясніть, чому плагіни мають бути без стану і що буває інакше.
- Поясніть, як виникає цикл плагінів, і чотири способи його уникнути.
- Перелічіть способи зберегти швидкість синхронних плагінів.
- Поясніть пастку з Target на Update і як її розв'язують образи.
