Скрипти форм працюють усередині великого застосунку, який писали не ви. Добре їх налагоджувати — означає користуватися інструментами браузера, кількома прийомами model-driven застосунків і тестами, що працюють без браузера.

## Інструменти розробника браузера

Натисніть **F12** на формі:

- **Sources**: знайдіть свій веб-ресурс (пошук за іменем, напр. `account.js`), ставте точки зупину, крокуйте, оглядайте `formContext`. Інструкція `debugger;` у коді зупиняє виконання там, коли інструменти відкриті.
- **Console**: помилки ваших обробників і ваші `console.log` під час розробки (приберіть чи огородіть їх перед постачанням).
- **Network**: виклики Web API з URL, кодами статусу й відповідями; фільтруйте за `api/data`.

Мінімізовані бандли важко читати: у збираннях для розробки генеруйте **source maps**, щоб точки зупину працювали у вашому TypeScript.

## Заміна скрипту без розгортання: AutoResponder

Проксі на кшталт **Fiddler** (його AutoResponder) або розширення браузера, що перенаправляє запити, може відповідати на запит `…/WebResources/contoso_/scripts/account.js` **вашим локальним файлом**. Ви редагуєте локально, оновлюєте форму й тестуєте на справжніх даних у спільному середовищі, нічого не завантажуючи й не публікуючи та не впливаючи на інших користувачів. Це найшвидший цикл зворотного зв'язку для клієнтської роботи.

## Вимкніть зайве, щоб ізолювати проблему

Model-driven застосунки приймають **URL-прапорці** для діагностики; наприклад, `&flags=DisableFormHandlers=true` завантажує форму без обробників подій, і так швидко видно, чи проблема в скриптах, чи в самій формі. **Monitor** показує кожен обробник, його бібліотеку й тривалість, а його *form checker* повідомляє про помилки скриптів і повільні обробники.

## Поширені помилки

- `Cannot read properties of null`: поля немає на цій формі або значення порожнє.
- Перевірка, що «іноді» не спрацьовує: асинхронний виклик, на який збереження не чекає.
- Неправильні порівняння: id lookup у дужках і верхньому регістрі, значення choice як числа проти підписів, дати в часовому поясі користувача.
- Обробник ніколи не запускається: неправильне ім'я функції чи простору імен у реєстрації події, не позначено «pass execution context» або бібліотеку не додано до форми.
- Змін не видно: веб-ресурс збережено, але не **опубліковано**, або браузер закешував стару версію.

## Модульні тести з моками

Скрипти з логікою заслуговують на тести. З **Jest** і моком Client API (бібліотека спільноти **xrm-mock** будує фейкові `Xrm` і контекст форми) можна тестувати обробники в Node. Тест виглядає приблизно так (точні назви допоміжних функцій дивіться в README бібліотеки):

```javascript
import { XrmMockGenerator } from "xrm-mock";
import { Contoso } from "../src/account";

beforeEach(() => {
  XrmMockGenerator.initialise();
  XrmMockGenerator.Attribute.createOptionSet("industrycode", 7);
  XrmMockGenerator.Attribute.createString("contoso_procurementcode", "");
});

test("shows the procurement code for public sector", () => {
  Contoso.Account.onLoad(XrmMockGenerator.getEventContext());
  expect(Xrm.Page.getControl("contoso_procurementcode").getVisible()).toBe(true);
});
```

(Мок надає об'єкт сторінки для перевірок; ваш продакшн-код і далі використовує контекст форми.) Мокайте виклики `Xrm.WebApi` через Jest, щоб тестувати асинхронну логіку без сервера. Наскрізні UI-тести з інструментами на кшталт Playwright повільніші й крихкі на model-driven формах; лишайте їх для кількох критичних сценаріїв.

## На співбесіді

- Поясніть, як поставити точку зупину у веб-ресурсі й переглянути його виклики Web API.
- Поясніть, як перенаправлення на кшталт AutoResponder пришвидшує клієнтську розробку.
- Перелічіть поширені причини, чому скрипт форми не запускається чи поводиться неправильно.
- Поясніть, як ви пишете модульні тести для скриптів форм.
