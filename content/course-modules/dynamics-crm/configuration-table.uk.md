Демо-activity в цьому модулі читає налаштування з **конфігураційної таблиці**. Добре спроєктувати таку таблицю важливо, бо багато проєктів приходять саме до цього шаблону.

## Таблиця

Створіть у своєму рішенні власну таблицю:

| Властивість | Значення |
| --- | --- |
| Відображуване ім'я | Configuration |
| Логічне ім'я | `contoso_configuration` |
| Володіння | **Organization** (налаштування належать усім, а не користувачу) |
| Основний стовпець назви | `contoso_key` (Key), один рядок тексту, обов'язковий |

Стовпці:

| Стовпець | Логічне ім'я | Тип | Примітки |
| --- | --- | --- | --- |
| Key | `contoso_key` | Текст (100) | Основна назва, напр. `invoice.prefix` |
| Value | `contoso_value` | Кілька рядків тексту | Налаштування — текстом чи JSON |
| Description | `contoso_description` | Кілька рядків тексту | Для чого воно й хто ним опікується |
| Status | `statecode` | (вбудований) | Неактивні рядки ігноруються |

## Унікальні ключі

Два рядки з однаковим ключем змушують кожного читача вгадувати. Додайте **альтернативний ключ** на `contoso_key`: тоді платформа відхилятиме дублікати, а інтеграції чи скрипти розгортання зможуть робити **upsert** налаштувань за ключем. Читачі все одно мають бути обережними (практика кидає виняток на дублікатах), бо неактивні рядки та старі дані існують.

## Безпека

- Таблиці у власності організації мають лише глибину None або Organization. Дайте **Read** ролям користувачів, чиї workflow і плагіни читають налаштування (або читайте їх у коді від SYSTEM).
- **Create, Write, Delete** дайте лише ролі адміністратора.
- **Не** зберігайте тут секрети: кожен із Read їх побачить. Використовуйте secure configuration кроку або секретні змінні середовища на основі Azure Key Vault.

## Перенесення налаштувань між середовищами

Рядки — це дані, а не компоненти рішення. Варіанти:

- **Configuration Migration tool** (`pac data export` / `pac data import`), із ключем за альтернативним ключем;
- скрипт розгортання, що робить upsert рядків;
- натомість **змінні середовища** — для значень, що відрізняються між середовищами й мають бути частиною ALM.

Поширений поділ: технічні значення для конкретних середовищ — у змінних середовища; списки й правила, якими опікується бізнес, — у конфігураційній таблиці.

## Застосунок для адміністраторів

Додайте таблицю в адміністративний model-driven застосунок із простим поданням (Key, Value, Status) і формою. Увімкніть для таблиці **аудит**, щоб бачити, хто й коли змінив налаштування, — це перше питання, коли щось ламається.

## Читання

З плагіна чи activity шукайте за ключем і статусом:

```csharp
var query = new QueryByAttribute("contoso_configuration") { ColumnSet = new ColumnSet("contoso_value") };
query.AddAttributeValue("contoso_key", key);
query.AddAttributeValue("statecode", 0);   // лише активні
var rows = service.RetrieveMultiple(query).Entities;
```

У плагінах, що виконуються часто, кешуйте результати на кілька хвилин.

## На співбесіді

- Спроєктуйте конфігураційну таблицю: володіння, стовпці, ключі, безпека.
- Поясніть, чому секретам у ній не місце.
- Поясніть, як її рядки потрапляють у тестове й продакшн-середовище.
- Порівняйте конфігураційну таблицю зі змінними середовища.
