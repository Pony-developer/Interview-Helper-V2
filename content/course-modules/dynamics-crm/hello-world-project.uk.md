Час створити перший плагін. Перш ніж писати код, проєкт треба налаштувати так, як очікує платформа, інакше реєстрація впаде з незрозумілими помилками.

## Що потрібно платформі

- **Бібліотека класів** під **.NET Framework 4.6.2**. Не .NET 8 і не .NET Standard: пісочниця завантажує збірки .NET Framework.
- Посилання на збірки SDK через NuGet-пакет **`Microsoft.CrmSdk.CoreAssemblies`** (у ньому `Microsoft.Xrm.Sdk.dll`).
- **Підпис строгим іменем**: збірку підписують файлом ключа (`.snk`).
- Публічні класи, що реалізують `Microsoft.Xrm.Sdk.IPlugin`.

## Швидкий шлях: Power Platform CLI

```text
mkdir Contoso.Plugins
cd Contoso.Plugins
pac plugin init --author Contoso
```

`pac plugin init` створює SDK-style проєкт під `net462`, додає посилання NuGet, генерує ключ підпису й додає клас **`PluginBase`**, що розпаковує контекст і сервіси за вас, а також приклад плагіна. Зберіть його через `dotnet build` або Visual Studio.

## Ручний шлях: Visual Studio

1. **New project → Class Library (.NET Framework)**, фреймворк **.NET Framework 4.6.2**, ім'я `Contoso.Plugins`.
2. **Manage NuGet Packages → Browse → `Microsoft.CrmSdk.CoreAssemblies`**, встановіть останню версію.
3. **Project → Properties → Signing → Sign the assembly → New…**, назвіть ключ `Contoso.Plugins.snk`. Ключ без пароля найпростіший для серверів збирання. Підпис дає збірці строге ім'я; це не секрет безпеки.
4. Видаліть `Class1.cs`, додайте `HelloWorldPlugin.cs`.

## Розумна структура

```text
Contoso.Plugins/
  Contoso.Plugins.csproj
  Contoso.Plugins.snk
  PluginBase.cs                 # спільна інфраструктура: контекст, сервіси, трасування
  Accounts/
    HelloWorldPlugin.cs         # тонкі класи IPlugin
    FollowUpTaskPlugin.cs
  Logic/
    FollowUpTaskService.cs      # бізнес-правила, які можна тестувати без IPlugin
Contoso.Plugins.Tests/          # тести xUnit з фейковим IOrganizationService
```

Зазвичай одна збірка на напрям рішення. Тримайте класи плагінів тонкими, а правила — в окремих класах, тоді техніки тестування з наступного модуля спрацюють.

## Залежності

Пісочниця завантажує лише вашу збірку та збірки самої платформи. Два способи використати іншу бібліотеку:

- **Пакети плагінів**: зберіть NuGet-пакет (`.nupkg`) з вашою збіркою та її залежностями й зареєструйте пакет замість однієї DLL. Проєкти з `pac plugin init` уміють його створювати. Це підтримуваний підхід.
- **ILMerge / ILRepack**, що зливає DLL в одну, ще трапляється в старих проєктах, але Microsoft це **не підтримує**.

Залежностей має бути мало: кожна бібліотека додає розмір, час завантаження й ризики під час оновлень.

## Версії

Версія збірки важлива під час реєстрації: кроки прив'язані до імені збірки, культури, токена публічного ключа та версії **major.minor**. Зміна build чи revision (`1.0.0.1` → `1.0.0.2`) оновлює збірку на місці; зміна major чи minor (`1.0` → `1.1`) вважається новою збіркою, і старі кроки й далі вказують на стару. Більшість команд тримає `1.0.0.x`, а для релізів використовує версії рішень.

## На співбесіді

- Назвіть цільовий фреймворк, NuGet-пакет і поясніть, чому збірку треба підписати.
- Поясніть, що дає `pac plugin init`.
- Поясніть, як сьогодні використати сторонню бібліотеку в плагіні.
- Поясніть, які зміни версії збірки створюють нову збірку під час реєстрації.
