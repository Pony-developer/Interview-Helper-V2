Кожен виклик, який робить плагін, виконується **від імені якогось користувача**, і Dataverse перевіряє привілеї цього користувача. Свідомий вибір цього користувача називають **імперсонацією**. Помилитеся — і плагін або падатиме для звичайних користувачів, або тихо дозволить їм змінювати дані, на які вони не мають прав.

## Користувачі в контексті

- **`context.InitiatingUserId`**: людина (чи application user), що насправді почала операцію. Уздовж ланцюжка він не змінюється.
- **`context.UserId`**: користувач, від імені якого виконується крок. Типово це той, хто викликав, але реєстрація кроку може це змінити.

## Run in User's Context

Під час реєстрації кроку параметр **Run in User's Context** визначає `context.UserId`:

- **Calling User** (типово): користувач, що запустив повідомлення.
- **Конкретний користувач**, наприклад окремий користувач «Integration» чи «Plug-in service» з вузькою роллю безпеки.

Сам по собі параметр нічого не змінює; він вирішує, що буде в `context.UserId`. Далі це використовує ваш код:

```csharp
var factory = (IOrganizationServiceFactory)serviceProvider.GetService(typeof(IOrganizationServiceFactory));

IOrganizationService asUser   = factory.CreateOrganizationService(context.UserId);           // користувач кроку
IOrganizationService asCaller = factory.CreateOrganizationService(context.InitiatingUserId); // завжди справжня людина
IOrganizationService asSystem = factory.CreateOrganizationService(null);                     // SYSTEM, без перевірки привілеїв
IOrganizationService asOther  = factory.CreateOrganizationService(serviceUserId);             // будь-який обраний вами id
```

## Коли що використовувати

| Потреба | Сервіс |
| --- | --- |
| Звичайна робота, що має поважати права користувача | `context.UserId` |
| Записати те, чого користувач не може торкатися: нотатку аудиту, лічильник, запис у закритій таблиці | `null` (SYSTEM), вузько |
| Діяти як сервісний обліковий запис із визначеною роллю | конкретний id користувача (з конфігурації) |
| Зафіксувати, хто насправді це зробив | читати `InitiatingUserId`, хоч який сервіс ви використовуєте |

Записи, створені сервісом, належать користувачу цього сервісу, якщо ви не задали `ownerid`, а `createdby` показує цього користувача. Нотатки, створені від SYSTEM, мають власником SYSTEM, і саме тому звичайні користувачі не можуть їх підробити.

## Ризики SYSTEM

Робота від SYSTEM пропускає всі перевірки безпеки, включно з бізнес-підрозділами та безпекою стовпців. Якщо ви прочитали дані як SYSTEM і скопіювали їх у запис, який бачить користувач, — ви щойно допустили витік. Використовуйте SYSTEM для конкретних записів, тримайте цей шлях коду коротким і ніколи не дозволяйте введенню користувача без перевірки обирати, який запис зачепить SYSTEM.

## Імперсонація ззовні

Зовнішній код теж може діяти від імені іншого користувача:

- **SDK**: задайте `serviceClient.CallerId = userId`.
- **Web API**: надішліть заголовок `CallerObjectId: <object id у Microsoft Entra>` (або старіший `MSCRMCallerID: <systemuserid>`).

Обліковий запис, що викликає, має мати привілей **Act on behalf of another user** (`prvActOnBehalfOfAnotherUser`). Тоді запис показує користувача, від імені якого діяли, у `createdby`, а справжнього викликача — у **`createdonbehalfby`**, тож аудит лишається чесним.

## На співбесіді

- Поясніть різницю між `UserId` та `InitiatingUserId`.
- Поясніть, що змінює «Run in User's Context».
- Наведіть приклад, коли плагін має писати від SYSTEM, і ризик робити так усюди.
- Поясніть, як інтеграція може створювати записи від імені користувача і що покаже аудит.
