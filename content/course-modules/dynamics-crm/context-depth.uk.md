`context.Depth` відповідає на одне питання: **на якій глибині операцій зараз це виконання?** Це інструмент платформи, щоб помічати ланцюжки плагінів, які запускають одне одного, і часта тема на співбесідах, бо ним так часто зловживають.

## Як зростає глибина

- Користувач зберігає акаунт: Update виконується на **глибині 1**.
- PostOperation-плагін на цьому Update викликає `service.Update` для контактів акаунта: ці Update виконуються на **глибині 2**.
- Плагін на Update контакту створює завдання: цей Create виконується на **глибині 3**.

Кожен виклик, який плагін чи workflow робить через сервіс організації, починає нову операцію на рівень глибше. Асинхронні кроки та workflow несуть глибину операції, що поставила їх у чергу.

## Ліміт

Якщо ланцюжок іде глибше за **максимальну глибину** (типово 8, рахуючи в часовому вікні близько години), платформа зупиняє його помилкою про виявлений нескінченний цикл. Ліміт захищає систему; досягти його — означає мати проблему дизайну, а не налаштування, яке треба збільшити.

## Класичний цикл

```csharp
// PostOperation, Update акаунта, без filtering attributes
var change = new Entity("account", context.PrimaryEntityId);
change["contoso_lastreview"] = DateTime.UtcNow;
service.Update(change);   // знову запускає цей самий крок на глибині 2, 3, 4...
```

## Виходи, від найкращого

1. **Задати значення на PreOperation** у Target замість виклику Update. Жодної нової операції, жодного циклу, жодного зайвого звернення до бази.
2. **Filtering attributes**: реєструвати крок лише для важливих стовпців (`creditlimit`, `telephone1`). Якщо крок пише лише інші стовпці, його власне оновлення його не запускає.
3. **Писати лише тоді, коли щось змінюється**: порівняти з pre-image і пропустити оновлення, якщо значення вже правильне.
4. **Перевірка глибини**, в крайньому разі:

```csharp
if (context.Depth > 1)
{
    tracing.Trace("Skipped at depth {0}", context.Depth);
    return;
}
```

## Чому перевірка глибини груба

`Depth > 1` не означає «викликано мною самим». Це означає «викликано *будь-чим*»: іншим плагіном, workflow, оновленням із flow, ExecuteMultiple з Custom API. Правило, що має виконуватися завжди, як-от перевірка даних, **не** повинно пропускатися лише тому, що зміна прийшла від автоматизації; саме так погані дані потрапляють через інтеграції. Використовуйте перевірку глибини для побічних ефектів, які мають сенс лише для прямих дій користувача, і пишіть про це в коментарі.

Точніша альтернатива — дивитися на **`context.ParentContext`**: пройти вгору ланцюжком і перевірити, чи вже не виконується те саме повідомлення для того самого запису (або ваш власний плагін).

## Глибина в асинхронній роботі

Асинхронні плагіни та фонові workflow виконуються пізніше, але несуть глибину, тож ланцюжок може зациклитися й через асинхронну чергу. Такі цикли помітити повільніше: системні завдання накопичуються й падають із тією самою помилкою нескінченного циклу.

## На співбесіді

- Поясніть, що збільшує `context.Depth`.
- Поясніть, що відбувається, коли досягнуто максимальної глибини.
- Наведіть чотири способи запобігти циклу й поясніть, чому `Depth > 1` — останній вибір.
- Поясніть, чому плагіни перевірки не повинні пропускати роботу через глибину.
