Dynamics рідко живе сам по собі: ERP-системи, вебсайти, сховища даних і бізнес-застосунки обмінюються з ним даними. На інтеграції йде велика частка часу розробника Dynamics.

## Автентифікація

Сервіси під'єднуються як **application user**:

1. Зареєструйте застосунок у **Microsoft Entra ID** із секретом клієнта або, краще, сертифікатом (чи керованою ідентичністю, якщо код працює в Azure).
2. Додайте застосунок як application user у середовище (Power Platform admin center).
3. Дайте йому **власну роль безпеки з мінімальними привілеями**, які йому потрібні. Ніколи не System Administrator.

Сервіс отримує OAuth-токен для `https://<org>.crm.dynamics.com/.default` (це робить MSAL, `ServiceClient` його обгортає) і викликає Web API або SDK.

## Вхідні: інші системи пишуть у Dataverse

- Використовуйте **Web API** з будь-якої мови або `ServiceClient` з .NET.
- Звертайтеся до записів за **альтернативними ключами** й використовуйте **Upsert**, щоб повторне надсилання того самого повідомлення нічого не ламало.
- Для обсягів використовуйте **масові повідомлення**: `CreateMultiple`, `UpdateMultiple`, `UpsertMultiple` або пакети `ExecuteMultiple` до 1000 запитів. `ExecuteTransaction` виконує до 1000 запитів в одній транзакції, коли вони мають пройти разом.
- Azure Data Factory, dataflows і Azure Synapse Link покривають масштабне перенесення даних без власного коду.

## Вихідні: Dataverse сповіщає інші системи

- **Service endpoints**: зареєструйте чергу чи топік Azure Service Bus, Event Hub або **webhook** у Plug-in Registration Tool, потім зареєструйте на ньому асинхронні кроки. Платформа надсилає контекст виконання (`RemoteExecutionContext`) як повідомлення. Azure Function забирає його й працює з іншою системою, з повторами й dead-letter-чергою.
- Flow у **Power Automate** з тригером Dataverse.
- **Synapse Link / Fabric** для аналітичних копій даних.

Уникайте синхронних викликів зовнішніх сервісів із плагінів: тоді кожне збереження чекає на іншу систему й падає разом із нею.

## Ліміти захисту сервісу

Dataverse захищає себе **лімітами захисту API** (service protection API limits), які рахуються для кожного користувача (включно з application users) і кожного вебсервера у ковзному 5-хвилинному вікні:

- кількість запитів (6000),
- сумарний час виконання (20 хвилин),
- одночасні запити (52).

Значення можуть змінюватися, тож звіряйтеся з документацією. Коли ліміт перевищено, Web API повертає **HTTP 429 Too Many Requests** із заголовком **`Retry-After`**, що каже, скільки секунд чекати. SDK кидає помилку з тією самою інформацією, а `ServiceClient` частину з них повторює автоматично.

Що робить вихований клієнт:

- На 429 (і на 503 Service Unavailable) чекає `Retry-After` і повторює. Якщо заголовка немає, відступає експоненційно: 1, 2, 4, 8 секунд…
- Здається після обмеженої кількості повторів і повідомляє про збій.
- **Не** повторює 400 Bad Request чи 403 Forbidden: помилковий сам запит, і повтор не допоможе.
- Використовує помірну кількість паралельних потоків. Почніть із малого й збільшуйте, доки не побачите 429; заголовок відповіді `x-ms-dop-hint` підказує ступінь паралелізму.
- Розподіляє великі навантаження між кількома application users лише в межах ліцензійних правил, а не щоб обійти ліміти.

Є також **ліміти за правом користування** (entitlement limits): денні квоти запитів, прив'язані до ліцензій. Їх відстежують для звітності, а не блокують кожен виклик, але важкі інтеграції варто планувати з огляду на них.

## Ідемпотентність і порядок

Повідомлення можуть прийти двічі чи не в тому порядку (Service Bus доставляє *щонайменше один раз*). Проєктуйте обробники так, щоб повторна обробка повідомлення мала той самий ефект, що й одна: upsert за ключем, порівняння версії чи часу зміни, збереження id оброблених повідомлень.

## На співбесіді

- Поясніть, як сервіс автентифікується як application user і чому йому потрібна роль із мінімальними привілеями.
- Опишіть варіанти вхідних і вихідних інтеграцій, включно із service endpoints.
- Поясніть ліміти захисту сервісу, HTTP 429 і `Retry-After` та як клієнт має повторювати запити.
- Поясніть, чому обробники інтеграцій мають бути ідемпотентними.
