**Класичні workflow** (їх ще називають процесами) — це оригінальна no-code автоматизація Dynamics CRM: дизайнер, у якому адміністратори будують кроки на кшталт «якщо статус Won, створити завдання й надіслати лист». Коли потрібного кроку немає, розробники пишуть **власну workflow activity** (custom workflow activity): клас на C#, що з'являється в дизайнері як новий крок.

## Де класичні workflow сьогодні

- Microsoft радить для нової автоматизації **flow у Power Automate** і публікує настанови з міграції класичних **фонових** workflow у flow.
- **Real-time** (синхронні) workflow досі широко використовують, бо flow не можуть працювати всередині транзакції.
- Тисячі наявних систем досі працюють на класичних workflow із власними activities. Підтримувати, налагоджувати й мігрувати їх — щоденна робота з Dynamics, і про них питають на співбесідах.

Тож вивчайте власні workflow activities, щоб **підтримувати** наявне, і знайте сучасні альтернативи для **нової** роботи.

## Що таке власна activity

Клас, похідний від **`CodeActivity`** (Windows Workflow Foundation), з:

- **вхідними аргументами**, які дизайнер workflow дає заповнити адміністраторам: фіксованими значеннями чи значеннями із запису («Account: Credit Limit»);
- **вихідними аргументами**, які можуть використати наступні кроки («якщо Found дорівнює Yes…»);
- методом **`Execute`**, що виконує роботу з доступом до контексту workflow і сервісу організації.

```csharp
public class GetConfigurationValue : CodeActivity
{
    [RequiredArgument, Input("Key")]
    public InArgument<string> Key { get; set; }

    [Output("Value")]
    public OutArgument<string> Value { get; set; }

    protected override void Execute(CodeActivityContext executionContext) { /* … */ }
}
```

## Навіщо її створювати

- **Повторне використання**: одна activity («Отримати значення конфігурації», «Порахувати робочі дні», «Додати в чергу») у десятках workflow.
- **Сила адміністраторам**: розробники роблять невеликі, добре протестовані блоки, а адміністратори складають їх без розгортання.
- **Те, чого не вміє дизайнер**: цикли по пов'язаних записах, складні обчислення, виклики сервісів, робота з рядками й датами.

## Real-time проти фонових

Та сама activity може працювати в обох:

- **Real-time workflow** виконуються синхронно, всередині транзакції, як синхронний плагін. Виняток скасовує збереження й показує повідомлення.
- **Фонові workflow** виконуються через асинхронний сервіс; збої видно в системних завданнях.

## Сучасні відповідники

| Класичне | Сучасне |
| --- | --- |
| Фоновий workflow | Хмарний flow у Power Automate |
| Власна workflow activity, яку використовують flow | **Custom API** (викликається з flow, застосунків, коду) |
| Real-time workflow з власною логікою | Синхронний плагін або real-time workflow, поки він підтримується |

Власну workflow activity **не можна викликати з хмарного flow**. Якщо логіку треба ділити з flow, винесіть її в Custom API на основі плагіна, а тонку activity лишіть лише для старих workflow, якщо вони її потребують.

## Що будує цей модуль

**Конфігураційну таблицю**, яку підтримують адміністратори, і activity «Отримати значення конфігурації», якою workflow її читають; далі — розгортання, налагодження й версіонування, а також порівняння плагінів і workflow.
