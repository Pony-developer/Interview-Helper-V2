**Керування життєвим циклом застосунку (ALM)** — це те, як зміни безпечно й повторювано проходять шлях від ідеї до продакшну. У Dataverse це середовища, контроль версій і автоматизовані конвеєри навколо рішень.

## Середовища

Типове налаштування:

- **Розробка**: окреме для кожного розробника чи команди, тут редагують некеровані рішення. Окремі середовища не дають людям перезаписувати зміни форм одне одного.
- **Збирання / перевірка**: необов'язкове, конвеєр імпортує туди зібране рішення й запускає перевірки.
- **Тестування / UAT**: лише керовані рішення, якомога ближче до продакшну за даними й конфігурацією.
- **Продакшн**: лише кероване, жодних прямих змін. **Managed Environments** додають керування: обмеження спільного доступу, обов'язкові перевірки рішень, вбудовані конвеєри.

## Контроль версій — джерело правди

`.zip` рішення — це бінарний пакет, який важко переглядати. Розпакуйте його в читабельні файли:

```text
pac auth create --environment https://contoso-dev.crm4.dynamics.com
pac solution clone --name ContosoSales          # перший раз: створює локальний проєкт
pac solution sync                               # далі: підтягує зміни із середовища
pac solution pack --zipfile out/ContosoSales.zip --packagetype Both
```

Кожна таблиця, форма й подання стає окремим XML-файлом, тож pull request показує, що саме змінилося. Код плагінів і PCF живе в тому самому репозиторії, а збирання компілює його в рішення.

## Конвеєри

Поширені варіанти:

- **Azure DevOps** з Power Platform Build Tools.
- **GitHub Actions** для Power Platform.
- **Power Platform Pipelines**: вбудовані конвеєри, які мейкери запускають без написання YAML.

Типовий конвеєр:

1. Розробники комітять розпаковане рішення (`pac solution sync`) разом із кодом плагінів і PCF.
2. **Збирання**: компіляція плагінів і PCF-контролів, пакування **керованого** рішення, запуск **solution checker** (статичний аналіз плагінів, скриптів і налаштувань).
3. **Розгортання в тестове середовище**: імпорт як upgrade з **файлом налаштувань розгортання** (deployment settings), що задає значення змінних середовища й посилання на з'єднання для цього середовища.
4. Тести, погодження й розгортання **того самого артефакту** в продакшн.

```text
pac solution import --path out/ContosoSales_managed.zip --settings-file settings/test.json --stage-and-upgrade
```

## Перенесення даних

Рішення переносять метадані, а не рядки. Довідкові дані (каталог товарів, конфігураційні таблиці, черги) переносять **Configuration Migration tool** (`pac data export` / `pac data import`), пакетом для **Package Deployer** або інтеграцією. Давайте довідковим рядкам стабільні GUID або альтернативні ключі, щоб імпорт можна було безпечно повторювати.

## Практичні правила

- Розділіть роботу на кілька рішень за напрямами (базова модель даних, функції продажів, інтеграції) з чіткими залежностями, а не одне величезне рішення чи десятки дрібних.
- Збільшуйте версію з кожним збиранням, щоб у кожному середовищі було видно, що встановлено.
- Ніколи не виправляйте щось просто в тестовому чи продакшн-середовищі; виправляйте в розробці й розгортайте знову.
- Тримайте секрети поза рішеннями: використовуйте *секретні* змінні середовища на основі Azure Key Vault.

## На співбесіді

- Опишіть стратегію середовищ і поясніть, чому продакшн отримує лише керовані рішення.
- Поясніть, як ви зберігаєте рішення в системі контролю версій і що роблять `pac solution clone`, `sync` і `pack`.
- Пройдіться конвеєром CI/CD і поясніть, де в ньому solution checker і налаштування розгортання.
- Поясніть, як довідкові дані переходять між середовищами.
