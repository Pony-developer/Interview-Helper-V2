Щоб писати добрі плагіни, потрібно уявляти, що відбувається між натисканням **Save** і появою рядка в базі даних.

## Шари

```text
 Клієнти            model-driven застосунки · мобільний · Outlook · Power Automate · інтеграції
                                      │  HTTPS (OAuth)
 Веб-сервіси        Web API (OData v4)  ·  Organization service (його використовує .NET SDK)
                                      │
 Платформа          перевірки безпеки · конвеєр виконання подій
                    (плагіни, бізнес-правила, real-time workflows) · кеш метаданих
                                      │
 Дані               Azure SQL (рядки) · сховище файлів і зображень · пошуковий індекс
 ─────────────────────────────────────────────────────────────────────────────
 Фон                асинхронний сервіс: асинхронні плагіни, workflows, системні завдання
 Пісочниця          ізольовані процеси, що виконують код плагінів
```

**Клієнти** ніколи не торкаються бази даних. Кожен клієнт, включно з формами самого застосунку, працює через **веб-сервіси**. Тому серверна логіка захищає дані від будь-якого джерела: чорного ходу немає.

**Шар платформи** обробляє кожен запит: перевіряє привілеї того, хто викликає, завантажує метадані (які стовпці має таблиця, їхні типи, зареєстровані кроки) і запускає **конвеєр виконання подій**, у який підключаються ваші плагіни. Про конвеєр — далі в цьому модулі.

**Шар даних** — це Azure SQL для рядків таблиць, сховище для файлів і зображень та пошуковий індекс. Ви ніколи не пишете SQL проти нього напряму; платформа генерує запити з QueryExpression, FetchXML і запитів Web API та додає фільтри безпеки.

## Синхронна й асинхронна робота

- **Синхронна** логіка виконується всередині запиту, поки користувач чекає: синхронні плагіни, real-time workflows, бізнес-правила.
- **Асинхронна** робота стає в чергу як **системне завдання** (system job), і її обробляє **асинхронний сервіс**: асинхронні плагіни, фонові workflows, масові видалення, імпорти. Flow працюють у Power Automate — окремому сервісі, що реагує на події Dataverse.

## Пісочниця

У Dynamics 365 online плагіни виконуються в **пісочниці** (sandbox): ізольованих робочих процесах, відокремлених від платформи та інших клієнтів. Пісочниця:

- не дає плагінам доступу до файлової системи, реєстру чи журналу подій;
- дозволяє вихідні HTTP/HTTPS-виклики лише за іменами хостів (не за IP-адресами);
- зупиняє будь-яке окреме виконання через **2 хвилини**;
- завантажує вашу збірку з бази даних, куди її поклала реєстрація.

Локальні (on-premises) інсталяції можуть реєструвати плагіни й поза пісочницею («isolation mode: none»), тому старіший код іноді робить речі, які online не працюють.

## Online і on-premises

| | Online (Dataverse) | On-premises (v9) |
| --- | --- | --- |
| Хостинг | Microsoft, в Azure, мультитенантно | Ваші сервери: front-end, back-end і deployment-ролі |
| Оновлення | Безперервні, дві хвилі релізів на рік | Ви встановлюєте оновлення самі |
| Плагіни | Лише пісочниця | Пісочниця або повна довіра |
| Автентифікація | Microsoft Entra ID (OAuth) | Active Directory, claims-based / IFD |
| Доступ до бази | Немає | Можливий, але запис не підтримується |

Майже всі нові проєкти — online; знання відмінностей on-premises допомагає, коли успадковуєте стару систему або мігруєте її.

## Чому це важливо для плагінів

- Ваш код виконується **посередині** запиту: повільний код сповільнює кожне збереження.
- Він працює в **спільному** процесі й може викликатися **одночасно**: тримайте його без стану.
- Синхронний код — частина **транзакції**: виняток відкочує збереження.
- Він виконується **для кожного клієнта**, включно з імпортами та інтеграціями, тож має обробляти дані, яких ви не очікували з форми.

## На співбесіді

- Намалюйте шари від клієнта до бази й покажіть, де виконуються плагіни.
- Поясніть, чому жоден клієнт не може обійти серверну логіку.
- Поясніть, що робить асинхронний сервіс.
- Перелічіть обмеження пісочниці та відмінності між online і on-premises.
