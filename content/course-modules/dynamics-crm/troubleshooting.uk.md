«У dev усе працювало» — з цього починається більшість продакшн-інцидентів. Розробник, який швидко з'ясовує, чому впав плагін, повільно зберігається форма чи зупинилася інтеграція, дуже цінний, і на співбесіді питають про конкретні інструменти, а не «я б налагодив».

## Читайте помилку уважно

Помилка Dataverse має **код**, **повідомлення** і, у файлі журналу, стек викликів. Кілька кодів трапляються постійно:

| Код | Значення |
| --- | --- |
| `0x80040265` | Плагін кинув `InvalidPluginExecutionException`: бізнес-помилка, яку ви навмисно підняли |
| `0x80040220` | Користувачу бракує привілею (повідомлення його називає, наприклад `prvReadAccount`) |
| `0x80040217` | Запис не існує (видалений, хибний id чи хибна таблиця) |
| `0x80072321`, `0x80072322`, `0x80072326` | Спрацювали ліміти захисту сервісу; чекайте `Retry-After` |
| «Generic SQL error» | Часто тайм-аут або взаємне блокування в базі; шукайте довгі транзакції й конкуренцію за блокування |

Повідомлення неочікуваного винятку в плагіні зазвичай приховує справжню причину. Тому кожен плагін має **перехопити, записати в трасування й кинути далі** зрозуміле повідомлення.

## Трасування

`ITracingService.Trace()` записує рядки, що зберігаються разом із виконанням:

- При помилці трасування показується у файлі журналу діалогу помилки й повертається викликачу.
- Коли налаштування середовища **Enable logging to plug-in trace log** має значення *Exception* або *All*, кожне виконання записує рядок у таблицю **Plug-in Trace Log** (`plugintracelog`) з текстом трасування, повідомленням, таблицею, глибиною, тривалістю та винятком. *All* — для діагностики; поверніть назад, бо рядки займають ємність журналів (старі видаляє системне завдання).

Трасуйте рішення, а не лише «зайшли в метод»: id, з якими працюєте, обрану гілку, значення, які порівнювали.

## Телеметрія в Application Insights

Для продакшну підключіть середовище до **Application Insights** (експорт даних у Power Platform admin center). Воно записує виконання плагінів, виклики API й завантаження форм із тривалістю та збоями, тож їх можна будувати на графіках, налаштовувати сповіщення й запитувати мовою KQL. Усередині плагіна сервіс `ILogger` (`Microsoft.Xrm.Sdk.PluginTelemetry.ILogger`) пише ваші власні журнали й метрики туди ж.

## Налагодження плагінів

Підключити налагоджувач до хмарного sandbox неможливо. Натомість:

1. Встановіть **Plug-in Profiler** з Plug-in Registration Tool і почніть профілювання кроку.
2. Відтворіть проблему. Профайлер записує контекст виконання, разом із target та образами, як запис профілю.
3. У Plug-in Registration Tool **відтворіть** (replay) профіль на локальній збірці з підключеною Visual Studio й пройдіть код покроково на реальних даних.

Модульні тести з фейковим контекстом (як в уроці про тестовані плагіни) лишаються найдешевшим способом відтворити помилку, коли вхідні дані вже відомі.

## Типові проблеми й де шукати

| Симптом | Куди дивитися |
| --- | --- |
| Плагін падає приблизно через 2 хвилини | Ліміт часу sandbox: повільний зовнішній виклик чи величезний цикл; винесіть роботу з транзакції |
| Помилки «infinite loop» або глибини | Плагін чи потік оновлює запис, що його запускає; filtering attributes, `context.Depth`, порівняння перед оновленням |
| Щось «не відбулося» | Системні завдання (асинхронні плагіни, workflows), історія запусків потоку, журнал трасування |
| Форма повільна | Monitor (у maker portal, *Monitor* для застосунку): події завантаження форми, мережеві виклики, час скриптів |
| Користувачі отримують «access denied» | Привілей у повідомленні, їхні ролі й бізнес-підрозділ, власник запису та надання доступу |
| Інтеграція зупинилася | Service endpoint і dead-letter черга Service Bus, журнали Azure Function, прострочені секрети реєстрації застосунку |

## Метод, що працює

1. Відтворіть, бажано в непродакшн-середовищі з тими самими даними.
2. Прочитайте повну помилку й трасування, а не лише перший рядок.
3. Звузьте, який компонент виконувався: перелічіть кроки, зареєстровані на цю таблицю й повідомлення, з їхніми стадіями та порядком, а також причетні потоки й бізнес-правила.
4. Виправляйте з тестом, що падає до виправлення.

## На співбесіді

- Поясніть, як працює трасування і звідки береться журнал трасування плагінів.
- Опишіть, як налагодити плагін через профайлер і replay.
- Назвіть типові коди помилок і що вони означають.
- Скажіть, що ви перевіряєте, коли асинхронний процес «не відбувся».
