Тип стовпця визначає, як зберігається значення, як SDK і Web API передають його вашому коду і що платформа може обчислити за вас. Більшість помилок у даних на проєктах Dynamics пов'язані з кількома типами: choice, дати, валюта та обчислювані стовпці.

## Стовпці choice

**Choice** (у SDK — *option set*) зберігає **ціле число**, а не мітку. Власні варіанти отримують значення від префікса значень видавця: видавець із префіксом `10000` створює `100000000`, `100000001` і так далі.

```csharp
account["new_tier"] = new OptionSetValue(100000001);          // запис
var tier = account.GetAttributeValue<OptionSetValue>("new_tier")?.Value;  // читання
```

Web API теж повертає число; мітки отримують через `Prefer: odata.include-annotations="OData.Community.Display.V1.FormattedValue"`.

- **Глобальний** choice спільний для багатьох стовпців (той самий список «Регіон» на account і lead); **локальний** належить одному стовпцю.
- Мітки перекладаються, і їх можна змінювати будь-коли. **Значення не можна змінювати ніколи**: вони є в даних, коді, потоках і звітах. Ніколи не видаляйте варіант, щоб додати його знову з тією самою міткою.
- **Choices** (множинний вибір) зберігають кілька значень (`OptionSetValueCollection`). Їх важче фільтрувати, групувати й використовувати у звітах, тож беріть їх лише для простих тегів.
- **Yes/No** — це choice із двох варіантів, що зберігається як boolean.

## Стан і причина стану

Кожна таблиця має `statecode` (Active / Inactive; для угоди Open / Won / Lost) і `statuscode` — **причину стану** (status reason). Кожна причина належить рівно одному стану, тому їх задають разом:

```csharp
var close = new Entity("new_project", id);
close["statecode"] = new OptionSetValue(1);       // Inactive
close["statuscode"] = new OptionSetValue(2);      // Completed (причина стану Inactive)
service.Update(close);
```

Деякі таблиці мають власні повідомлення: угоди закривають через `WinOpportunityRequest` і `LoseOpportunityRequest`, звернення — через `CloseIncidentRequest`. **Переходи** причин стану можуть обмежувати, яка причина може йти після якої.

## Дата й час

Dataverse зберігає дати в **UTC**. **Поведінка** (behaviour) стовпця визначає, що бачать користувачі й код:

| Поведінка | Зберігається | Показується | Для чого |
| --- | --- | --- | --- |
| User local | UTC | У часовому поясі кожного користувача | Зустрічі, дедлайни, позначки часу |
| Date only | Дата без часу | Як введено, без перерахунку | Дні народження, дати початку договорів |
| Time zone independent | Як введено | Як введено, без перерахунку | Заселення в готель о 14:00 за місцевим часом |

Класична помилка: день народження, збережений як *User local* опівночі за Києвом, у користувача в Нью-Йорку показується попереднім днем. SDK повертає значення *User local* в UTC (`DateTimeKind.Utc`); перерахунок у часовий пояс користувача — завдання клієнта. Стовпець *User local* можна один раз змінити на іншу поведінку, але наявні значення не перераховуються автоматично (для цього є `ConvertDateAndTimeBehaviorRequest`).

## Валюта

Стовпець валюти зберігається як `Money` у **валюті транзакції** запису (`transactioncurrencyid`). Dataverse додає двійника в **базовій валюті** організації:

```text
estimatedvalue_base = estimatedvalue / exchangerate
```

`exchangerate` копіюється в запис, коли його створюють або змінюють його валюту чи грошові значення. Курс **не живий**: оновлення курсу в записі валюти не переоцінює старі записи, доки їх не збережуть знову. Звіти, що підсумовують суми в різних валютах, мають використовувати стовпці `_base`.

## Lookup

Lookup у SDK — це `EntityReference`: логічне ім'я таблиці плюс GUID. Web API читає його як `_parentcustomerid_value` і записує через прив'язку:

```json
{ "parentcustomerid_account@odata.bind": "/accounts(00000000-0000-0000-0000-000000000001)" }
```

## Стовпці, які обчислює платформа

- **Calculated** (обчислювані): формула над стовпцями рядка та його батьків N:1, обчислюється **під час читання запису**, тож значення завжди актуальне.
- **Formula**: наступник calculated-стовпців на Power Fx, теж обчислюється під час читання.
- **Rollup**: агрегат (`SUM`, `COUNT`, `MIN`, `MAX`, `AVG`) над **дочірніми записами** зв'язку 1:N з необов'язковими фільтрами («сума відкритих угод»). Їх обчислює **асинхронно** системне завдання (за замовчуванням щогодини після першого масового обчислення), тож плагін, який щойно створив дочірній запис, не прочитає нову суму в тій самій транзакції. Користувач може перерахувати rollup на формі; код викликає `CalculateRollupFieldRequest`. Кожен rollup має супутні стовпці `<name>_date` (час останнього обчислення) і `<name>_state`. Їхня кількість обмежена на таблицю й на середовище.
- **Autonumber**: рядок за форматом на кшталт `INV-{SEQNUM:5}-{DATETIMEUTC:yyyyMMdd}-{RANDSTRING:3}`. Послідовність гарантовано унікальна, але може мати пропуски.

Коли значення має бути точним у момент транзакції (наприклад, сума рахунку, яку перевіряє плагін), обчислюйте його в плагіні, а не покладайтеся на rollup.

## Стовпці file та image

Стовпці **File** та **Image** зберігають двійковий вміст у файловому сховищі (на базі Azure Blob Storage), а не в базі даних. Вони мають максимальний розмір, великі файли завантажують і вивантажують частинами (`InitializeFileBlocksUpload`, `UploadBlock`, `CommitFileBlocksUpload`), і вони враховуються у **файлову ємність**. Стовпець image може бути основним зображенням таблиці з автоматичною мініатюрою.

## На співбесіді

- Поясніть, чому choice зберігається як ціле число і чому його значення не можна змінювати.
- Опишіть три поведінки дат і помилку «день народження на день раніше».
- Поясніть валютні стовпці `_base` і чому курс не живий.
- Порівняйте calculated, formula та rollup стовпці й поясніть, чому rollup не транзакційні.
