**Покриття коду** відповідає на питання «яку частину мого коду виконали тести?». Інструмент спостерігає за програмою під час виконання тестів, а потім повідомляє, які рядки, гілки й методи були досягнуті, а які — ніколи.

## Як читати число покриття

```csharp
static string Describe(int n)
{
    if (n < 0)
    {
        return "negative";     // рядок A
    }
    if (n == 0)
    {
        return "zero";         // рядок B
    }
    return "positive";         // рядок C
}
```

З єдиним тестом `Describe(5)` рядки **A** та **B** не виконуються ніколи. Покриття рядків — близько 60%, а звіт показує їх червоним. Додайте `Describe(-1)` та `Describe(0)`, і виконаються всі рядки.

Червоні рядки розповідають, **що точно не протестовано**. Це найкорисніше, що робить звіт про покриття.

## Види покриття

| Вид | Що рахує |
| --- | --- |
| **Рядків** (інструкцій) | рядки коду, що виконалися |
| **Гілок** | результати умов: і `true`, і `false` кожного `if` |
| **Методів** | методи, викликані принаймні раз |

Покриття **гілок** суворіше. Розгляньте:

```csharp
static int Abs(int n)
{
    if (n < 0) n = -n;
    return n;
}
```

Тест із `Abs(-5)` виконує **кожен рядок**: 100% покриття рядків. Але випадок, коли умова хибна (`n >= 0`), ніколи не виконувався, тож покриття гілок лише 50%. Помилка в цьому випадку лишилася б непоміченою.

## Як отримати числа в .NET

Шаблон xUnit містить **Coverlet**. Ця команда збирає дані:

```text
dotnet test --collect:"XPlat Code Coverage"
```

Вона записує XML-файл у теку `TestResults`. Інструменти на кшталт **ReportGenerator** перетворюють його на зрозумілий HTML-звіт, а Visual Studio (Enterprise) і Rider можуть показувати покриті рядки в редакторі.

## Покриття — не якість

100% покриття означає, що кожен рядок **виконався**. Це не означає, що щось було **перевірено**:

```csharp
[Fact]
public void Add_Runs()
{
    Calculator.Add(2, 3);     // жодної перевірки: рядок покрито, але нічого не верифіковано
}
```

Тест проходить, покриття 100%, а `Add` може повертати що завгодно. Покриття може довести, що код **не** протестовано, але не може довести, що він **протестований**.

Тому мета на кшталт «80% покриття» сама по собі погана. Коли число стає ціллю, люди пишуть тести, що піднімають число, а не тести, що знаходять помилки.

## Розумний спосіб користування

- Дивіться на **непокритий** код, а не на відсоток. Чи це важливий код, як-от логіка з рішеннями, обчислення й обробка помилок? Протестуйте його.
- Не женіться за 100%. Прості геттери властивостей, згенерований код і звичайний `Main` цих зусиль не варті.
- Стежте за **тенденцією**: різке падіння після зміни — добре питання для код-рев'ю.
- Зосередьтеся на покритті **гілок** важливої логіки.

## Мутаційне тестування: чи помічають тести зміни?

Чесніше питання — «якби код був хибним, чи провалився б якийсь тест?». **Мутаційне тестування** відповідає на нього автоматично. Інструмент робить невеликі навмисні зміни в коді (**мутанти**): `<` стає `<=`, `+` стає `-`, `true` стає `false`, інструкцію видаляють. Потім для кожного мутанта запускає тести.

- Якщо якийсь тест провалюється, мутанта **вбито**: добре.
- Якщо всі тести досі проходять, мутант **вижив**: тести не помічають такого різновиду помилок.

Інструмент для .NET — **Stryker.NET**. Частка вбитих мутантів (mutation score) каже про якість ваших тестів більше, ніж покриття рядків. Він повільний, тож його застосовують до важливих частин коду.

Мутаційний тест можна зробити й вручну: замініть `<` на `<=` у вашому коді й запустіть тести. Якщо вони лишаються зеленими, бракує граничного тесту. Практичне завдання «Тестування» в цьому модулі побудоване саме на цій ідеї: ваші тести мають відхиляти хибні версії.
