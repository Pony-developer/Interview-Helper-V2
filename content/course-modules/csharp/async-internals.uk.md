## Що компілятор робить з `async`

`async`-метод переписується в **скінченний автомат** (state machine): приховану структуру, полями якої є локальні змінні методу, і метод `MoveNext`, що містить тіло, розрізане на шматки в кожному `await`.

На кожному `await task` згенерований код:

1. просить у задачі її **awaiter** (`task.GetAwaiter()`);
2. якщо задача **вже завершена** (`IsCompleted`), продовжує одразу, синхронно, без додаткових витрат;
3. інакше зберігає поточний стан, реєструє «виклич `MoveNext` знову, коли задача завершиться» (`OnCompleted`) і **повертається** до викликаючого;
4. коли задача завершується, `MoveNext` виконується знову, переходить до збереженого стану і забирає результат через `GetResult()` (який повторно кидає виняток задачі, якщо він був).

Тому `async`-метод повертається до викликаючого на першому `await` незавершеної задачі, і тому `await` можна застосувати до будь-чого, що має відповідний метод `GetAwaiter()`.

## `SynchronizationContext`: де виконується продовження

Перед кроком 3 `await` захоплює поточний **контекст синхронізації**:

- у WPF і WinForms це потік UI; продовження відправляють назад у нього, тож після `await` можна безпечно оновлювати елементи керування;
- у старому ASP.NET (.NET Framework) це був контекст запиту;
- в **ASP.NET Core і консольних застосунках його немає**: продовження виконується в будь-якому потоці пулу.

## `ConfigureAwait(false)`

```csharp
string text = await File.ReadAllTextAsync(path).ConfigureAwait(false);
```

Це означає: «не повертайся в захоплений контекст, продовжуй у будь-якому потоці». Так трохи швидше, і це запобігає взаємному блокуванню, описаному нижче. Використовуйте його в коді **бібліотек**, які не знають, хто їх викликає. Не використовуйте його в коді UI, що чіпає елементи керування після `await`. У прикладному коді ASP.NET Core він нічого не змінює.

## Класичне взаємне блокування

```csharp
// обробник кнопки у WPF
void Button_Click(object sender, EventArgs e)
{
    string data = LoadAsync().Result;   // блокує потік UI і чекає на задачу
}

async Task<string> LoadAsync()
{
    await Task.Delay(100);              // продовження хоче повернутися в потік UI...
    return "done";                      // ...який заблоковано через .Result: ніхто ніколи не продовжить
}
```

Потік UI чекає на задачу, а задача чекає на потік UI. Виправлення: зробити обробник `async` і використати `await` (найкраще) або використати `ConfigureAwait(false)` усередині `LoadAsync`.

## Два антипатерни

- **Sync over async**: `.Result`, `.Wait()`, `.GetAwaiter().GetResult()` на незавершеній задачі. Окрім взаємних блокувань, це блокує потік пулу; під навантаженням у пулі закінчуються потоки (**голодування пулу потоків**, thread-pool starvation), і весь сервер сповільнюється. Використовуйте `async` на всьому шляху вгору.
- **Async over sync**: загортання обчислювального чи блокувального методу в `Task.Run` усередині бібліотеки з назвою `XxxAsync`. Це лише переносить блокування в інший потік. Нехай викликаючий сам вирішує, чи використовувати `Task.Run`.

## Правило

`await` перевіряє, чи задача завершена, і якщо ні — повертається і продовжує пізніше, за замовчуванням у захопленому контексті. Ніколи не блокуйтеся на асинхронному коді; у бібліотеках використовуйте `ConfigureAwait(false)`.
