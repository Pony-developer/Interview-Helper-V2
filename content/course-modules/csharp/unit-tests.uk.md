**Модульний тест** перевіряє один невеликий шматок коду, зазвичай метод, ізольовано, швидко й без людського судження. Добрий набір таких тестів — це страхувальна сітка: ви змінюєте код упевнено, бо зламану поведінку виявляють за лічені секунди.

## Arrange, Act, Assert

Майже кожен тест має три частини:

```csharp
[Fact]
public void Discount_TenPercentOff_ReducesPrice()
{
    // Arrange: готуємо вхідні дані
    decimal price = 200m;

    // Act: викликаємо код, що тестується
    decimal result = Shop.ApplyDiscount(price, 10);

    // Assert: перевіряємо результат
    Assert.Equal(180m, result);
}
```

Залишайте частини помітними, а **дію** обмежуйте одним викликом. Тест із кількома незв'язаними діями й перевірками провалюється з незрозумілих причин.

## Іменування

Назва тесту має розповідати, що зламалося, ще до того, як хтось відкриє код. Популярний шаблон — **Метод_Сценарій_ОчікуванийРезультат**:

```text
Capitalize_EmptyString_ReturnsEmptyString
Divide_ByZero_ThrowsDivideByZeroException
IsLeapYear_Year1900_ReturnsFalse
```

Коли на сервері збірки червоніє `IsLeapYear_Year1900_ReturnsFalse`, ви вже знаєте багато.

## Що робить модульний тест добрим

Запам'ятайте слово **FIRST**:

- **Fast** (швидкий): мілісекунди, щоб ви запускали їх усі часто.
- **Isolated** (ізольований, незалежний): тест не залежить від іншого тесту й не зважає на порядок виконання.
- **Repeatable** (відтворюваний): той самий результат щоразу, на кожному комп'ютері.
- **Self-validating** (самоперевірний): проходить чи провалюється сам, без того, щоб хтось читав вивід.
- **Timely** (вчасний): написаний разом із кодом або навіть перед ним.

## Відтворюваність означає відсутність прихованих входів

Тест не повинен залежати від речей, що змінюються:

- **поточний час** (`DateTime.Now`);
- **випадкові** числа (беріть фіксоване зерно: `new Random(42)`);
- **мережа**, база даних, файлова система, змінні середовища;
- **культура** комп'ютера (передавайте `CultureInfo.InvariantCulture`, коли це важливо).

Коли коду потрібна така річ, дайте йому параметр чи інтерфейс, щоб тест міг підставити фіксоване значення:

```csharp
// важко тестувати: результат залежить від сьогоднішньої дати
static bool IsWeekend() => DateTime.Now.DayOfWeek >= DayOfWeek.Saturday;

// легко тестувати: дата — аргумент
static bool IsWeekend(DateTime date) =>
    date.DayOfWeek == DayOfWeek.Saturday || date.DayOfWeek == DayOfWeek.Sunday;
```

Код, який легко тестувати, зазвичай і добре спроєктований: малі методи з явними входами й виходами.

## Тестування винятків

Збій — теж поведінка, і вона заслуговує на тест:

```csharp
[Fact]
public void Divide_ByZero_Throws()
{
    Assert.Throws<DivideByZeroException>(() => Calculator.Divide(1, 0));
}
```

`() => ...` — це **лямбда**: крихітний метод без імені. `Assert.Throws` запускає її й проходить, лише якщо виникає очікуваний виняток. Тест, який не кидає виняток, коли мав би, знайшов помилку.

## Тести з даними

Коли ту саму логіку треба перевірити на багатьох вхідних даних, не копіюйте тест. Зробіть так, щоб він приймав параметри:

```csharp
[Theory]
[InlineData(2000, true)]
[InlineData(1900, false)]
[InlineData(2024, true)]
[InlineData(2023, false)]
public void IsLeapYear_ReturnsExpected(int year, bool expected)
{
    Assert.Equal(expected, Calendar.IsLeapYear(year));
}
```

Фреймворк запускає метод **один раз для кожного `InlineData`** і звітує про кожен випадок окремо. Додати випадок коштує один рядок.

## Та сама ідея на простому C#

Без фреймворку впорається таблиця випадків і цикл. Саме це роблять практичні завдання:

```csharp
int[] years =       { 2000, 1900, 2024, 2023 };
bool[] expected =   { true, false, true, false };

for (int i = 0; i < years.Length; i++)
{
    bool actual = IsLeapYear(years[i]);
    Console.WriteLine((actual == expected[i] ? "ok" : "FAIL") + ": " + years[i]);
}
```

## Підробки замість реального світу

Модульний тест не повинен надсилати справжній лист чи списувати гроші зі справжньої картки. Код, що тестується, говорить з **інтерфейсом**, а тест дає йому **підробку** (stub чи mock), яка повертає підготовлені відповіді й запам'ятовує, про що її питали:

```csharp
interface IClock { DateTime Now { get; } }

class FixedClock : IClock
{
    public DateTime Now => new DateTime(2026, 1, 1);
}
```

Бібліотеки на кшталт Moq створюють такі підробки за вас.

## Чого уникати

- **Логіки в тестах**: цикли та `if` ускладнюють довіру до тесту. Тест має бути простішим за код, який перевіряє.
- **Тестування приватних деталей**: тестуйте публічну поведінку, щоб рефакторинг не ламав тести.
- **Тестів, що залежать один від одного**: спільного стану, який один тест лишає наступному.
- **Перевірок усього підряд**: перевіряйте те, що важливо для цього сценарію, і не більше.
- **Ігнорування тесту, що падає**, замість його виправлення. Набір із «відомими збоями» вчить усіх ігнорувати червоний колір.
