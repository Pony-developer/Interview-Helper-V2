**Розділяй і володарюй** — найважливіше застосування рекурсії для ефективності. Замість того, щоб атакувати велику задачу напряму, ви:

1. **Ділите** її на менші підзадачі того самого виду (зазвичай на дві половини).
2. **Володарюєте**: розв'язуєте кожну підзадачу рекурсивно. Крихітні — це базовий випадок.
3. **Поєднуєте** відповіді частин у відповідь для цілого.

## Приклад: максимум

```csharp
static int Max(int[] a, int left, int right)
{
    if (left == right) return a[left];               // один елемент: базовий випадок

    int middle = left + (right - left) / 2;
    int leftMax = Max(a, left, middle);              // розв'язуємо ліву половину
    int rightMax = Max(a, middle + 1, right);        // розв'язуємо праву половину
    return Math.Max(leftMax, rightMax);              // поєднуємо
}
```

Тут простіший цикл, і це те саме O(n). Приклад показує **шаблон**; справжня сила з'являється, коли крок поєднання хитрий.

## Сортування злиттям

Відсортуйте масив: розбийте його навпіл, відсортуйте кожну половину й **злийте** дві відсортовані половини в один відсортований масив. Злиття — це єдиний прохід, що раз за разом бере менший із двох передніх елементів:

```csharp
static int[] MergeSort(int[] a)
{
    if (a.Length <= 1) return a;                      // базовий випадок

    int middle = a.Length / 2;
    int[] left = new int[middle];
    int[] right = new int[a.Length - middle];
    Array.Copy(a, 0, left, 0, middle);
    Array.Copy(a, middle, right, 0, a.Length - middle);

    return Merge(MergeSort(left), MergeSort(right));  // розділити, розв'язати, поєднати
}

static int[] Merge(int[] left, int[] right)
{
    int[] result = new int[left.Length + right.Length];
    int i = 0, j = 0, k = 0;
    while (i < left.Length && j < right.Length)
    {
        result[k++] = left[i] <= right[j] ? left[i++] : right[j++];
    }
    while (i < left.Length) result[k++] = left[i++];
    while (j < right.Length) result[k++] = right[j++];
    return result;
}
```

Дерево для 8 елементів:

```text
[5 2 8 1 9 3 7 4]                 рівень 0: 1 масив із 8
[5 2 8 1]   [9 3 7 4]             рівень 1: 2 масиви по 4
[5 2] [8 1] [9 3] [7 4]           рівень 2: 4 масиви по 2
[5][2][8][1][9][3][7][4]          рівень 3: 8 масивів по 1 (листки)
```

На зворотному шляху частини зливаються рівень за рівнем. Кожен рівень обробляє **всі `n` елементів** один раз (злиття), а рівнів **log₂ n**. Тож час — **O(n log n)**. Це значно краще, ніж O(n²) простих сортувань, і те саме, що в `Array.Sort`.

## Підрахунок роботи: рекурентне співвідношення

Якщо `T(n)` — час для вхідних даних розміру `n`, сортування злиттям задовольняє

```text
T(n) = 2 · T(n / 2) + O(n)
        └ дві половини ┘   └ злиття
```

Три типові форми:

| Співвідношення | Значення | Час |
| --- | --- | --- |
| `T(n) = T(n / 2) + O(1)` | одна половина, стала робота (двійковий пошук) | O(log n) |
| `T(n) = 2 · T(n / 2) + O(1)` | обидві половини, стала робота (максимум) | O(n) |
| `T(n) = 2 · T(n / 2) + O(n)` | обидві половини, лінійна робота (сортування злиттям) | O(n log n) |

Один зі способів побачити це: накресліть дерево й додайте роботу **за рівнями**. У сортуванні злиттям кожен рівень робить `n` роботи, а рівнів `log₂ n`.

## Ще приклади

**Двійковий пошук** ділить діапазон і відкидає одну половину: розв'язується лише одна підзадача, тож поєднання немає.

**Швидкий степінь**: `x^p = (x^(p/2))²`, одна підзадача половинного розміру.

**Швидке сортування** ділить масив навколо **опорного елемента**: менші значення йдуть ліворуч, більші — праворуч, а потім кожну сторону сортують рекурсивно. Робота припадає на **поділ**, а поєднувати нічого. У середньому це O(n log n), але невдалий вибір опорних елементів на вже відсортованих даних може дати O(n²).

**Знаходження найближчої пари точок** та **множення великих чисел** (Карацуба) швидші за очевидний метод завдяки тому самому шаблону.

## Коли це працює

Розділяй і володарюй добре підходить, коли:

- задачу **можна розбити** на незалежні частини того самого виду;
- підзадачі **менші в сталу кількість разів** (вдвічі, втричі), а не на одиницю;
- **поєднання** відповідей дешеве (лінійне чи краще).

Погано підходить, коли підзадачі **перекриваються**, тобто ті самі розв'язуються знову й знову (як у дереві Фібоначчі). Це випадок для мемоїзації та динамічного програмування.

## Практичні зауваження

- **Малі випадки**: справжні бібліотеки припиняють ділення на розмірі близько 10–20 й закінчують простим методом на кшталт сортування вставками, бо для крихітних шматків накладні витрати рекурсії більші за економію.
- **Пам'ять**: сортування злиттям потребує додаткового масиву розміру O(n). Глибина рекурсії лише O(log n), тож для стека небезпеки немає.
- **Паралелізм**: дві половини незалежні, тож їх можна розв'язувати на різних ядрах процесора одночасно.
- **Вибір середини**: пишіть `left + (right - left) / 2`, а не `(left + right) / 2`, що може переповнитися для великих індексів.
