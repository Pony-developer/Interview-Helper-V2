Почати новий проєкт із тестами легко. Важкий випадок — проєкт, що вже існує, з тисячами рядків і без тестів, та команда, яка зайнята. Ця лекція про те, як упроваджувати тести крок за кроком.

## Починайте з малого й там, де болить

Не зупиняйте все, щоб «написати тести для всієї системи». Це ніколи не буде закінчено. Натомість:

1. **Нова функція**: пишіть для неї тести по ходу справи.
2. **Виправлення помилки**: спершу напишіть тест, що відтворює помилку, потім виправте її.
3. **Ризикована зміна**: перш ніж чіпати старий шматок коду, додайте тести, що описують, що він робить зараз.

За кілька місяців частини коду, що змінюються найчастіше, а це саме ті, яким потрібні тести, виявляться покритими, без жодного «великого проєкту тестування».

## Характеризаційні тести для старого коду

Для застарілого коду, якого ніхто не розуміє, перша мета — не вирішити, що **правильно**, а зафіксувати, що код **робить**. Це називається **характеризаційним тестом**:

1. Викличте код із вхідними даними.
2. Подивіться, що він повертає.
3. Напишіть тест, що стверджує саме це.

Тест не каже «це правильно», а лише «так це поводиться сьогодні». Тепер можна безпечно рефакторити: якщо тест червоніє, ви змінили поведінку, і можете вирішити, чи це було задумано.

## Як зробити код придатним до тестування

Старий код часто важко тестувати, бо він усе робить в одному місці: читає файл, обчислює та друкує водночас. Допомагає кілька невеликих кроків:

- **Відокремте** обчислення від введення й виведення: метод, що бере значення й повертає результат, можна тестувати, а метод, що читає консоль, — ні.
- Передавайте **залежності** (час, файл, сервіс) як параметри чи інтерфейси.
- Розбийте величезний метод на менші й тестуйте малі.
- Уникайте глобального (статичного) стану, який один тест лишає наступному.

```csharp
// важко тестувати: читає консоль і друкує
static void Main()
{
    int age = int.Parse(Console.ReadLine());
    Console.WriteLine(age >= 18 ? "adult" : "minor");
}

// легко тестувати: чиста функція
static string Classify(int age) => age >= 18 ? "adult" : "minor";
```

## Де живуть тести

У .NET звичайне розташування — **окремий тестовий проєкт** поруч з основним:

```text
Shop/
  Shop.Core/             код
  Shop.Core.Tests/       тести для нього (посилається на Shop.Core)
  Shop.sln
```

Тести **не** постачаються з продуктом. Усередині тестового проєкту віддзеркалюйте структуру коду: `Calculator` тестується в `CalculatorTests`.

## Запускайте їх автоматично

Тест, який ніхто не запускає, марний. Зробіть запуск тестів автоматичним:

- **Локально**: перед кожним комітом запускайте тести, що стосуються вашої зміни. Тримайте весь набір достатньо швидким, щоб запускати часто.
- **У безперервній інтеграції (CI)**: на кожен push чи pull request сервер збирає проєкт і запускає всі тести. Зміна з червоними тестами не зливається. Мінімальний крок GitHub Actions:

```yaml
- name: Test
  run: dotnet test --configuration Release
```

CI — це місце, де закінчується проблема «на моїй машині працює».

## Здорові звички

- **Вважайте червону збірку терміновою.** Один зламаний тест, який усі ігнорують, перетворює набір на шум.
- **Виправляйте чи видаляйте нестабільні тести.** Нестабільний тест то проходить, то падає з тим самим кодом через таймінг, порядок, випадковість чи мережу. Він привчає перезапускати, доки не стане зеленим, а це руйнує довіру.
- **Тримайте тести швидкими.** Набір, що виконується за секунди, запускають. Той, що виконується пів години, — ні.
- **Рецензуйте тести** під час код-рев'ю так само уважно, як і код.
- **Давайте тестам зрозумілі назви** й одну причину падіння.
- **Видаляйте тести, які втратили сенс**, наприклад коли змінилася сама вимога.

## Що вимірювати

Не вимірюйте «кількість тестів». Кращі питання:

- Як часто помилки потрапляють на продакшн і чи міг їх виявити якийсь тест?
- Скільки часу минає, перш ніж ви дізнаєтеся, що зміна щось зламала?
- Чи наважується команда рефакторити?
- Скільки тестів зараз червоні, проігноровані чи нестабільні?

## План першого тижня

1. Створіть тестовий проєкт і запустіть **один** тривіальний тест через весь ланцюжок: локально та в CI.
2. Додайте тести для наступної помилки, яку виправлятимете.
3. Оберіть найкритичніший або найскладніший метод і покрийте його таблицею випадків, зокрема межами.
4. Зробіть тести частиною означення «готово»: «зміна завершена, коли є тести й вони проходять».

Мета — не ідеальний набір за тиждень, а звичка, що лишається.
