Одна з найкорисніших навичок — розпізнати **ланцюжок перевірок, який мав би бути поліморфізмом**. Він виглядає так:

```csharp
static double Area(object shape)
{
    if (shape is Circle c)
    {
        return Math.PI * c.Radius * c.Radius;
    }
    else if (shape is Square s)
    {
        return s.Side * s.Side;
    }
    else if (shape is Rectangle r)
    {
        return r.Width * r.Height;
    }
    throw new ArgumentException("Unknown shape");
}
```

Або те саме з **кодом типу**:

```csharp
class Employee
{
    public int Type;                         // 1 = розробник, 2 = керівник, 3 = стажист
}

static int Pay(Employee e)
{
    switch (e.Type)
    {
        case 1: return 3000;
        case 2: return 4000 + 100 * e.Reports;
        case 3: return e.Hours * 15;
        default: throw new ArgumentException("Unknown type");
    }
}
```

## Чому це болить

- **Кожен новий вид** (`Triangle`, `Contractor`) потребує **нової гілки** в цій функції та в кожній **іншій** функції, що перевіряє тип: `Perimeter`, `Draw`, `Describe`, `Save`. Забута гілка дає виняток «Unknown shape» під час виконання, на бойовому сервері.
- Знання про один вид **розкидано** по програмі, а код однієї фігури лежить у десяти місцях.
- Компілятор **не може допомогти**: він не каже, який `switch` треба оновити.

Це називається **порушенням принципу відкритості/закритості**: код має бути **відкритим** для додавання нових видів і **закритим** для редагування коду, що вже працює.

## Рефакторинг

1. Знайдіть **спільну ідею** гілок: тут це «щось, що має площу».
2. Додайте її в базовий тип як **віртуальний чи абстрактний** член: `public abstract double Area { get; }`.
3. **Перенесіть кожну гілку** в клас, якому вона належить: гілка `Circle` іде в `Circle.Area` і так далі.
4. Замініть увесь ланцюжок **одним викликом**: `shape.Area`.
5. **Видаліть** стару функцію.

```csharp
abstract class Shape { public abstract double Area { get; } }

class Circle : Shape
{
    private readonly double radius;
    public Circle(double radius) { this.radius = radius; }
    public override double Area => Math.PI * radius * radius;      // гілка живе поруч зі своїми даними
}

class Square : Shape { /* ... */ }
```

Після цього **новий** вид — це **один новий клас**. Жоден існуючий код не змінюється, а компілятор перевіряє, що новий клас має все потрібне (члени `abstract`).

Дані теж покращуються: поля `Radius` чи `Side` можуть бути **приватними**, бо код, якому вони були потрібні ззовні, тепер усередині класу.

Для **коду** типу створіть клас для **кожного значення** і перетворіть `switch` на віртуальний метод. Поле `Type` зникає, бо тип об'єкта **і є** кодом.

## Чи всі `switch` погані?

Ні. `switch` — це добре, коли:

- вибір іде серед **малого стабільного набору** значень (дні тижня, команди меню), а нове значення трапляється рідко;
- він в **одному** місці, зазвичай там, де об'єкти **створюються** зі вхідних даних (**фабрика**): `case "circle": return new Circle(...)`;
- він працює із **простими даними** (`enum`), і різної поведінки, яку можна прикріпити, немає.

`switch` — це **запах коду**, коли **той самий** `switch` чи ланцюжок `if` з'являється в **кількох функціях**, а кожен новий вид потребує правок у всіх.

## Зіставлення зі зразком на межі

У C# 7 є `switch` зі зразками типів, що є охайнішим способом записати «поганий» ланцюжок:

```csharp
switch (shape)
{
    case Circle c: return Math.PI * c.Radius * c.Radius;
    case Square s: return s.Side * s.Side;
    default: throw new ArgumentException("Unknown shape");
}
```

Це коротше й зрозуміліше, але це **той самий** дизайн із тими самими проблемами. Він пасує на **краю** системи, коли ви отримуєте об'єкти типів, які не можете змінити (наприклад, із бібліотеки) і не можете додати до них метод. Для власних класів віртуальний метод зазвичай кращий.

## Короткий перелік перевірок

1. Чи код питає об'єкт, **чим він є**, а потім **щось із ним робить**?
2. Чи те саме питання з'являється в кількох місцях?
3. Чи новий вид об'єкта означав би правки старого коду?

Якщо відповідь «так», **перенесіть поведінку в об'єкт**. Цю ідею іноді виражають словами **«кажи, а не питай»**: не питайте об'єкт про його тип і не вирішуйте за нього, а накажіть йому виконати роботу.
