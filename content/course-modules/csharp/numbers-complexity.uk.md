З масивом `n` — це кількість елементів, і все зрозуміло. З **числами** є пастка. Який розмір вхідних даних, коли вхід — число 1 000 000?

## Розмір числа — це його довжина

Число записується цифрами. Число 1 000 000 має 7 цифр, а число в тисячу разів більше — лише на 3 більше. Кількість інформації в `N` — близько **log N**: кількість цифр або кількість бітів.

Тож для алгоритмів із числами чесний розмір входу — **b = log₂ N**, кількість бітів. Алгоритм, що робить `N` кроків, робить близько `2ᵇ` кроків. Він **експоненційний** за розміром входу, хоча й виглядає «лінійним за N».

Ось чому лічба від 1 до N — повільна справа для великого N: вона швидка лише тому, що «великі» числа у звичайних програмах мають мало цифр.

## Завдання з цифрами: O(log N)

Цикл, що відділяє по одній цифрі, виконується стільки разів, скільки є цифр:

```csharp
static int DigitSum(long n)
{
    int sum = 0;
    while (n > 0)
    {
        sum += (int)(n % 10);
        n /= 10;
    }
    return sum;
}
```

Для `n = 10¹⁸` це 19 проходів. Складність — **O(log N)**, тобто **O(b)** за розміром входу: лінійна за кількістю цифр. Це справді швидко.

## Пробне ділення: O(√N)

Найпростіша перевірка на простоту перебирає дільники до квадратного кореня:

```csharp
static bool IsPrime(long n)
{
    if (n < 2) return false;
    for (long d = 2; d * d <= n; d++)
        if (n % d == 0) return false;
    return true;
}
```

Вона робить до √N кроків. Для `N` близько 10¹² це 10⁶: миттєво. Для `N` близько 10¹⁸ це 10⁹: близько секунди. Але в термінах **розміру входу** `b = log₂ N` маємо `√N = 2^(b/2)`: експоненційно. Числу з 300 цифр знадобилося б близько 10¹⁵⁰ кроків, що назавжди поза досяжністю. Саме тому шифрування інтернету ґрунтується на **складності розкладання** великих чисел на множники: ніхто не знає швидкого алгоритму.

## Алгоритм Евкліда: O(log N)

Найбільший спільний дільник двох чисел: замінюйте пару `(a, b)` на `(b, a mod b)`, доки `b` не стане нулем.

```csharp
static long Gcd(long a, long b)
{
    while (b != 0)
    {
        long r = a % b;
        a = b;
        b = r;
    }
    return a;
}
```

Після кожних двох кроків числа принаймні вдвічі зменшуються, тож кількість кроків — **O(log min(a, b))**, щонайбільше близько п'яти разів кількість цифр. Порівняйте з наївним способом, коли перебирають усі числа від меншого до 1: **O(N)**, експоненційно за кількістю цифр. Для `Gcd(10¹⁸, 10¹⁷ + 3)` Евклід робить менш ніж сотню кроків, а наївний спосіб зробив би 10¹⁷.

## Степінь через повторне піднесення до квадрата: O(log p)

Обчислювати `xᵖ`, множачи `x` на себе `p − 1` разів, — це O(p). Але `x¹⁶ = (((x²)²)²)²`: чотири піднесення до квадрата замість п'ятнадцяти множень.

```csharp
static long Power(long x, int p)
{
    long result = 1;
    while (p > 0)
    {
        if (p % 2 == 1) result *= x;   // цей біт p дорівнює 1
        x *= x;                        // квадрат
        p /= 2;                        // наступний біт
    }
    return result;
}
```

Воно робить близько `log₂ p` раундів. Обчислення `x¹⁰⁰⁰⁰⁰⁰⁰⁰⁰` займає близько 30 раундів замість мільярда. Той самий прийом, із взяттям остачі після кожного множення, — серце сучасної криптографії. (Стережіться переповнення: `long` вміщує лише близько 9 · 10¹⁸.)

## Факторіал і Фібоначчі

- `n!` циклом робить `n` множень: **O(n)**. Але **числа стають величезними**: 20! уже заповнює `long`, а `1000!` має 2 568 цифр. З такими числами множення — не один крок, а зростає з кількістю цифр.
- `n`-те число Фібоначчі циклом з двома змінними: **O(n)** додавань. Матричним методом чи «швидким подвоєнням» — **O(log n)** множень. Наївна рекурсія — O(2ⁿ).

## Решето Ератосфена

Щоб знайти **всі** прості числа до `N`, викреслювання кратних набагато швидше, ніж перевірка кожного числа окремо:

```csharp
bool[] isComposite = new bool[N + 1];
for (int i = 2; (long)i * i <= N; i++)
    if (!isComposite[i])
        for (int j = i * i; j <= N; j += i)
            isComposite[j] = true;
```

Час — **O(N log log N)**: майже лінійний. Ціна — **пам'ять**: O(N) для масиву. Це типовий обмін простору на час.

## Псевдополіноміальні алгоритми

Іноді алгоритм поліноміальний за **значенням** числа, але експоненційний за його **довжиною**. Лічба до N, пробне ділення та стандартний розв'язок задачі про рюкзак динамічним програмуванням (час пропорційний місткості `W`) саме такі. Вони годяться, коли числа малі, і безнадійні, коли мають сотні цифр. Завжди питайте: *складність виражена через значення чи через кількість цифр?*
