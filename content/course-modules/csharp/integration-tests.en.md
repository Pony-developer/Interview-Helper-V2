Unit tests prove that each piece works. They do not prove that the pieces work **together**: that the route is mapped, the JSON has the expected shape, dependency injection can build the controller, the SQL runs on a real database, and the middleware returns 401 without a token. That is the job of **integration tests**.

## How many of each

The classic **test pyramid**:

- at the bottom, **many unit tests**: milliseconds each, precise, run on every save;
- in the middle, **fewer integration tests**: seconds each, check the joints (HTTP, database, serialization, DI);
- at the top, **a few end-to-end tests**: a real browser against a deployed system (Playwright, Selenium); slow and fragile, but closest to the user.

For web APIs, many teams put more weight on the middle (Kent C. Dodds's "testing trophy"): a test that sends a real HTTP request to the app and checks the response covers a lot of code and survives refactoring well. Either way, the slow tests should be few.

## WebApplicationFactory

The package `Microsoft.AspNetCore.Mvc.Testing` starts your **whole application in memory**: the real `Program`, configuration, DI container, middleware pipeline, routing and controllers, on top of an in-memory `TestServer` instead of Kestrel. You get an `HttpClient` that calls it without opening a network port.

```csharp
public class ProductsApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient client;

    public ProductsApiTests(WebApplicationFactory<Program> factory)
    {
        client = factory.CreateClient();
    }

    [Fact]
    public async Task GetProduct_Existing_Returns200AndJson()
    {
        var response = await client.GetAsync("/api/products/1");

        Assert.Equal(HttpStatusCode.OK, response.StatusCode);
        var product = await response.Content.ReadFromJsonAsync<ProductDto>();
        Assert.Equal("Keyboard", product!.Name);
    }

    [Fact]
    public async Task CreateProduct_WithoutName_Returns400()
    {
        var response = await client.PostAsJsonAsync("/api/products", new { price = 10 });
        Assert.Equal(HttpStatusCode.BadRequest, response.StatusCode);
    }
}
```

`WebApplicationFactory<Program>` needs to see the `Program` class of the app. With top-level statements that class is generated by the compiler and is internal; before .NET 10 you added `public partial class Program { }` at the end of `Program.cs` (or used `InternalsVisibleTo`). Since .NET 10 the framework generates the public declaration for you.

The factory is expensive to build, so share it with `IClassFixture` (one app per test class) or a collection fixture.

## Replacing services for the test

The app is real, but some of its dependencies should not be: you do not want to charge real cards or send real e-mails. Subclass the factory, or call `WithWebHostBuilder`, and swap registrations:

```csharp
public class ApiFactory : WebApplicationFactory<Program>
{
    public FakeMailer Mailer { get; } = new FakeMailer();

    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment("Testing");
        builder.ConfigureTestServices(services =>
        {
            services.RemoveAll<IMailer>();
            services.AddSingleton<IMailer>(Mailer);
            services.RemoveAll<IPaymentGateway>();
            services.AddSingleton<IPaymentGateway, AlwaysApprovesGateway>();
        });
    }
}
```

`ConfigureTestServices` runs **after** the app's own registrations, so your doubles win. Replace only what leaves the process and is not yours: payment, e-mail, third-party APIs. Keep your own code, and if possible your own database, real.

Authentication is often replaced too: a test authentication handler that signs every request in as a known test user, so the tests do not need real tokens.

## The database

This is where integration tests earn their keep, and where they are most often done wrong.

| Option | Verdict |
| --- | --- |
| **EF Core InMemory provider** | Not a relational database: no SQL, no constraints, no real transactions, different query behaviour. Tests pass while production fails. Microsoft's own docs advise against it for testing. |
| **SQLite in memory** | A real SQL database and fast, but a different engine from your SQL Server or PostgreSQL: types, functions and locking differ. |
| **The real engine in a container (Testcontainers)** | Same engine and version as production; a few seconds to start. The usual choice today. |

```csharp
public class DbFixture : IAsyncLifetime
{
    private readonly PostgreSqlContainer container = new PostgreSqlBuilder()
        .WithImage("postgres:16-alpine")
        .Build();

    public string ConnectionString => container.GetConnectionString();

    public Task InitializeAsync() => container.StartAsync();
    public Task DisposeAsync() => container.DisposeAsync().AsTask();
}
```

Testcontainers starts a throwaway Docker container for the test run. Start it once per run or per collection, apply your migrations, and point the app at it in `ConfigureTestServices`.

Tests that share a database must not see each other's data. Common strategies:

- **unique data per test**: each test creates its own customer with a new id and only queries that;
- **reset between tests**: delete the data (the Respawn library does it quickly and in the right order of foreign keys);
- **a transaction per test** that is rolled back at the end (fast, but does not work when the code under test commits its own transactions).

## Keeping integration tests healthy

- Run them in CI on every pull request, not "sometimes before a release".
- Mark them (`[Trait("Category", "Integration")]`) so developers can run only the fast tests locally.
- Never depend on test order or on data that another test created.
- No real external services: a test that fails because a partner's sandbox is down teaches the team to ignore red builds.
- Check **behaviour visible from outside**: status codes, response bodies, what ended up in the database, what the fake mailer received. Not private details.

## In an interview

"How do you test an ASP.NET Core API?" A good answer has layers: unit tests for the domain logic with fakes at the edges; integration tests through `WebApplicationFactory` with the real pipeline, external services replaced in `ConfigureTestServices`, and a real database in a container; a handful of end-to-end tests for the critical user paths; all of it running in CI.
