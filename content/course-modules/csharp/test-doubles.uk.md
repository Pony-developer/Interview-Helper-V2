Модульний тест має перевіряти один шматок коду — швидко й відтворювано. Але справжній код працює з базами даних, веб-API, поштовими серверами й годинником. **Тестовий дублер** (test double) — це об'єкт, що підміняє таку залежність під час тесту, як каскадер підміняє актора. Назву й класифікацію запропонував Джерард Месарош у книзі *xUnit Test Patterns*, і про них часто питають на співбесідах.

> **Примітка.** Онлайн-запускач цього курсу не вміє завантажувати пакети NuGet, тож приклади з бібліотеками в цьому модулі — для вашого комп'ютера. У практичних завданнях ті самі ідеї будуються вручну.

## П'ять видів дублерів

Приклади використовують такий сервіс: він знімає оплату з клієнта й надсилає квитанцію поштою.

```csharp
public interface IPaymentGateway { bool Charge(string card, decimal amount); }
public interface IMailer { void Send(string to, string text); }
public interface IAuditLog { void Write(string entry); }

public class CheckoutService
{
    public CheckoutService(IPaymentGateway gateway, IMailer mailer, IAuditLog audit) { /* ... */ }
    public bool Pay(string email, string card, decimal amount) { /* ... */ }
}
```

| Дублер | Що робить | Приклад |
| --- | --- | --- |
| **Dummy** (манекен) | Передається лише для заповнення параметра; насправді не використовується | `null` або порожній `IAuditLog` у тесті, якому байдужий аудит |
| **Stub** (стаб, заглушка) | Повертає коду, що тестується, підготовлені відповіді | шлюз, чий `Charge` завжди повертає `false` |
| **Spy** (шпигун) | Стаб, що ще й записує, як його викликали; тест потім перевіряє записи | поштовик, що додає кожен лист у `List<string>` |
| **Mock** (мок) | Заздалегідь знає, які виклики очікувати, і тест їх перевіряє | «`Send` має бути викликаний один раз з `ann@example.com`» |
| **Fake** (фейк) | Робоча, спрощена реалізація | репозиторій у пам'яті, фейковий годинник |

Написані вручну стаб і шпигун — часто лише кілька рядків:

```csharp
class DecliningGateway : IPaymentGateway          // стаб
{
    public bool Charge(string card, decimal amount) { return false; }
}

class SpyMailer : IMailer                         // шпигун
{
    public readonly List<string> Sent = new List<string>();
    public void Send(string to, string text) { Sent.Add(to + ": " + text); }
}

[Fact]
public void Pay_DeclinedCard_SendsNoReceipt()
{
    var mailer = new SpyMailer();
    var service = new CheckoutService(new DecliningGateway(), mailer, new NullAuditLog());

    bool paid = service.Pay("ann@example.com", "4111", 10m);

    Assert.False(paid);
    Assert.Empty(mailer.Sent);
}
```

У побуті все це називають «моками», а бібліотеки на кшталт Moq створюють будь-який вид одним класом. На співбесіді покажіть, що розрізняєте їх: **стаб подає дані всередину, мок (чи шпигун) перевіряє, що вийшло назовні у вигляді викликів.**

## Перевірка стану і перевірка поведінки

Результат можна перевірити двома способами:

- **Перевірка стану** (state verification): виконати код, а потім подивитися на результат чи стан: повернене значення, що тепер лежить у фейковому репозиторії.
- **Перевірка поведінки** (behaviour verification): перевірити, що код зробив правильні виклики до залежностей: `Send` викликано один раз із такими аргументами.

Де можна, обирайте стан. Тест, що перевіряє результат, переживає рефакторинг: можна перейменувати приватні методи, об'єднати два виклики в один, додати кешування — і тест проходить, доки поведінка правильна. Перевіряйте виклики, коли **виклик і є результатом**: надіслати лист, опублікувати повідомлення, зняти оплату з картки. Ніщо інше не покаже, що це сталося.

## Дві школи

- **Класична** (детройтська) школа використовує справжні об'єкти скрізь, де вони швидкі й детерміновані, і підміняє лише повільне, спільне або те, що поза процесом: базу даних, мережу, файлову систему, годинник. «Модуль» — це одиниця поведінки, яка може охоплювати кілька класів.
- **Мокістська** (лондонська) школа ізолює кожен клас: кожного співпрацівника замінюють моком, а тести переважно перевіряють взаємодії.

Мокістські тести точно вказують на зламаний клас, але знають багато про те, як з'єднано код, тож ламаються, коли змінюється це з'єднання. Більшість команд сьогодні тяжіє до класичного підходу: мокати на межах системи, а не між власними класами.

## Що підміняти, а що ні

Підміняйте:

- **Зовнішні залежності поза процесом, які ви не контролюєте**: платіжних провайдерів, сервіси пошти й SMS, сторонні API, шини повідомлень.
- **Недетерміновані входи**: годинник, випадкові числа, `Guid.NewGuid()`.
- **Повільні речі**, коли тест про щось інше.

Не підміняйте:

- **Значення й чисту логіку**: `Money`, `DateRange`, калькулятор ціни. Використовуйте справжні.
- **Власну базу даних** у тестах коду доступу до даних. Замоканий `DbContext` нічого не доводить про ваш SQL; потрібен інтеграційний тест (див. останню лекцію модуля).
- **Чужі типи**, мокаючи їхні методи по одному. Мок `HttpClient` чи клієнта SDK кодує ваше припущення про поведінку бібліотеки. Загорніть бібліотеку у власний невеликий інтерфейс (`IExchangeRates`) і мокайте його, або використайте тестові помічники самої бібліотеки.

## Тривожні ознаки

- Тест налаштовує більше моків, ніж має рядків справжніх перевірок.
- Мок повертає мок, що повертає мок (`repo.GetUnitOfWork().GetSession().Query()`): код, що тестується, знає забагато про своїх сусідів.
- Перевірка викликів, що не є частиною результату, наприклад «логер викликано двічі».
- Кожен рефакторинг ламає десятки тестів, хоча програма працює.

Тест, якому потрібно багато дублерів, зазвичай щось каже про дизайн: клас робить забагато або залежить від надто багатьох речей.
