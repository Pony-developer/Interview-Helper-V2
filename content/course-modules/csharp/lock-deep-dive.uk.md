Ви вже знаєте, що `lock` пускає в блок лише один потік за раз. На співбесідах ідуть далі: що таке `lock` насправді, на чому можна блокуватися і чому всередині нього заборонено `await`.

## `lock` — це `Monitor`

```csharp
lock (sync)
{
    balance += amount;
}
```

компілюється в:

```csharp
bool taken = false;
try
{
    Monitor.Enter(sync, ref taken);
    balance += amount;
}
finally
{
    if (taken) Monitor.Exit(sync);
}
```

Тож блокування завжди звільняється, навіть після винятку. Будь-який об'єкт у .NET може слугувати блокуванням, бо середовище виконання вміє прикріпити запис блокування до будь-якого об'єкта.

`lock` — **реентерабельний**: потік, що вже тримає блокування, може ввійти в нього знову (наприклад, через рекурсивний виклик), не заблокувавши сам себе.

## На чому блокуватися

Блокуйтеся на **приватному readonly-об'єкті**, що існує лише для цього:

```csharp
private readonly object sync = new object();
```

Не блокуйтеся на:

- `this`: будь-який сторонній код, що має посилання на ваш об'єкт, теж може на ньому заблокуватися і заблокувати вас;
- `typeof(MyClass)`: він спільний для всього процесу;
- **рядку**: рядкові літерали інтернуються, тож `lock ("key")` у двох не пов'язаних класах — це те саме блокування;
- значущому типі: він щоразу пакується в новий об'єкт, тож блокування ніколи не спрацює (компілятор це забороняє).

Починаючи з .NET 9 є окремий тип `System.Threading.Lock`: `private readonly Lock sync = new();`. Він трохи швидший і чітко показує своє призначення.

## Жодного `await` усередині `lock`

```csharp
lock (sync)
{
    await SaveAsync();   // помилка компіляції CS1996
}
```

Монітор належить **потоку**, а після `await` метод може продовжитися в іншому потоці, який тоді спробував би звільнити блокування, яким не володіє. Для асинхронного коду використовуйте `SemaphoreSlim` і `WaitAsync` (наступна лекція).

## Взаємні блокування і таймаути

Два потоки, що беруть два блокування в протилежному порядку, можуть вічно чекати один на одного. Ліки:

- брати блокування завжди **в одному порядку**;
- тримати блокування якомога коротше і ніколи не викликати всередині нього невідомий код (події, колбеки);
- використовувати `Monitor.TryEnter(sync, timeout)`, щоб відмовитися замість вічного очікування.

## Видимість і `volatile`

Без синхронізації компілятор чи процесор можуть тримати значення в регістрі або переставляти читання і записи. Цикл `while (!stop) { }` може так і не побачити, що інший потік присвоїв `stop = true`. `lock`, `Interlocked` і `Volatile.Read`/`Volatile.Write` створюють **бар'єри пам'яті**, що роблять зміни видимими. Ключове слово `volatile` на полі робить те саме для простих прапорців, але не робить `count++` атомарним.

## Ліниве ініціалізування

Класичне «блокування з подвійною перевіркою» для синглтона легко написати неправильно. Використовуйте `Lazy<T>`, який за замовчуванням потокобезпечний:

```csharp
private static readonly Lazy<Config> config = new Lazy<Config>(() => Config.Load());
public static Config Instance => config.Value;   // Load виконається один раз, навіть із багатьма потоками
```

## Правило

Блокуйтеся на приватному об'єкті, тримайте блок коротким і без `await` та невідомого коду, беріть кілька блокувань в одному незмінному порядку і віддавайте перевагу готовим інструментам, як-от `Interlocked` і `Lazy<T>`, а не синхронізації, написаній вручну.
