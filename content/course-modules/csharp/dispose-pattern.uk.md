А якщо хтось забуде викликати `Dispose`? Для пам'яті це неважливо: її забере GC. Для «сирого» дескриптора операційної системи — важливо: без страховки дескриптор витікає до завершення процесу. Ця страховка — **фіналізатор**.

## Фіналізатори

```csharp
class NativeBuffer
{
    private IntPtr memory = Marshal.AllocHGlobal(1024);

    ~NativeBuffer()            // фіналізатор: його викликає GC, а не ви
    {
        Marshal.FreeHGlobal(memory);
    }
}
```

Коли об'єкт із фіналізатором стає недосяжним, GC не звільняє його одразу. Він ставить об'єкт у чергу, і спеціальний **потік фіналізації** пізніше викликає `~NativeBuffer()`. Лише після цього пам'ять можна повернути. Ціна:

- об'єкт переживає щонайменше одне зайве збирання і тому переходить у старше покоління;
- порядок виконання фіналізаторів не визначено, тож фіналізатор не має користуватися іншими об'єктами з фіналізаторами;
- у .NET Core і новіших фіналізатори **не** виконуються, коли процес завершується.

Сьогодні фіналізатор майже ніколи не пишуть вручну: дескриптор обгортають у `SafeHandle` (наприклад, `SafeFileHandle`), який уже його має.

## Повний патерн Dispose

Коли клас усе ж напряму володіє некерованим ресурсом і може мати нащадків, класичний патерн такий:

```csharp
public class ResourceHolder : IDisposable
{
    private IntPtr buffer = Marshal.AllocHGlobal(1024);   // некерований ресурс
    private readonly Stream log = File.OpenWrite("log");  // керований, disposable
    private bool disposed;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);   // уже прибрано: фіналізатор не потрібен
    }

    protected virtual void Dispose(bool disposing)
    {
        if (disposed) return;
        if (disposing)
        {
            log.Dispose();           // керовані об'єкти: лише під час виклику з Dispose()
        }
        Marshal.FreeHGlobal(buffer); // некеровані ресурси: завжди
        buffer = IntPtr.Zero;
        disposed = true;
    }

    ~ResourceHolder()
    {
        Dispose(false);              // із фіналізатора: інших керованих об'єктів не чіпаємо
    }
}
```

Навіщо прапорець `disposing`? Коли виконується фіналізатор, інші керовані об'єкти (тут — `log`) уже могли бути фіналізовані, тож чіпати їх небезпечно. Під час виклику з `Dispose()` усе ще живе.

`GC.SuppressFinalize(this)` прибирає об'єкт із черги фіналізації, тож його звільняють за одне збирання замість двох.

Нащадок перевизначає `Dispose(bool)`, звільняє власні ресурси і викликає `base.Dispose(disposing)`.

## Коротка версія

`sealed`-класу, що володіє лише **керованими** disposable-об'єктами, нічого з цього не треба: ні фіналізатора, ні прапорця, лише `Dispose()`, що звільняє його поля. Саме так виглядає більшість класів, які ви писатимете.

## Правило

Фіналізатори — страховка для некерованих ресурсів, а не заміна `Dispose`. Замість власного фіналізатора обирайте `SafeHandle`, а повний патерн застосовуйте лише для не-sealed класу, що напряму володіє некерованим ресурсом.
