Можна написати програму, що дає правильну відповідь, і все одно не мати змоги нею користуватися. Причина часто не в помилці, а у **виборі алгоритму**.

## Одна задача, два алгоритми

Знайдіть прізвище в телефонній книзі на 1 000 000 записів, відсортованих за алфавітом.

- **Перегляд** з першої сторінки: до 1 000 000 поглядів.
- **Відкрити посередині**, вирішити, яку половину лишити, і повторити: щонайбільше **20** поглядів, бо 2²⁰ ≈ 1 000 000.

Обидва дають правильну відповідь. Один швидший у 50 000 разів, а розрив **росте** з розміром книги. Для книги на мільярд прізвищ перегляд потребує мільярда поглядів, а ділення навпіл — 30.

## Та сама ідея в числах

Сучасний процесор виконує приблизно від 10⁸ до 10⁹ простих операцій на секунду. Візьмімо 10⁸:

| Операцій | Час |
| --- | --- |
| 10⁶ | 0.01 с |
| 10⁸ | 1 с |
| 10¹⁰ | 100 с (майже 2 хвилини) |
| 10¹² | 10 000 с (майже 3 години) |
| 10¹⁵ | 10⁷ с (приблизно 4 місяці) |

Тепер порівняйте два способи відсортувати 1 000 000 чисел:

- простий метод, що порівнює кожну пару, приблизно n² = 10¹² операцій: **3 години**;
- добрий метод, як-от той, що стоїть за `Array.Sort`, приблизно n · log₂ n ≈ 2 · 10⁷ операцій: **0.2 секунди**.

Той самий комп'ютер, ті самі дані, той самий правильний результат.

## Швидший комп'ютер не врятує поганий алгоритм

Припустімо, ваш комп'ютер став **у 100 разів швидшим**. Наскільки більшу задачу ви розв'яжете за той самий час?

| Алгоритм | Розмір, який можна обробити |
| --- | --- |
| приблизно n кроків | у 100 разів більший |
| приблизно n² кроків | лише у **10** разів більший |
| приблизно 2ⁿ кроків | лише на **7** елементів більше (бо 2⁷ ≈ 100) |

Для алгоритму, що повільно зростає, кращий комп'ютер допомагає багато. Для того, що зростає швидко, майже нічого. Чекати швидшого заліза — не план: план — кращий алгоритм.

## Навіть формула — це алгоритм

Додайте числа від 1 до n:

```csharp
long sum = 0;
for (int i = 1; i <= n; i++)
    sum += i;                      // n кроків
```

```csharp
long sum = (long)n * (n + 1) / 2;  // 1 крок, яким би не було n
```

Друга версія взагалі не має циклу й займає однаковий час для n = 10 та для n = 10 000 000 000.

## Відомі ціни поганого вибору

**Фібоначчі за означенням**

```csharp
static long Fib(int n) => n < 2 ? n : Fib(n - 1) + Fib(n - 2);
```

`Fib(50)` робить понад 10¹⁰ викликів, бо ті самі значення обчислюються знову й знову. Цикл, що пам'ятає два останні числа, потребує **50** кроків.

**Перевірка кожної пари на дублікати**

Порівняти кожен елемент з кожним іншим: n² кроків. Покласти елементи в `HashSet` і питати «чи я це бачив?»: приблизно n кроків. Для мільйона елементів це 10¹² проти 10⁶.

## Де це важливо

Майже все, чим ви користуєтеся, складено з алгоритмів, обраних із урахуванням їхньої вартості: пошукові системи та карти (маршрути, найближчі місця), сортування й фільтрація списків, стиснення файлів і відео, перевірка правопису, рекомендації, бази даних (індекси роблять запит логарифмічним замість лінійного), шифрування.

## Спершу алгоритм, потім мікрооптимізація

Прискорити цикл на 20%, переписавши його тіло, — невелика перемога. Замінити алгоритм O(n²) на O(n log n) для великих вхідних даних — перемога в тисячі разів. Тож порядок такий:

1. Зробіть правильно.
2. Оберіть алгоритм відповідної складності.
3. Лише тоді, і лише якщо виміряно, що повільно, налаштовуйте деталі.

Цей модуль дає вам словник, **складність** та **O-нотацію**, щоб порівнювати алгоритми до запуску.
