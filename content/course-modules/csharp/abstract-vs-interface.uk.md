C# дає два інструменти для незавершеного типу: **абстрактний клас** та **інтерфейс**. Вони схожі, і початківці часто питають, що вибрати. Ось мапа.

## Порівняння

| | Абстрактний клас | Інтерфейс |
|---|---|---|
| Має код (тіла методів) | Так | Ні (лише сигнатури) |
| Має поля й конструктори | Так | Ні |
| Кілька для одного класу | **Ні**, один базовий клас | **Так**, скільки потрібно |
| Модифікатори доступу членів | Будь-які | Усі публічні |
| Відношення | «є різновидом» | «вміє / має роль» |
| Чи можуть непов'язані класи ділити його | Незручно | Природно |
| Зміна пізніше | Додати звичайний член безпечно | Додавання члена ламає всіх, хто реалізує |

## Питання, що вирішують

**1. Це роль чи різновид?**

- `IComparable<T>`, `IDisposable`, `IEnumerable<T>`: **ролі**. `Book`, `string` і `Version` можуть бути порівнюваними, а в усьому іншому не мають нічого спільного. **Інтерфейс.**
- `Shape`, `Animal`, `Document`: **різновиди** речей, що мають спільну структуру. **Абстрактний клас.**

**2. Чи є спільний код або дані?** Якщо похідним класам потрібні ті самі **поля** й той самий **код** (наприклад, `Describe()`, що вживає абстрактні частини), покладіть його в абстрактний клас. Інтерфейс не може його тримати, а копіювання — це проблема, з якої ми почали.

**3. Чи потрібні класові кілька ролей?** Клас має лише **один** базовий клас, але може реалізувати **багато** інтерфейсів. Якщо ролі мають поєднуватися (`Report` є `IPrintable`, `ISavable` та `IComparable<Report>`), це мусять бути інтерфейси.

**4. Чи реалізовуватимуть його сторонні?** Якщо інші люди писатимуть власні класи (плагіни, тести з підробками), **інтерфейс** — дружніший контракт: він не просить нічого, крім методів.

## Вживайте обидва

Два інструменти добре поєднуються. Поширений дизайн: **інтерфейс** — це контракт для зовнішнього світу, а **абстрактний клас** — готовий помічник, що реалізує більшу його частину:

```csharp
interface IShape
{
    double Area { get; }
    string Describe();
}

abstract class ShapeBase : IShape                      // помічник: спільна частина реалізації
{
    public abstract double Area { get; }
    public string Describe() { return GetType().Name + " " + Math.Round(Area, 2); }
}

class Circle : ShapeBase { /* лише власна частина кола */ }
```

Код, що вживає фігури, просить `IShape`. Клас, що хоче допомоги, походить від `ShapeBase`. Клас, що не може (він уже має базовий клас), реалізує `IShape` сам.

## Композиція замість успадкування

Успадкування — **сильний** зв'язок: похідний клас залежить від усіх деталей базового, і зміна в базовому може зламати похідні. Поширена порада: **віддавайте перевагу композиції** («має») перед успадкуванням («є») і вживайте успадкування, коли відношення «є» **справжнє** й стабільне.

```csharp
// успадкування: «Stack Є List»... тоді будь-хто може вставити в середину стека
class Stack : List<int> { }

// композиція: Stack МАЄ список і показує лише операції стека
class Stack
{
    private readonly List<int> items = new List<int>();
    public void Push(int x) { items.Add(x); }
    public int Pop() { int x = items[items.Count - 1]; items.RemoveAt(items.Count - 1); return x; }
}
```

Друга версія дає класові **контроль** над власним інтерфейсом, а це ідея абстракції та інкапсуляції разом.

## Малі інтерфейси

Добрий інтерфейс — **малий**: один-два члени. `IComparable<T>` має один метод. «Товстий» інтерфейс із двадцятьма методами змушує тих, хто реалізує, писати те, чого вони не потребують. Якщо ви бачите такий інтерфейс, **розділіть** його на кілька, кожен з однією роллю. Це принцип «розділення інтерфейсів».

## Короткий путівник

1. Потрібен лише **контракт** або **роль**: **інтерфейс**.
2. Потрібен контракт **і** спільний код або дані для **родини** типів: **абстрактний клас** (і, можливо, інтерфейс спереду).
3. Не впевнені: почніть з **інтерфейсу**. Додати абстрактний помічник пізніше легше, ніж прибрати зв'язок успадкування.
