Лінійний пошук — O(n), а двійковий — O(log n). На папері це вирішує суперечку. На практиці варто знати, **наскільки велика** різниця, **коли** вона з'являється і як чесно її виміряти.

## Кількості кроків

Для одного успішного пошуку в найгіршому випадку:

| n | Лінійний пошук | Двійковий пошук | Співвідношення |
| --- | --- | --- | --- |
| 10 | 10 | 4 | 2.5× |
| 100 | 100 | 7 | 14× |
| 1 000 | 1 000 | 10 | 100× |
| 1 000 000 | 1 000 000 | 20 | 50 000× |
| 1 000 000 000 | 1 000 000 000 | 30 | 33 000 000× |

Розрив росте разом з `n`. На мільйоні елементів один лінійний пошук виконує приблизно стільки роботи, як 50 000 двійкових.

## Не лише пошук: додайте сортування

Двійковому пошуку потрібні відсортовані дані. Припустімо, дані **не** відсортовані, а у вас `k` запитів. Порівняйте:

- **Лінійні пошуки**: `k` запитів, кожен щонайбільше `n` кроків: близько **k · n**.
- **Сортування, потім двійкові пошуки**: **n · log n** на сортування, потім **k · log n**: близько **(n + k) · log n**.

Для `n = 1 000 000`:

| k (кількість запитів) | Лінійно: k · n | Сортування + двійковий: (n + k) · 20 |
| --- | --- | --- |
| 1 | 10⁶ | близько 2 · 10⁷ (**гірше**) |
| 20 | 2 · 10⁷ | близько 2 · 10⁷ (рівно) |
| 1 000 | 10⁹ | близько 2 · 10⁷ (**у 50 разів краще**) |
| 1 000 000 | 10¹² | близько 4 · 10⁷ (**у 25 000 разів краще**) |

**Точка беззбитковості** — приблизно `k ≈ log n`. Для одного пошуку сортування — марнотратство. Для тисячі — вигідна оборудка. Якщо дані вже відсортовані (прочитані з бази даних з індексом, підтримуються відсортованими під час вставки), ви взагалі не платите за сортування.

## Третій варіант: хеш-таблиця

`Dictionary` чи `HashSet` відповідає на «чи воно є?» за **O(1)** у середньому, а побудова з даних коштує O(n):

| Метод | Підготовка | Один запит |
| --- | --- | --- |
| Лінійний пошук | немає | O(n) |
| Двійковий пошук | сортування, O(n log n) | O(log n) |
| `HashSet` | побудова, O(n) | O(1) у середньому |

Для простої перевірки належності `HashSet` зазвичай виграє. Але в двійкового пошуку лишаються застосування, яких немає в хеш-таблиці:

- він працює на **впорядкованих** даних: «перший елемент, не менший за x», «найближчий елемент», «скільки їх між a і b» (**межі** у практичних завданнях цього модуля);
- він не потребує додаткової пам'яті, коли масив уже є;
- він дає детермінований найгірший випадок без колізій хешів.

## Чесне вимірювання

Підрахунок порівнянь точний і однаковий на кожному комп'ютері. Іноді хочеться й справжнього часу. У .NET користуйтеся `Stopwatch`:

```csharp
using System.Diagnostics;

var data = new int[1_000_000];
for (int i = 0; i < data.Length; i++) data[i] = i * 2;     // відсортовано, усі парні

var timer = Stopwatch.StartNew();
int found = 0;
for (int x = 0; x < 1000; x++)                              // 1000 запитів
    if (Array.BinarySearch(data, x * 2) >= 0) found++;
timer.Stop();

Console.WriteLine(found + " found in " + timer.Elapsed.TotalMilliseconds + " ms");
```

(Роздільники розрядів на кшталт `1_000_000` потребують C# 7 або новішого.)

Бенчмарк, що каже правду, написати складніше, ніж здається:

- **Розігрійте.** Перший запуск включає час на JIT-компіляцію, завантаження бібліотек і заповнення кешів. Запустіть код один раз, перш ніж вмикати таймер.
- **Повторіть і візьміть медіану.** Одне вимірювання — шум. Запустіть багато разів і подивіться на серединне значення чи мінімум.
- **Використовуйте режим Release.** Збірка Debug вимикає оптимізації, і числа нічого не кажуть про справжню програму.
- **Не дайте роботі зникнути.** Якщо відкинути результат, розумний компілятор може прибрати все обчислення. Використайте результат: надрукуйте його або додайте до суми.
- **Міряйте те, що маєте на увазі.** Не включайте в час пошуку час побудови даних чи друку.
- **Порівнюйте подібне з подібним**: ті самі дані, той самий комп'ютер, нічого іншого не запущено.

Для серйозних вимірювань є бібліотека **BenchmarkDotNet**, яка робить розігрів, повторення та статистику за вас.

## Коли лінійний пошук виграє

Для малих `n` сталі важать. Цикл лінійного пошуку дуже простий і читає пам'ять по порядку, що процесор любить. Двійковий пошук стрибає масивом і на кожному кроці робить **важкопередбачуване розгалуження**. Для масивів до кількох десятків елементів лінійний перегляд часто такий самий швидкий, як двійковий пошук, або швидший, і не потребує сортування.

Тож правильне питання ніколи не звучить лише «в кого менше O?». Спитайте:

1. Яким є `n`?
2. Скільки буде пошуків?
3. Чи дані відсортовані, або їх можна дешево підтримувати відсортованими?
4. Чи дані змінюються? (Підтримання масиву відсортованим під вставками коштує O(n) щоразу.)

## Рахувати замість вимірювати час

Щоб порівнювати обидва в цьому курсі, ми **рахуємо кроки**. Результат не залежить від машини й точно відтворюваний, що пасує завданню, відповідь на яке перевіряють порівнянням виводу.

```csharp
static int LinearSteps(int[] a, int value)
{
    int steps = 0;
    for (int i = 0; i < a.Length; i++)
    {
        steps++;
        if (a[i] == value) break;
    }
    return steps;
}
```

Саме такі лічильники ви писали в практичному завданні «Рахуємо кроки» модуля про складність.

## Підсумок

- Двійковий пошук **астрономічно** швидший для великих відсортованих даних: 30 кроків проти мільярда.
- Сортування — інвестиція: воно окуповується приблизно після `log n` запитів.
- Хеш-таблиця часто краща для чистих перевірок належності, а двійковий пошук — для питань про **порядок**.
- Для крихітних масивів не турбуйтеся: простий цикл так само добрий.
- Міряйте чесно або рахуйте кроки.
