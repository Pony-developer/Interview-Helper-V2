Припустімо, у об'єкт потрапило погане значення, а програма продовжує, ніби нічого не сталося. Це **відкладена помилка**: помилку зроблено зараз, а помічають її пізніше.

```csharp
class Order
{
    public int Quantity;                           // публічне: перевірки немає
    public decimal PricePerItem;

    public decimal Total() { return Quantity * PricePerItem; }
}

var order = new Order { Quantity = -3, PricePerItem = 9.99m };     // одруківка: мінус
// ...сто рядків, інші методи, інший файл...
Console.WriteLine(order.Total());                  // -29.97: клієнт отримує «повернення коштів»
```

Помилку зроблено в рядку з `Quantity = -3`. Її **знаходять** у звіті, в рахунку або вона трапляється клієнтові, а траса стека (якщо вона є) вказує на **хибне** місце. Тепер треба відповісти на питання «хто записав від'ємне число?», а в програмі тисячі рядків.

## Ціна зростає з відстанню

Що далі симптом від причини, то дорожчий пошук:

- погане значення виявлено **в момент запису**: траса стека показує точний рядок із помилкою;
- значення збережено, використано в наступному обчисленні, записано у файл: помилка виявляється **десь в іншому місці**;
- погані дані **збережено в базі даних**, і вони живуть роками.

## Швидка відмова

Принцип захисного програмування — **fail fast** («падай швидко»): коли щось не так, **зупиняйтеся одразу**, голосно, **у тому місці, де це пішло не так**. Не «виправляйте» дані мовчки й не сподівайтеся, що хтось перевірить пізніше.

```csharp
public void SetQuantity(int quantity)
{
    if (quantity < 0)
    {
        throw new ArgumentOutOfRangeException("quantity", "The quantity cannot be negative");
    }
    this.quantity = quantity;
}
```

Тепер `SetQuantity(-3)` **кидає виняток прямо там**. Траса стека показує того, хто викликав і передав погане число. Замовлення не торкнуто (воно має колишню правильну кількість), бо перевірка йде **перед** присвоєнням.

## Який виняток кидати

| Ситуація | Виняток |
|---|---|
| Аргумент поганий загалом (порожній текст, `null`) | `ArgumentException`, `ArgumentNullException` |
| Число поза дозволеним діапазоном | `ArgumentOutOfRangeException` |
| Об'єкт у неправильному стані для цього виклику (порожній список, закритий файл) | `InvalidOperationException` |
| Зовсім не підтримується | `NotSupportedException` |

Перший параметр винятків аргументів — **назва параметра** (`nameof(quantity)` — безпечний спосіб це записати). Повідомлення каже програмістові, **що не так і що дозволено**.

## Спершу перевіряйте, потім змінюйте

Метод, що змінює об'єкт, мусить **спершу перевірити все**, і лише тоді щось змінювати. Інакше виняток може залишити об'єкт **наполовину зміненим**:

```csharp
public void Transfer(Account to, decimal amount)
{
    if (amount <= 0 || amount > balance) throw new ArgumentException("Bad amount");
    balance -= amount;                      // зміни починаються лише після всіх перевірок
    to.balance += amount;
}
```

## Мовчазне «виправлення» — теж відкладена помилка

```csharp
if (quantity < 0) quantity = 0;             // ховає помилку того, хто викликав
```

Це виглядає дружньо, але тепер програма працює з числом, якого ніхто не просив, а справжня помилка живе далі. Для **помилки програміста** віддавайте перевагу **винятку**. Для помилки, яку може зробити **користувач** (хибний текст у полі), повертайте результат на кшталт `false` від `TryParse` і доручіть інтерфейсові пояснити проблему.
