## Як працює lock (П134)

```csharp
lock (_sync) { _count++; }
// компілюється в:
bool taken = false;
try
{
    Monitor.Enter(_sync, ref taken);
    _count++;
}
finally
{
    if (taken) Monitor.Exit(_sync);
}
```

Кожен об'єкт у купі має слово заголовка. `Monitor.Enter` спершу пробує дешеве **тонке блокування (thin lock)**: записує id потоку-власника в заголовок через атомарне порівняння з обміном і коротко «крутиться» (spin) при конкуренції. Якщо конкуренція триває, блокування **роздувається** до **sync block** (запис у таблиці рантайму) з подією очікування ОС, і потоки, що чекають, блокуються. Блокування **реентерабельне** для потоку-власника. `Monitor.Wait/Pulse` дають умовні змінні. (У .NET 9 з'явився ще й окремий тип `System.Threading.Lock`.)

**Структури використати не можна**: `lock` потребує типу посилання. Структура при кожному `lock` упаковувалася б у *новий* об'єкт, тож кожен потік блокував би інший об'єкт і нічого б не було захищено — компілятор видає помилку. Блокуйте приватний `readonly object`, ніколи не `this`, `Type` чи рядок (інші можуть заблокувати той самий екземпляр). Ніколи не робіть `await` всередині `lock` (це заборонено); замість цього — `SemaphoreSlim.WaitAsync`.

## Дерева виразів (П135)

`Expression<Func<User, bool>> e = u => u.Age > 18;` змушує компілятор побудувати **структуру даних** — `LambdaExpression` з `BinaryExpression(GreaterThan, MemberExpression(u.Age), ConstantExpression(18))` — замість IL. З нею можна:
- **досліджувати / перекладати**: EF Core перетворює її на SQL, OData — на запити, драйвер MongoDB — на фільтри;
- **будувати** під час виконання через `Expression.Property`, `Expression.Lambda` (динамічні фільтри, мапери);
- **компілювати** через `.Compile()` у делегат, що працює з нативною швидкістю, — так замінюють повільну рефлексію (швидкі геттери/сетери властивостей, мапери об'єктів).

## GC у деталях; чому три покоління (П136)

- Виділення: локальний для потоку **контекст виділення** в Gen 0; виділення — це зсув вказівника.
- GC запускається через вичерпання бюджету Gen 0, `GC.Collect` або нестачу пам'яті. Керовані потоки призупиняються в **безпечних точках**.
- **Позначення** від коренів: стеки й регістри потоків (за GC-інформацією, яку генерує JIT), статичні поля, GC-дескриптори (зокрема закріплені), черга фіналізації. Для збирання Gen 0/1 посилання зі старших поколінь на молодші знаходять через **card table** (бар'єр запису позначає «картку», коли посилання записується в старий об'єкт), тож сканувати Gen 2 не треба.
- **Планування / переміщення / ущільнення** (або прибирання у списки вільних блоків, коли ущільнювати невигідно), оновлення посилань, **підвищення** вцілілих. Об'єкти з фіналізаторами переживають одне додаткове збирання: їх кладуть у f-reachable чергу, потік фіналізації виконує `Finalize`, і наступне збирання їх звільняє.
- Gen 2 у більшості конфігурацій збирається **фоново** (конкурентно). **Server GC** має по купі й потоку GC на кожне ядро (пропускна здатність); **workstation GC** надає перевагу затримці й пам'яті. Починаючи з .NET 7 купа організована в **регіони**. **LOH** (≥ 85 000 байтів) і **POH** (купа закріплених об'єктів, .NET 5) збираються разом із Gen 2.

**Чому три?** Це емпіричний інженерний компроміс, що спирається на поколіннєву гіпотезу: більшість об'єктів помирає дуже молодими (Gen 0, збирається часто й дешево), частина живе протягом однієї операції, наприклад запиту (Gen 1 працює як **буфер**, щоб вони передчасно не потрапили в Gen 2), а решта — довгожителі (Gen 2, збирається рідко). Кожне додаткове покоління потребує власних бюджетів, сканування card table і копіювання під час підвищення, а користь швидко зменшується; з лише двома об'єкти середнього віку «протікали» б у дороге покоління. Інші рантайми обрали інакше (SGen у Mono має два покоління; збирачі JVM різняться), а це показує, що це рішення налаштування, а не закон. Саме таке міркування й перевіряє питання.

## Трасування, секрети, CI/CD, CORS (П137–140)

**Трасування Web API**: **OpenTelemetry** (`AddOpenTelemetry().WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation().AddSqlClientInstrumentation())`) експортує трейси в Jaeger, Zipkin, Grafana Tempo чи Azure Monitor / Application Insights. ASP.NET Core автоматично передає заголовок W3C `traceparent`; для власних span-ів — `ActivitySource`, структуроване логування (Serilog) з trace id у кожному рядку логу, метрики через `Meter`.

**Секрети**:
- Машини розробників: **User Secrets** (`dotnet user-secrets set "Db:Password" …`) зберігаються поза репозиторієм у профілі користувача й завантажуються в середовищі Development; або змінні середовища / локальний `.env`, що ігнорується git.
- Продакшн: **Azure Key Vault** (`builder.Configuration.AddAzureKeyVault(uri, new DefaultAzureCredential())`) з доступом через **managed identity** — жодних облікових даних у конфігурації взагалі; секрети Kubernetes (бажано синхронізовані зі сховища); змінні середовища, які впроваджує платформа. Ніколи не комітьте секрети; ротуйте їх; надавайте перевагу доступу на основі ідентичності (managed identity до SQL, Storage, Service Bus) замість рядків підключення.

**CI/CD для .NET-сервісів у хмарі**: на кожен pull request — `dotnet restore`, `build`, модульні + інтеграційні тести (Testcontainers), аналіз коду, сканування залежностей на вразливості; після злиття — один раз зібрати Docker-образ (multi-stage), позначити його SHA коміту, запушити в реєстр (ACR); розгортати **той самий артефакт** через середовища (dev → staging → prod) з інфраструктурою як кодом (Bicep/Terraform), міграціями БД окремим кроком (EF migration bundles), затвердженнями/гейтами, health check-ами та безпечним викочуванням: blue-green чи canary (deployment slots в App Service, rolling updates в AKS), автоматичний відкат. Інструменти: GitHub Actions або Azure DevOps Pipelines; секрети з Key Vault / федеративні облікові дані OIDC замість збережених ключів.

**CORS** дозволяє сторінці в браузері з іншого origin звертатися до вашого API.

```csharp
builder.Services.AddCors(o => o.AddPolicy("web", p => p
    .WithOrigins("https://app.example.com")
    .AllowAnyHeader()
    .WithMethods("GET", "POST")
    .AllowCredentials()));
// …
app.UseRouting();
app.UseCors("web");      // після UseRouting, перед UseAuthorization
app.UseAuthorization();
```

Або для окремих кінцевих точок через `[EnableCors("web")]` / `.RequireCors("web")`. Не поєднуйте `AllowAnyOrigin()` з передаванням облікових даних (credentials). CORS забезпечують браузери; це не межа безпеки на боці сервера.

## Generics, незмінність, IEnumerable, Stack (П141–144)

**Generics** — це можливість CLR, а не лише компілятора: метадані зберігають узагальнене визначення, а JIT створює конкретизації на вимогу — **окремий нативний код для кожного типу значення** (без упакування, повна спеціалізація), **спільний код для всіх типів посилань** (`__Canon`) із пошуком точного типу під час виконання, коли треба (наприклад, `typeof(T)`, `new T()`). Обмеження (`where T : struct, IComparable<T>`) перевіряють і компілятор, і рантайм. Статичні поля — свої для кожного закритого типу: `Cache<int>.Value` і `Cache<string>.Value` різні.

**Незмінний тип**: `public sealed record Money(decimal Amount, string Currency);` або клас із полями `readonly` / властивостями лише з `init`, валідацією в конструкторі, без сетерів, з `IReadOnlyList`/`ImmutableArray` для колекцій (і захисними копіями вхідних масивів), рівністю за значенням, методами `With…`, що повертають нові екземпляри. `readonly struct` — для малих значень. Запечатайте клас (`sealed`), щоб нащадок не додав змінного стану.

**`IEnumerable<T>` у деталях**: `GetEnumerator()` повертає `IEnumerator<T>` з `MoveNext()`, `Current` і `Dispose()`. `foreach` компілюється в цикл у `try/finally`, що їх викликає (і використовує структурний енумератор через duck typing, коли він є, наприклад `List<T>.Enumerator`, уникаючи виділень). Методи-ітератори (`yield`) компілюються в клас, що є водночас і enumerable, і енумератором, з полем стану; `GetEnumerator` уперше повертає себе (якщо той самий потік), інакше — копію. Енумератор `List<T>` перевіряє поле `version` і кидає `InvalidOperationException`, якщо список змінили під час перебору. `Dispose` виконує блоки `finally` всередині ітераторів, коли ви робите `break` раніше.

**`Stack<T>`** — це масив із вказівником `size`: `Push` пише в `array[size++]` і подвоює масив, коли той заповнився (амортизовано O(1)); `Pop` читає `array[--size]` і очищає слот для GC (O(1)); `Peek` — O(1). LIFO. `Queue<T>` — кільцевий буфер на масиві з головою та хвостом.

## Власні структури даних, інтерфейс + абстрактний клас, конструктори структур (П145–147)

Типові приклади, які варто згадати: LRU-кеш (словник + зв'язний список), префіксне дерево (trie) для автодоповнення, кільцевий буфер для метрик, черга з пріоритетом до появи `PriorityQueue` у .NET 6, неблокуюча чи обмежена черга, фільтр Блума, дерево інтервалів. Поясніть, чому стандартна не підходила (виділення пам'яті, потокобезпечність, політика витіснення, розкладка в пам'яті), і як ви її тестували.

**Інтерфейс + абстрактний клас разом**: інтерфейс — публічний контракт (`IRepository<T>`, легко мокати й реалізовувати інакше), а абстрактний базовий клас дає спільну «обв'язку» (`RepositoryBase<T>` зі спільним CRUD, шаблонні методи). Споживачі залежать від інтерфейсу; реалізації успадковують базу для зручності, але не зобов'язані. BCL робить так само: `IList<T>` + `Collection<T>`, `IComparer<T>` + `Comparer<T>`, `Stream` + абстрактні члени.

**Конструктори структур за замовчуванням**: структура завжди має неявну «нульову» ініціалізацію: `default(T)`, `new T[100]`, поля класів і неприсвоєні поля структур створюються обнуленням пам'яті **без виклику будь-якого конструктора** — саме це робить масиви структур дешевими. Тож власний конструктор без параметрів виконувався б лише іноді (для `new S()`, але не для елементів масиву чи `default`), а це заплутує, тому C# забороняв його до **C# 10**. Тепер його можна оголосити (і ініціалізатори полів), але `default(S)` та елементи масивів усе одно його пропускають. Проєктуйте структури так, щоб повністю нульове значення було коректним.
