## Як база даних зберігає дані (П148)

Візьмімо SQL Server (PostgreSQL за духом схожий):
- Файли даних поділені на **сторінки по 8 КБ**, згруповані в **екстенти по 64 КБ**. Сторінка має заголовок, рядки й масив слотів, що вказують на рядки.
- Таблиця з кластерним індексом — це **B+-дерево**: кореневі й проміжні сторінки містять ключі та вказівники, **листові сторінки містять рядки** в порядку ключа. Без кластерного індексу це **купа (heap)** (невпорядковані сторінки, рядки знаходять за RID). Некластерні індекси — окремі B+-дерева, листки яких указують на кластерний ключ.
- Великі значення (`varchar(max)`, `varbinary(max)`) потрапляють на сторінки переповнення / LOB. Columnstore-індекси зберігають дані за колонками в стиснутих сегментах.
- Сторінки зчитуються в **буферний пул** (RAM); зміни робляться в пам'яті й записуються в **журнал транзакцій** (write-ahead logging); «брудні» сторінки пізніше пишуться на диск контрольними точками та lazy writer-ом.
- PostgreSQL зберігає таблиці як купи сторінок по 8 КБ; MVCC тримає кілька **версій рядка** в самій таблиці (їх прибирає `VACUUM`), а WAL забезпечує довговічність.

## Види баз даних і коли яку використовувати (П149–150)

| Вид | Приклади | Для чого добрі |
|---|---|---|
| Реляційні (OLTP) | SQL Server, PostgreSQL, MySQL | бізнес-дані, транзакції, цілісність, довільні запити — вибір за замовчуванням |
| Документні | MongoDB, Cosmos DB | агрегати, що читаються/пишуться цілком, гнучка схема, каталоги, профілі користувачів |
| Ключ-значення / кеш | Redis, Memcached | кешування, сесії, обмеження частоти запитів, розподілені блокування, рейтинги |
| Колонкові (wide-column) | Cassandra, ScyllaDB | величезні обсяги записів, часові ряди, відомі шаблони запитів, кілька регіонів |
| Пошукові | Elasticsearch, OpenSearch, Azure AI Search | повнотекстовий пошук, фасети, аналітика логів |
| Графові | Neo4j, Cosmos DB Gremlin | запити з великою кількістю зв'язків: соцграфи, рекомендації, шахрайство |
| Часових рядів | InfluxDB, TimescaleDB | метрики, IoT |
| Колонкові / OLAP | ClickHouse, Snowflake, Synapse | аналітика над великими наборами даних |

Обирайте за **шаблонами доступу**, вимогами до узгодженості, масштабом і досвідом команди. «Поліглотне зберігання»: реляційна система обліку плюс Redis для кешу й пошуковий індекс — звична комбінація. Починайте з PostgreSQL/SQL Server, якщо немає конкретної причини інакше.

## Денормалізація та рівні ізоляції на практиці (П151–152)

**Денормалізація** свідомо додає надлишковість, щоб пришвидшити читання: `CustomerName` у замовленнях для звітів, попередньо обчислені суми й лічильники, матеріалізовані/індексовані подання, read-моделі в CQRS, вбудовані документи в NoSQL. Ціна: більше місця й синхронізація копій (тригери, код застосунку, події) — тож робіть це на виміряних «гарячих» точках читання.

Вибір рівня ізоляції:
- **Read Committed** (за замовчуванням): більшість OLTP-роботи. З **RCSI/Snapshot** у SQL Server читачі не блокують записувачів.
- **Repeatable Read / Serializable**: коли транзакція читає дані й потім ухвалює рішення на їхній основі (перевір-потім-дій, наприклад «забронювати місце, якщо вільне»), або фінансові інваріанти між рядками. Очікуйте більше блокувань чи помилок серіалізації — повторюйте такі транзакції.
- **Snapshot**: узгоджені звіти за станом на момент часу без блокування записувачів; стережіться **write skew** і конфліктів оновлення.
- **Read Uncommitted / NOLOCK**: лише для приблизних моніторингових запитів, де хибні чи продубльовані рядки прийнятні.

Часто краще за підвищення рівня: атомарні умовні оновлення, `UPDLOCK`/`SELECT … FOR UPDATE` на рядках, які змінюватимете, або оптимістична конкурентність із колонкою `rowversion` (EF Core `[Timestamp]` → `DbUpdateConcurrencyException`).

## Як СУБД реалізують ACID (П153)

- **Атомарність і довговічність**: **журнал попереднього запису (WAL)**. Кожна зміна записується в журнал раніше, ніж сторінка даних; на `COMMIT` записи журналу скидаються на диск (це точка довговічності). Після збою відновлення **повторює** закомічені зміни, яких ще немає у файлах даних, і **відкочує** незакомічені (у стилі ARIES у SQL Server; відтворення WAL у PostgreSQL).
- **Ізольованість**: **блокування** (спільні/ексклюзивні/update-блокування, intent-блокування, key-range-блокування для Serializable) та/або **MVCC** — читачі бачать знімок закомічених версій рядків (PostgreSQL завжди; SQL Server — через сховище версій у tempdb з RCSI/Snapshot).
- **Узгодженість**: обмеження (PK, FK, UNIQUE, CHECK), тригери й гарантії вище; решта — відповідальність застосунку.

## Оптимізація запитів (П154)

Майте реальну історію: що було повільним (p95, як знайшли — Query Store, APM, slow log), що показав план, що ви змінили і виміряний результат. Типові виправлення: складений/покривний індекс під `WHERE` + `ORDER BY`; переписування несаргабельних умов; прибирання N+1 запитів (EF `Include`, проєкції через `Select`, split queries); keyset-пагінація замість `OFFSET` на великих таблицях; пакетні записи; виправлення parameter sniffing; оновлення статистики; архівування чи партиціювання великих таблиць; кешування результатів; перенесення звітів на репліку для читання.

## Проблеми конкурентності й розподілені блокування (П155–156)

Проблеми конкурентних запитів: **втрачені оновлення** (два цикли «прочитати-змінити-записати» перезаписують одне одного), **брудне / неповторюване / фантомне читання**, **write skew**, **взаємні блокування** (дві транзакції блокують ресурси в протилежному порядку — база вбиває одну; лікується однаковим порядком, коротшими транзакціями, правильними індексами), **ланцюжки блокувань** і **ескалація блокувань**, вичерпання пулу з'єднань, «гарячі» рядки (один рядок-лічильник, який оновлюють усі).

**Розподілене блокування** (лише один екземпляр виконує задачу / обробляє сутність одночасно):
- **Redis**: `SET lock:invoice:42 <унікальний-токен> NX PX 30000` — встановити лише якщо ключа немає, з терміном дії, щоб упалий власник не тримав його вічно. Звільняти Lua-скриптом, що видаляє ключ, **лише якщо значення досі дорівнює вашому токену**. Продовжувати TTL під час роботи (watchdog). Для кількох вузлів Redis Redlock дискусійний; для коректності додавайте **fencing-токен** (монотонно зростаюче число, яке ресурс перевіряє під час запису), бо призупинений процес може «прокинутися» вже після того, як його блокування спливло.
- **SQL Server**: `sp_getapplock @Resource = 'invoice:42', @LockMode = 'Exclusive', @LockOwner = 'Session'`; **PostgreSQL**: `pg_try_advisory_lock(42)`. Просто й коректно, якщо база вже є; прив'язано до часу життя з'єднання/транзакції.
- **ZooKeeper / etcd / Consul**: блокування на основі консенсусу із сесіями та ефемерними вузлами — найсильніші гарантії.
- Azure: **оренда blob** (`BlobLeaseClient`, 15–60 с або безстрокова).

Бібліотеки: `DistributedLock` (Medallion) підтримує SQL Server, Postgres, Redis, Azure blobs.
