## Що розв'язують мікросервіси і як вони спілкуються (П157–158)

Мікросервіси ділять систему на сервіси, що **розгортаються** незалежно, навколо бізнес-можливостей, і кожен володіє своїми даними. Вони розв'язують **організаційне масштабування** (команди випускають незалежно, менше конфліктів злиття й релізів), **незалежне масштабування** «гарячих» частин, **ізоляцію збоїв** і свободу технологій для кожного сервісу. Ціна: складність розподілених систем (збої мережі, кінцева узгодженість, версіоновані контракти, спостережуваність, зрілість DevOps). Добре структурований **модульний моноліт** часто кращий старт.

Спілкування:
- **Синхронне**: REST/HTTP (JSON), **gRPC** (HTTP/2, Protobuf, швидкий, потоковий; чудовий між сервісами), GraphQL (переважно для клієнтів/BFF). Просто, але зчіплює доступність і затримки.
- **Асинхронне**: повідомлення й події через брокер — команди в чергу (RabbitMQ, черги Azure Service Bus), події через publish/subscribe (топіки, Kafka). Розв'язує в часі, поглинає піки навантаження, але потребує ідемпотентності й кінцевої узгодженості.
- Патерни: API Gateway / BFF (YARP, Azure API Management), виявлення сервісів, service mesh (mTLS, повтори, трасування через sidecar-и — Istio, Linkerd, Dapr).

## Розподілені транзакції (П159)

- **Двофазний коміт (2PC/XA)**: координатор просить усіх учасників підготуватися, а потім закомітити. Сильна узгодженість, але блокує, повільний, координатор — єдина точка відмови, і більшість хмарних брокерів/NoSQL-сховищ його не підтримують.
- **Сага**: послідовність локальних транзакцій, кожна публікує подію чи команду; якщо крок не вдається, **компенсувальні транзакції** скасовують попередні кроки (повернути платіж, звільнити товар на складі). **Хореографія**: сервіси реагують на події один одного (немає центрального «мозку», важче простежити). **Оркестрація**: оркестратор саги (скінченний автомат: MassTransit, NServiceBus, Durable Functions, Temporal) каже кожному сервісу, що робити — легше міркувати й моніторити.
- Допоміжні патерни: **transactional outbox / inbox**, ідемпотентні споживачі, **TCC** (try-confirm-cancel: зарезервувати, потім підтвердити), семантичні блокування (статус «Pending») і прийняття **кінцевої узгодженості** в UX.

## Circuit breaker, трасування (П160–161)

**Circuit breaker** обгортає виклики до залежності. **Замкнений**: виклики проходять; збої рахуються. Коли збоїв більше за поріг, він **розмикається**: виклики одразу падають (або повертають запасне значення) протягом паузи, що дає залежності час відновитися й не дає потокам накопичуватися. Потім **напіввідкритий**: проходить пробний виклик; успіх замикає ланцюг, збій знову розмикає. У .NET: **Polly** / `Microsoft.Extensions.Http.Resilience` (`AddStandardResilienceHandler()` = тайм-аут + повтори з jitter + circuit breaker). Поєднуйте з тайм-аутами, bulkhead-ами й повторами — і ніколи не повторюйте сліпо неідемпотентні виклики.

**Простежити запит через багато сервісів**: розподілене трасування з **OpenTelemetry**. Точка входу починає **trace** (trace id); кожен сервіс створює **span-и** й передає контекст у заголовку W3C `traceparent` (HTTP) або в заголовках повідомлень (брокери — MassTransit/Azure SDK роблять це самі). Експортуйте в Jaeger, Zipkin, Tempo чи Application Insights, щоб бачити все дерево викликів із часами. Пов'язуйте **логи** (trace id у кожному структурованому рядку логу, централізовано в Seq/ELK/Log Analytics) і **метрики** (RED: rate, errors, duration). Локально дашборд .NET Aspire одразу показує трейси між сервісами.

## Брокери й семантика доставки (П162–164)

**Брокер повідомлень** приймає, зберігає й маршрутизує повідомлення між продюсерами й споживачами: черги (точка-точка), топіки/exchange-і (pub/sub), збереження, підтвердження, повтори, dead-letter-черги.

- **At-most-once** (щонайбільше раз): повідомлення підтверджується (чи автозавершується) **до** обробки. Падіння губить його; дублікатів не буває. Годиться для метрик чи телеметрії.
- **At-least-once** (щонайменше раз): підтвердження **після** обробки. Падіння → повторна доставка → **дублікати**. Стандарт для бізнес-даних; споживачі мусять бути **ідемпотентними** (таблиця inbox / оброблені id, upsert, природні ключі) і витримувати зміну порядку.
- **Exactly-once** (рівно раз): у загальному випадку від початку до кінця неможливо в ненадійній мережі; існує *фактично один раз* = доставка at-least-once + ідемпотентна обробка. Kafka пропонує ідемпотентних продюсерів і транзакції для exactly-once **у межах Kafka** (consume-transform-produce); Azure Service Bus має виявлення дублікатів за `MessageId` у часовому вікні; побічні ефекти поза брокером (БД, листи) усе одно потребують ідемпотентності.

Поведінка клієнта залежно від семантики: для at-least-once — обробити, зберегти, **потім** завершити/підтвердити; робити обробники ідемпотентними; використовувати outbox під час публікації; обробляти «отруйні» повідомлення (максимальна кількість доставок → dead-letter-черга, алерт, інструменти повторного відтворення); продовжувати блокування для довгої обробки; свідомо налаштовувати prefetch і паралелізм. Для at-most-once — спершу підтвердити, прийняти можливі втрати, тримати обробку дешевою.

Інструменти: **RabbitMQ** (гнучка маршрутизація, класичні робочі черги), **Azure Service Bus** (керований корпоративний брокер: сесії/FIFO, транзакції, відкладені повідомлення, dead-lettering, виявлення дублікатів), **Kafka** / Azure Event Hubs (високопродуктивні потоки подій, повторне читання за offset, партиції), Amazon SQS/SNS, Redis Streams, NATS; у межах процесу: `System.Threading.Channels`, `BlockingCollection`. Абстракції .NET: **MassTransit**, NServiceBus, Wolverine, Rebus. Обирайте за потребами: команди й процеси в Azure → Service Bus (+ MassTransit); потоки подій із повторним читанням і величезними обсягами → Kafka/Event Hubs; власний хостинг і гнучка маршрутизація → RabbitMQ.

## Azure (П165–168)

Види сервісів **Service Fabric**: **stateless**-сервіси (як будь-який веб-API/воркер), **stateful** reliable services (стан у реплікованих `IReliableDictionary`/`IReliableQueue` поруч із кодом, партиційований і реплікований між вузлами), **Reliable Actors** (модель віртуальних акторів, однопотоковість у межах актора), **guest executables** і **контейнери**. Сьогодні більшість нових проєктів натомість використовують AKS або Container Apps.

**Azure Table Storage** (і Table API у Cosmos DB): дешеве, масштабоване NoSQL-сховище «ключ-атрибути». Кожна сутність має **PartitionKey + RowKey** (єдиний індекс, разом унікальні) і до 252 властивостей. Обмеження: ефективні запити лише за PartitionKey/RowKey (інші фільтри сканують партицію чи таблицю), немає вторинних індексів, з'єднань і агрегацій, сутність ≤ 1 МБ, **пакетні транзакції (entity group) лише в межах однієї партиції, до 100 операцій**, пагінація через continuation token-и, обмеження пропускної здатності партиції (проєктуйте ключі, щоб уникати «гарячих» партицій). Чудово для логів, телеметрії, простих пошуків за ключем.

**Холодний старт Azure Functions**: у плані **Consumption** неактивний застосунок вивантажується, тож перший запит чекає, поки хост запуститься й завантажить ваш код (секунди). Пом'якшення: план **Premium (Elastic Premium)** з постійно готовими й прогрітими екземплярами; **Flex Consumption** з постійно готовими екземплярами; **Dedicated**-план (App Service) з *Always On*; невеликий пакет і залежності, run from package, без важкої статичної ініціалізації, isolated worker з ReadyToRun; як обхідний шлях — тригер за таймером, що тримає застосунок «теплим».

**Черги й топіки Azure Service Bus**: **черга** — точка-точка: кожне повідомлення отримує **один** із конкурентних споживачів (розподіл роботи). **Топік** — publish/subscribe: кожна **підписка** отримує власну копію кожного повідомлення (за потреби з фільтрами SQL/correlation), і кожна підписка поводиться як черга зі своїми конкурентними споживачами. Черги — для команд («ProcessPayment»), топіки — для подій («OrderPlaced»), які споживають кілька сервісів. Топіки потребують рівня Standard або вище.
