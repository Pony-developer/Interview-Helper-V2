Список Middle містить кілька фрагментів типу «чи спрацює?» і «що тут не так?». Квіз після цієї лекції перевіряє кожен із них.

## 1. Виклик методу на null

```csharp
SomeClass myClass = null;
myClass.SomeMethod();
```

Зазвичай — `NullReferenceException`. **Але** якщо `SomeMethod` — **метод розширення** (`static void SomeMethod(this SomeClass c)`), виклик компілюється в `Extensions.SomeMethod(myClass)` — статичний виклик, що отримує `null` як аргумент, і працює, якщо метод обробляє null. У цьому й підступ — на цьому тримаються помічники на кшталт `string.IsNullOrEmpty`. (Виклик методу екземпляра на null завжди кидає виняток, навіть якщо метод не використовує `this`: C# генерує `callvirt`, який перевіряє null.)

## 2. Повернення звільненого об'єкта

```csharp
SomeClass GetTable()
{
    using (var table = new SomeClass())
    {
        return table;
    }
}

var table = GetTable();
table.Draw();   // ObjectDisposedException або гірше: тихо зламаний стан
```

`using` викликає `Dispose()`, коли керування виходить із блоку — зокрема через `return`. Викликач отримує вже звільнений об'єкт. Виправлення: не звільняйте те, що повертаєте; ним володіє **викликач** і обгортає його в `using`.

## 3. `is`, а потім приведення

```csharp
if (shape is Circle)
    Console.WriteLine(((Circle)shape).Radius);
```

Дві перевірки типу (`is`, потім приведення). Використайте зіставлення зі зразком — одна перевірка й типізована змінна: `if (shape is Circle c) Console.WriteLine(c.Radius);`. Ще краще: якщо кожна фігура має що надрукувати, зробіть це віртуальним членом і уникайте перевірок типу (поліморфізм), або для закритих ієрархій використовуйте `switch` за типами.

## 4. Винятки для керування потоком виконання

```csharp
public int Quantity
{
    get
    {
        try { return int.Parse(TxtQuantity.Text); }
        catch { return 0; }
    }
}
```

- Винятки дорогі й призначені для виняткових ситуацій; некоректний ввід користувача — очікуваний. Використайте `int.TryParse(TxtQuantity.Text, out var q) ? q : 0`.
- Голий `catch` поглинає все, зокрема справжні баги.
- Мовчки повертаючи 0, ви ховаєте проблему від користувача: валідуйте ввід в UI й показуйте помилку.
- Геттер властивості, що звертається до UI-контролів і розбирає текст, змішує шари; розбирайте один раз у view model / на кроці валідації.

## 5. Повторний кидок

```csharp
try { SomeMethod(); }
catch (Exception e)
{
    Log(e.Message);
    throw e;
}
```

- `throw e;` **скидає стек викликів** до цього рядка, і ви втрачаєте місце, де насправді сталася помилка. Використовуйте `throw;`. Щоб додати контекст, обгорніть: `throw new OrderException("…", e);` (зберігає внутрішній виняток).
- Логування лише `e.Message` губить тип і стек: логуйте об'єкт винятку (`logger.LogError(e, "…")`).
- Логуйте **або** перекидайте, а не те й інше на кожному рівні, інакше та сама помилка потрапить у лог багато разів.
- Перехоплювати `Exception` доречно лише на межі (обробник верхнього рівня, middleware) або якщо ви кидаєте далі.
