## Завдання

Питання 155: «Які проблеми можуть спричинити конкурентні запити до бази?» Класичний випадок: кілька воркерів беруть задачі з таблиці. З наївним «`SELECT` першої задачі в черзі, потім `UPDATE`» два воркери можуть узяти ту саму задачу. Розв'язок — забирати задачу **однією інструкцією**, що блокує рядок і змушує інших воркерів **пропускати** заблоковані рядки замість очікування.

Скрипт підготовки створює таблицю `jobs`. Напишіть чотири інструкції:

1. Воркер **`w1`** забирає задачу з черги з найвищим `priority` (за рівності — з меншим `id`): `status = 'running'`, `worker = 'w1'`, поверніть `id, name, worker`. Використайте підзапит з `ORDER BY priority DESC, id LIMIT 1 FOR UPDATE SKIP LOCKED` усередині `UPDATE … WHERE id = (…)` і `RETURNING`.
2. Воркер **`w2`** забирає наступну задачу так само.
3. `w1` завершує: встановіть `status = 'done'` для його задачі в роботі й поверніть `id, status`.
4. Покажіть фінальний стан: `SELECT id, name, status, worker FROM jobs ORDER BY id`.

Зверніть увагу: задача 3 уже виконується (іншим воркером), а задача 5 завершена — їх не можна забирати.

Очікуваний результат:

----+---------------+--------

(1 row)

 id | status
----+--------
  4 | done

 id |      name       | status  | worker
----+-----------------+---------+--------
  1 | send-newsletter | queued  | NULL

  4 | charge-cards    | done    | w1
  5 | cleanup-temp    | done    | w1
