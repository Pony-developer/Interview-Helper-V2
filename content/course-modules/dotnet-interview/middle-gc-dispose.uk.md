## Спостерігаємо за роботою GC (П79–80)

```csharp
Console.WriteLine(GC.CollectionCount(0));      // скільки збирань Gen 0 уже було
var small = new byte[100];
Console.WriteLine(GC.GetGeneration(small));    // 0: нові об'єкти стартують у Gen 0
GC.Collect();
Console.WriteLine(GC.GetGeneration(small));    // 1: він вижив, тож його підвищено
var big = new byte[100_000];
Console.WriteLine(GC.GetGeneration(big));      // 2: великі об'єкти йдуть у LOH, що звітується як Gen 2
```

Що робить GC за одне збирання:
1. **Призупиняє** керовані потоки в безпечних точках.
2. **Позначає**: обходить посилання від коренів — локальні змінні й аргументи в кадрах стеку й регістрах кожного потоку, статичні поля, GC-дескриптори (зокрема закріплені), черга фіналізації.
3. **Планує, переміщує й ущільнює** вцілілі об'єкти (або просто прибирає мертві у списки вільних блоків) і виправляє кожне посилання.
4. **Підвищує** вцілілих: Gen 0 → Gen 1 → Gen 2.
5. **Відновлює** потоки; об'єкти, що потребують фіналізації, стають у чергу потоку фіналізації.

Чому це швидко для молодих об'єктів: більшість об'єктів помирає до наступного збирання Gen 0, а збирання Gen 0 переглядає лише невелику молоду область (посилання старі→молоді відстежуються бар'єром запису та card table).

Варто знати налаштування: `<ServerGarbageCollector>` (купа на кожне ядро — пропускна здатність, за замовчуванням в ASP.NET Core), `<ConcurrentGarbageCollection>` (фоновий Gen 2), `GCSettings.LatencyMode`, `<GCHeapHardLimit>` і DATAS (динамічне підлаштування під пам'ять контейнера).

## Фіналізатори

```csharp
class Holder
{
    private IntPtr _handle = Native.Open();
    ~Holder() => Native.Close(_handle);   // компілюється в перевизначення Object.Finalize
}
```

- Об'єкт із фіналізатором реєструється під час виділення. Коли він стає недосяжним, його не звільняють: він переходить у f-reachable чергу, **єдиний потік фіналізації** викликає `Finalize`, і лише *наступне* збирання його звільняє — тож він підвищується й живе довше.
- Порядок і час не гарантовані; інші фіналізовані об'єкти, на які ви посилаєтеся, можуть уже бути фіналізовані; виняток у фіналізаторі обвалює процес.
- На практиці ви майже ніколи його не пишете: обгортайте дескриптори ОС у `SafeHandle` (має надійний фіналізатор) і реалізуйте лише `IDisposable`.

## Патерн Dispose (П81)

```csharp
public class Resource : IDisposable
{
    private SafeFileHandle? _file;        // володіє некерованим станом (через SafeHandle)
    private readonly Stream _log;         // володіє керованим disposable
    private bool _disposed;

    public void Dispose()
    {
        Dispose(disposing: true);
        GC.SuppressFinalize(this);        // фіналізатор більше не потрібен
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;            // ідемпотентність: Dispose можна викликати багато разів
        if (disposing)
        {
            _log.Dispose();               // керовані об'єкти: лише під час виклику з Dispose()
            _file?.Dispose();
        }
        // сирі некеровані ресурси (якщо є) звільняються тут, на обох шляхах
        _disposed = true;
    }

    protected void ThrowIfDisposed() => ObjectDisposedException.ThrowIf(_disposed, this);
    // ~Resource() => Dispose(false);     // лише якщо клас тримає СИРІ некеровані дескриптори
}
```

Навіщо прапорець `disposing`: під час виклику з `Dispose()` безпечно чіпати інші керовані об'єкти; із фіналізатора — ні (вони вже можуть бути фіналізовані або частково зібрані), тож звільняти можна лише сирі некеровані дескриптори. Похідні класи перевизначають `Dispose(bool)` і наприкінці викликають `base.Dispose(disposing)`. Для асинхронного звільнення реалізуйте `IAsyncDisposable` і використовуйте `await using`.

`using` — це просто синтаксис для `try { … } finally { x?.Dispose(); }`; форма оголошення `using var x = …;` звільняє в кінці охопної області видимості.

## Large Object Heap (П82)

- Об'єкти ≥ **85 000 байтів** (на практиці великі масиви: `byte[]`, `char[]` за величезними рядками, внутрішні масиви `List<T>` із багатьма елементами).
- Виділяються одразу в LOH, збираються лише з Gen 2, **за замовчуванням не ущільнюються** → фрагментація й зростання пам'яті.
- Виділення в LOH дорожче (пам'ять треба обнулити) і може запускати збирання Gen 2.
- Засоби: перевикористовувати буфери (`ArrayPool<T>.Shared`, `RecyclableMemoryStream`), читати дані потоково замість завантаження цілих файлів, задавати розмір списків наперед, щоб уникнути повторного подвоєння великих масивів, обробляти частинами, а за потреби — встановити `GCSettings.LargeObjectHeapCompactionMode = CompactOnce` перед примусовим збиранням.
