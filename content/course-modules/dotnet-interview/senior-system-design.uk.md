Співбесіди Senior майже завжди містять відкрите питання на проєктування. Єдиної правильної відповіді немає: інтерв'юер стежить, як ви уточнюєте вимоги, шукаєте компроміси й заглиблюєтеся там, де це важливо.

## Схема для будь-якого питання на проєктування

1. **Уточніть вимоги**: функціональні (що роблять користувачі) і нефункціональні (кількість користувачів, запитів на секунду, обсяг даних, затримка, доступність, узгодженість, безпека, бюджет). Запишіть цифри.
2. **Оцініть**: обсяг сховища на рік, піковий RPS, пропускну здатність. Це скаже, чи вистачить однієї бази.
3. **API й модель даних**: основні кінцеві точки/повідомлення й сутності.
4. **Архітектура верхнього рівня**: клієнти → CDN → балансувальник / API gateway → сервіси → бази даних, кеші, черги, об'єктне сховище.
5. **Заглиблення** в найскладнішу частину (часто її обирає інтерв'юер), потім **масштабування, збої й моніторинг**: що зламається першим, як ви це помітите, як відновитеся.

## Приклади з DOU коротко

- **FTP-сервер**: керувальне з'єднання (команди `USER`, `LIST`, `RETR`, `STOR`) і окремі з'єднання для даних (активний і пасивний режими); одна асинхронна задача на сесію (`TcpListener`, `Socket`, `PipeReader`), віртуальний корінь для кожного користувача проти обходу шляхів (`..`), потокова передача файлів замість завантаження цілком, обмеження на з'єднання й швидкість, TLS (FTPS).
- **Вебсервер**: цикл прийому з'єднань на сокеті, розбір HTTP-запитів (keep-alive, chunked encoding, обмеження заголовків), маршрутизація до обробників або статичних файлів, пул потоків / асинхронне I/O, тайм-аути проти повільних клієнтів, TLS, коректне завершення — по суті те, що робить Kestrel; згадайте конвеєр middleware.
- **Хостинг зображень із правами доступу**: завантаження через API → оригінали в **об'єктному сховищі** (Azure Blob / S3), метадані (власник, ACL, розмір, хеш) у базі; мініатюри генеруються **асинхронно** через чергу + воркер; роздача через **CDN**; контроль доступу через **короткоживучі підписані URL** (SAS-токени), перевірені за ACL (приватне, за посиланням, публічне, спільне з користувачами/групами); дедуплікація за хешем вмісту; антивірусна перевірка; квоти.
- **Front office + back office**: окремі застосунки (і часто окремі API/BFF) над спільним доменом: публічний сайт, оптимізований під масштаб і кешування, та внутрішня адмінка з ширшими правами (RBAC, журнал аудиту), різні периметри розгортання й безпеки (back office за SSO/VPN), взаємодія через доменні сервіси або події; read-модель для звітів back office.
- **Клон соцмережі (Instagram)**: користувачі, підписки, пости з медіа, стрічка, лайки, коментарі. Медіа в об'єктному сховищі + CDN. Заглиблення — **стрічка**: *fan-out on write* (покласти id поста в заздалегідь обчислену стрічку кожного підписника в Redis — швидке читання, дорого для знаменитостей) проти *fan-out on read* (зливати пости тих, на кого підписаний, під час читання), зазвичай гібрид. Лічильники — через асинхронну агрегацію; пошук — Elasticsearch; шардинг за id користувача.

## Лічильник партнерів у бідів

> Bid містить список партнерів. Біди живуть у сервісі торгів, партнери — в сервісі партнерів. Перший екран показує список бідів із кількістю партнерів у кожному. Як зберігати й показувати лічильник?

Варіанти:
1. **Викликати сервіс партнерів для кожного біда** під час рендерингу списку — N+1 віддалених викликів, повільно, і сторінка списку падає, коли сервіс партнерів недоступний. Відкидаємо.
2. **Пакетний виклик**: сервіс бідів один раз на сторінку питає `GET /partners/counts?bidIds=1,2,3`. Просто, завжди точно, але все одно зчіплює доступність і додає затримку; прийнятно для невеликого трафіку.
3. **Денормалізувати лічильник у сервіс торгів** (рекомендовано): сервіс партнерів публікує події `PartnerAddedToBid` / `PartnerRemovedFromBid` (через outbox); сервіс торгів споживає їх **ідемпотентно** й підтримує `PartnersCount` у біді (або локальну таблицю read-моделі `BidPartnerIds`, з якої лічильник виводиться, — тоді дублікати подій нешкідливі). Сторінці списку тоді потрібен один локальний запит. Компроміс: лічильник **кінцево узгоджений** (коротке відставання для екрана списку зазвичай прийнятне; сторінка деталей може показувати живий список).
4. **BFF / шар композиції** або окрема **read-модель** (CQRS), що підписана на події обох сервісів і обслуговує цей екран.

Поговоріть про: ідемпотентність (зберігати id партнерів, а не просто інкрементувати), порядок (додавання/видалення приходять не в тому порядку → версії або перерахунок), початкове заповнення лічильників і періодичне звіряння розбіжностей.
