Питання 161 («як налагоджувати систему з багатьох мікросервісів?») насправді про **спостережуваність**: уміння відповідати на нові питання про працюючу систему за сигналами, які вона випромінює.

## Три сигнали

| Сигнал | Відповідає на | API в .NET |
|---|---|---|
| **Логи** | що сталося, з подробицями | `ILogger<T>` (структуровано) |
| **Метрики** | скільки / як часто / як довго, агреговано | `System.Diagnostics.Metrics.Meter` (`Counter`, `Histogram`, `UpDownCounter`) |
| **Трейси** | куди пішов час між сервісами для одного запиту | `System.Diagnostics.Activity` / `ActivitySource` |

Їх пов'язує **trace id**: кожен рядок логу, записаний під час запиту, містить trace id, тож із повільного трейсу можна перейти до його логів.

## OpenTelemetry в ASP.NET Core

```csharp
builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("orders-api"))
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddEntityFrameworkCoreInstrumentation()
        .AddSource("Orders")                            // ваш власний ActivitySource
        .AddOtlpExporter())                             // у Jaeger, Tempo, Azure Monitor, Honeycomb…
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation()                    // GC, пул потоків, винятки
        .AddMeter("Orders")
        .AddOtlpExporter());
builder.Logging.AddOpenTelemetry(o => o.AddOtlpExporter());

// власний span і метрика
private static readonly ActivitySource Source = new("Orders");
private static readonly Counter<long> Placed = new Meter("Orders").CreateCounter<long>("orders.placed");

using var activity = Source.StartActivity("PlaceOrder");
activity?.SetTag("order.id", order.Id);
Placed.Add(1, new KeyValuePair<string, object?>("channel", "web"));
```

Передача контексту автоматична для вхідних/вихідних HTTP-запитів (заголовок W3C `traceparent`) і gRPC; для брокерів повідомлень SDK (Azure Service Bus, MassTransit) кладуть контекст трейсу в заголовки повідомлень.

## Що вимірювати

- **RED** для сервісів, керованих запитами: **R**ate (запити/с), **E**rrors (невдалі запити/с), **D**uration (гістограми затримок — p50, p95, p99, а не середні).
- **USE** для ресурсів: **U**tilization (використання), **S**aturation (насичення: довжини черг, черга пулу потоків), **E**rrors.
- Бізнес-метрики: розміщені замовлення, невдалі платежі — часто першими показують проблему.
- Рантайм .NET: час пауз GC і розмір купи, довжина черги пулу потоків, частота винятків, конкуренція за блокування.

## SLI, SLO й алерти

- **SLI**: виміряний показник — «частка запитів оформлення замовлення, що завершилися < 500 мс».
- **SLO**: ціль — «99,5% за 30 днів». Решта 0,5% — **бюджет помилок**: поки він є, випускайте функціонал; коли вичерпано — фокус на надійності.
- **SLA**: договірна обіцянка зі штрафами (м'якша за SLO).
- Алертуйте на **симптоми, які відчувають користувачі** (швидкість витрачання бюджету SLO, частота помилок), а не на кожен сплеск CPU; кожен алерт потребує runbook.

## Налагодження повільного запиту між сервісами

1. Знайдіть повільний чи невдалий запит в інтерфейсі трасування (фільтр за кінцевою точкою, статусом, тривалістю) — або почніть з алерту.
2. Відкрийте його трейс: «водоспад» span-ів показує, який сервіс і який виклик (SQL-запит, HTTP-виклик, очікування в черзі) забрав час.
3. Перейдіть до логів з тим самим trace id за подробицями й винятками.
4. Перевірте метрики цього сервісу в той час (насичення? GC? пул потоків? розгортання?).
5. Відтворіть із тими самими вхідними даними; для проблем пам'яті чи CPU зніміть дамп/трейс (`dotnet-dump`, `dotnet-trace`) з ураженого екземпляра.

## Ціна й пастки

Мітки з високою кардинальністю в метриках (id користувача, id замовлення) роздувають сховище — кладіть їх у трейси й логи. Семплюйте трейси при великому обсязі (head sampling: зберігати N%; tail sampling у колекторі: зберігати помилки й повільні). Ніколи не логуйте секрети чи персональні дані. Локально **дашборд .NET Aspire** показує логи, метрики й трейси всіх ваших сервісів без налаштувань.

## Консистентне хешування (практика)

Партиційовані системи — розподілені кеші (Redis Cluster використовує hash slots), Cassandra, шардовані бази, «липке» балансування — мусять вирішувати, який вузол володіє ключем. `hash(key) % N` переміщує майже кожен ключ, коли N змінюється. **Консистентне хешування** розміщує вузли (як багато віртуальних точок) на кільці; ключ належить першому вузлу за годинниковою стрілкою від свого хешу, тож додавання чи видалення вузла переміщує лише близько 1/N ключів. Ви реалізуєте кільце й виміряєте різницю.
