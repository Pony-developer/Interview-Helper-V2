Питання 149–150 («які бази й коли?») на рівні Senior перетворюються на «а як ви її масштабуєте?». Ось стандартні кроки в порядку, в якому їх зазвичай роблять.

## 0. Спершу зробіть швидшою одну базу

Індекси під запити, усунення N+1 запитів, кешування гарячих читань (Redis), пул з'єднань, перенесення звітів з primary, архівування старих даних, потужніше залізо (вертикальне масштабування — нудно, але дешево порівняно зі складністю розподілених систем).

## 1. Реплікація

```text
           записи
client ──────────────► primary ── WAL / передавання журналу ──► replica 1 (читання)
       ◄── читання ─────────────────────────────────────────────► replica 2 (читання)
```

- **Асинхронна** реплікація: швидкі записи, але репліки відстають (від мілісекунд до секунд) → застарілі читання, а перемикання може втратити останні записи.
- **Синхронна**: коміт чекає на репліку → без втрати даних при перемиканні, повільніші записи.
- Проблеми read-your-writes: після збереження певний час направляйте читання користувача на primary, або повертайте збережені дані напряму, або чекайте на позицію журналу репліки.
- У .NET: окремі рядки підключення / `DbContext`-и для читання й запису; «ApplicationIntent=ReadOnly» в Azure SQL; PostgreSQL з кінцевою точкою репліки.

## 2. Партиціювання (усередині одного сервера)

```sql
CREATE TABLE events (id bigint, created_at timestamptz, payload jsonb) PARTITION BY RANGE (created_at);
CREATE TABLE events_2026_03 PARTITION OF events FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
```

Запити з фільтром за ключем партиції чіпають лише потрібні партиції (partition pruning); видалити місяць — це `DROP TABLE events_2025_01` замість повільного `DELETE`. Чудово для часових рядів і логів.

## 3. Шардинг (між серверами)

Розподіліть рядки за **ключем шарда** по кількох базах: id тенанта для SaaS, id користувача для соцмережі.

- **За хешем** (рівномірно; консистентне хешування, щоб додавання шарда переміщувало лише частину даних), **за діапазоном** (легкі діапазонні запити, ризик «гарячих» шардів), **за довідником** (таблиця «тенант → шард»; гнучко, ще один компонент).
- Ціна: запити й з'єднання між шардами стають роботою застосунку; транзакції між шардами потребують саг; ребалансування — окрема операція; унікальні id потребують глобальної схеми (GUID v7, Snowflake id).
- Керовані варіанти: Azure Cosmos DB (ключ партиції), Citus для PostgreSQL, Elastic Database tools для Azure SQL, Vitess для MySQL.

## 4. CAP і PACELC

- **CAP**: під час **розділення** мережі розподілене сховище мусить обрати **узгодженість** (відмовити частині запитів) або **доступність** (відповідати, можливо застарілими даними).
- **PACELC**: *інакше*, у звичайному режимі, воно обирає між **затримкою** й **узгодженістю** — наприклад, синхронна реплікація = узгоджено, але повільніше.
- Приклади: один primary PostgreSQL — радше CP; Cassandra/DynamoDB налаштовуються (кворумні читання/записи); Cosmos DB пропонує п'ять рівнів від Strong до Eventual (за замовчуванням **Session**).

## 5. Пагінація в масштабі

`OFFSET 100000` змушує базу прочитати й відкинути 100 000 рядків; до того ж результати зсуваються при вставленні рядків. **Keyset (seek) пагінація** використовує останній рядок попередньої сторінки як курсор:

```sql
SELECT id, created_at, title
FROM events
WHERE (created_at, id) < (@lastCreatedAt, @lastId)      -- порівняння рядкових значень (PostgreSQL, MySQL; у SQL Server емулюють)
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- потрібен індекс на (created_at DESC, id DESC); id розв'язує нічиї, тож жоден рядок не пропущено й не повторено
```

У SQL Server пишуть `WHERE created_at < @c OR (created_at = @c AND id < @id)`. API повертає непрозорий курсор (Base64 двох значень) замість номерів сторінок. Ці запити ви напишете в практиці.

## 6. Експлуатаційні теми, які варто згадати

Бекапи й відновлення на момент часу (знайте свої **RPO** — скільки даних можна втратити — і **RTO** — скільки може тривати відновлення), перевірка відновлення, онлайнові зміни схеми (міграції expand/contract), обмеження з'єднань (пули, PgBouncer), моніторинг повільних запитів (Query Store, `pg_stat_statements`), планування потужностей.
