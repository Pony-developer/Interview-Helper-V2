## ООП: чотири принципи (П1–2)

- **Інкапсуляція**: об'єкт приховує свій стан і відкриває поведінку. Приватні поля й публічні методи тримають інваріанти в одному місці: `BankAccount` відкриває `Withdraw(amount)`, а не `Balance`, який можна присвоїти.
- **Успадкування**: клас перевикористовує й розширює інший клас (`class Manager : Employee`). Застосовуйте його для справжніх відношень «є»; в інших випадках краще композиція.
- **Абстракція**: працюємо з суттєвим контрактом і ховаємо деталі. `Stream` дає читати байти, не зважаючи, звідки вони: з файлу, пам'яті чи мережі.
- **Поліморфізм**: один виклик, багато реалізацій. `shape.Area()` виконує `Circle.Area` або `Square.Area` залежно від типу під час виконання (віртуальна диспетчеризація). Перевантаження — поліморфізм часу компіляції (ad-hoc); generics — параметричний поліморфізм.

Кожен тип .NET неявно походить від **`System.Object`** (структури — через `System.ValueType`). У C# **немає множинного успадкування класів**: один базовий клас, але скільки завгодно інтерфейсів.

## Рекурсія та лямбди (П3–4)

**Рекурсія** — метод, що викликає сам себе для меншої задачі. Їй потрібен **базовий випадок** і рух до нього, інакше кожен виклик додає кадр стеку, аж до `StackOverflowException`, який неможливо перехопити. Глибоку рекурсію можна замінити циклом і явним `Stack<T>`.

```csharp
static int Factorial(int n) => n <= 1 ? 1 : n * Factorial(n - 1);
```

**Лямбда-вираз** — анонімна функція: `x => x * 2`. Вона перетворюється на делегат (`Func<int, int>`) або на дерево виразів (`Expression<Func<int, int>>`, яке EF Core перекладає в SQL). Лямбди можуть **захоплювати** зовнішні змінні (замикання): компілятор переносить такі змінні в прихований клас.

## Багатопотоковість (П5)

Виконання кількох частин роботи одночасно, щоб задіяти всі ядра процесора або не блокувати UI. Основні інструменти: `Task` і `Task.Run`, `Parallel.For/ForEach`, PLINQ (`AsParallel()`), `Thread` (низький рівень), `ThreadPool`, а також синхронізація: `lock`, `Interlocked`, `SemaphoreSlim`, конкурентні колекції (`ConcurrentDictionary`). Ризики: стани гонитви, взаємні блокування, складніше налагодження.

## Основи вебу (П6–8, 10)

- **JSON**: текстовий формат даних: об'єкти `{}`, масиви `[]`, рядки, числа, `true/false`, `null`. У .NET: `System.Text.Json` (`JsonSerializer.Serialize/Deserialize`) або Newtonsoft.Json.
- **REST**: архітектурний стиль для HTTP API. Ресурси мають URI (`/orders/42`); з ними працюють HTTP-методами (GET читає, POST створює, PUT замінює, PATCH змінює, DELETE видаляє); сервер не зберігає стану; відповіді можна кешувати; коди статусу мають значення (200, 201, 204, 400, 404, 500).
- **SPA**: браузер завантажує одну HTML-оболонку й пакет JavaScript; навігація перемальовує подання на клієнті, а дані приходять з API у JSON (React, Angular, Vue). Переваги: UX як у застосунку, менше трафіку. Недоліки: SEO і перше завантаження потребують уваги (допомагає серверний рендеринг).
- **GET і POST**: GET читає, він **безпечний та ідемпотентний**, параметри в URL (потрапляють у логи, обмежені за довжиною, кешуються, їх можна зберегти в закладках). POST передає дані в тілі, не ідемпотентний (два POST можуть створити два замовлення) і за замовчуванням не кешується. Жоден із них не шифрується: шифрує лише HTTPS.

## Патерни, Docker, тести (П9, 11–12)

**Патерни GoF**, які ви найімовірніше назвете: Singleton, Factory Method, Builder, Strategy, Observer (події C#), Decorator (обгортки `Stream`, middleware ASP.NET), Adapter, Facade, Iterator (`IEnumerable`). Наведіть реальний приклад, де ви його застосували й чому.

**Docker** пакує застосунок із рантаймом і залежностями в **образ**; **контейнер** — ізольований процес, запущений з цього образу, що ділить ядро з хостом. Він розв'язує проблему «на моїй машині працює», дає відтворюване середовище й просте масштабування. Недоліки: ще один шар, який треба вивчити й захистити, образи треба підтримувати, дані зі станом потребують томів, ізоляція слабша, ніж у повної віртуальної машини.

**Модульні й інтеграційні тести**: модульний тест перевіряє один клас чи метод ізольовано, із залежностями, заміненими підробками чи моками; він швидкий і точно вказує на збій. Інтеграційний тест перевіряє реальні компоненти разом (базу даних, HTTP-конвеєр через `WebApplicationFactory`, файлову систему): повільніший, але ловить помилки зв'язування й конфігурації.
