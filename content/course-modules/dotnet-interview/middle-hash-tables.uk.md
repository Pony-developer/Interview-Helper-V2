## Від ключа до кошика (П100)

Хеш-таблиця зберігає записи в масиві **кошиків** (buckets). Щоб знайти ключ:

```text
hash   = key.GetHashCode()          // наприклад, 1_337_420_911
index  = (hash & 0x7FFFFFFF) % buckets.Length   // наприклад, 7
bucket[7] → (key, value) → (key, value) → null   // кожен ключ порівнюємо через Equals
```

Якщо хеш-функція рівномірно розкладає ключі, а таблиця не надто заповнена, у кожному кошику 0–2 записи: пошук, вставлення й видалення — O(1) у середньому. У цьому вся суть: замість порівняння з кожним елементом (O(n)) чи проходу деревом (O(log n)) ви стрибаєте одразу в потрібне місце.

## Добра хеш-функція (П101)

1. **Детермінована** в межах процесу: рівні ключі → рівні хеші. Це контракт `Equals`/`GetHashCode`: якщо `a.Equals(b)`, то `a.GetHashCode() == b.GetHashCode()`. Зворотне не обов'язкове (колізії допустимі).
2. **Рівномірна**: рівно розкладає типові ключі по кошиках.
3. **Швидка**: вона виконується на кожній операції.
4. **Лавинний ефект**: мала зміна входу змінює багато бітів результату.
5. Для недовірених вхідних даних — **стійка до навмисних колізій**: з цієї причини .NET Core рандомізує хешування рядків для кожного процесу (ніколи не зберігайте значення `GetHashCode()`).

Криптографічні хеші (SHA-256) — інший інструмент: стійкі до колізій і односторонні, але надто повільні для словника.

```csharp
public sealed class Point(int x, int y) : IEquatable<Point>
{
    public int X { get; } = x;
    public int Y { get; } = y;
    public bool Equals(Point? o) => o is not null && o.X == X && o.Y == Y;
    public override bool Equals(object? o) => Equals(o as Point);
    public override int GetHashCode() => HashCode.Combine(X, Y);   // ніколи не просто X ^ Y: (1,2) і (2,1) зіткнуться
}
```

Record-и генерують правильні `Equals`/`GetHashCode` самі. Поля, що входять у хеш, не повинні змінюватися, поки об'єкт лежить у словнику чи множині.

## Колізії (П102)

Два різні ключі в одному кошику неминучі (принцип Діріхле). Стратегії:

- **Ланцюжки (separate chaining)**: кожен кошик містить зв'язний список записів. Просто й деградує поступово. `Dictionary<TKey,TValue>` у .NET використовує ланцюжки, реалізовані масивами: `int[] buckets` містить індекс першого запису, а `Entry[] entries` має індекс `next` — жодних об'єктів-вузлів, добра локальність кешу.
- **Відкрита адресація**: при колізії перевіряються інші слоти того самого масиву — лінійне зондування (`i+1, i+2…`), квадратичне, подвійне хешування. Для видалення потрібні «надгробки». Використовується в багатьох високопродуктивних таблицях.
- **Збільшення**: коли `count / buckets` (**коефіцієнт заповнення**) перевищує поріг, виділяється більший масив (.NET бере наступне просте ≥ 2×) і всі записи вставляються заново. Окремий `Add` тоді коштує O(n), амортизовано O(1).
- Найгірший випадок: усі ключі в колізії → O(n) на операцію. Java й .NET пом'якшують атаки рандомізованим хешуванням рядків (Java ще й перетворює довгі ланцюжки на дерева).

## Складність Dictionary&lt;K,V&gt; (П103)

| Операція | У середньому | У найгіршому |
|---|---|---|
| `Add`, `TryAdd`, запис через індексатор | O(1), O(n) при збільшенні | O(n) |
| `TryGetValue`, `ContainsKey`, читання через індексатор | O(1) | O(n) |
| `Remove` | O(1) | O(n) |
| `ContainsValue` | O(n) | O(n) |
| Перебір | O(n) | O(n) |

Поради: передавайте місткість, коли знаєте розмір (`new Dictionary<K,V>(10_000)`), щоб уникнути збільшень; передавайте компаратор для ключів без урахування регістру (`StringComparer.OrdinalIgnoreCase`); `CollectionsMarshal.GetValueRefOrAddDefault` — для гарячих лічильників; `FrozenDictionary` (.NET 8) — для пошуку лише на читання, збудованого один раз.

## Структури ключ-значення (П90)

- У пам'яті: `Dictionary`, `SortedDictionary` (дерево, упорядкований), `SortedList` (два відсортовані масиви, компактний), `ConcurrentDictionary` (дрібнозернисті блокування), `ImmutableDictionary`, `FrozenDictionary`, `Lookup<K,V>` (один ключ → багато значень), `ConditionalWeakTable` (прив'язує дані до об'єктів, не утримуючи їх живими).
- Поза процесом: Redis, Memcached, DynamoDB, Azure Table Storage, etcd — та сама ідея в масштабі мережі, зазвичай із партиціюванням за хешем ключа (консистентне хешування).
