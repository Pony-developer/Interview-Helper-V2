## Окрім ООП, і ваші найскладніші задачі (П122–123)

Назвіть парадигми, які ви справді застосовували, і де:
- **Функціональне програмування**: незмінні дані (record), чисті функції, LINQ, функції вищого порядку, типи `Result`/`Option` замість винятків для очікуваних збоїв, зіставлення зі зразком.
- **AOP** (аспектно-орієнтоване програмування): наскрізний код навколо методів — фільтри й middleware ASP.NET, декоратори, перехоплювачі Castle DynamicProxy, вплітання PostSharp/Fody, генератори коду.
- **Реактивне програмування** (Rx.NET, `IObservable`), **подієво-орієнтована** архітектура, **DDD** (агрегати, об'єкти-значення, доменні події), **data-oriented** дизайн для гарячих шляхів (`Span<T>`, структури, уникнення виділень пам'яті).

Для «трьох найскладніших проблем» використовуйте **STAR**: Situation (ситуація), Task (завдання), Action (дії: які варіанти розглядали і *чому* обрали один), Result (виміряний: «p99 затримка 2 с → 200 мс»). Інтерв'юери перевіряють глибину, відповідальність і чи винесли ви уроки.

## Зчеплення і статичні класи (П124–125)

**Слабко зв'язаний** код залежить від абстракцій і невеликих контрактів, тож частину можна змінити, замінити чи протестувати, не чіпаючи інших. Сильно зв'язаний код знає конкретні класи, внутрішні деталі й глобальний стан: зміна розходиться всюди.

Як зменшити зчеплення: залежати від інтерфейсів і впроваджувати їх (DIP + DI); маленькі сфокусовані інтерфейси; події, повідомлення чи медіатори замість прямих викликів; стабільні DTO/контракти на межах модулів; ховати внутрішнє (`internal`, приватні сетери); уникати спільного змінного стану.

**Статичні класи збільшують зчеплення**: викликач жорстко прив'язаний до однієї реалізації, яку не підміниш і не замокаєш (`DateTime.Now`, `File.ReadAllText` усередині бізнес-логіки). Чисті помічники без стану (`Math.Max`, методи розширення) — нормально; для всього, що має I/O, час чи стан, впроваджуйте абстракцію (`TimeProvider`, `IFileSystem`).

## Вимірювання продуктивності (П126, 128)

- Мікробенчмарки: **BenchmarkDotNet** (прогрів, багато ітерацій, статистика, `[MemoryDiagnoser]` для виділень). Наївний цикл зі `Stopwatch` у Debug вимірює JIT і відладчик, а не ваш код.
- Профілювання: профайлер Visual Studio, dotTrace/dotMemory, PerfView, `dotnet-trace` (семплювання CPU), `dotnet-counters` (GC, швидкість виділень, довжина черги пулу потоків, винятки за секунду), `dotnet-gcdump`/`dotnet-dump` (купа), Application Insights / OpenTelemetry у продакшні.
- **Так, вимірювання впливає на виміряне**: інструментування додає накладні витрати, семплювання має похибку, Debug-збірки вимикають оптимізації, логування й таймери виділяють пам'ять. Надавайте перевагу семплювальним профайлерам і міряйте Release-збірки під реалістичним навантаженням.

Типові вузькі місця: CPU (алгоритми з поганою складністю, надмірний LINQ у гарячих циклах, regex без кешування, серіалізація), пам'ять (швидкість виділень → часті GC, «текучка» в LOH, витоки через статичні кеші й обробники подій), I/O (балакучі виклики до БД, N+1 запити, відсутні індекси, синхронне I/O, без пулу з'єднань), конкуренція (блокування, голодування пулу потоків через блокуючий код).

Зменшення пам'яті та трафіку пам'яті: уникати виділень у гарячих шляхах (`Span<T>`, `stackalloc`, `ArrayPool<T>`, перевикористання `StringBuilder`, `ValueTask`), структури для малих даних, уникати упакування й замикань, читати великі дані потоково замість завантаження цілком (`IAsyncEnumerable`, `Stream`), розумно кешувати з обмеженням розміру, відписуватися від подій, `RecyclableMemoryStream`.

## Multi-stage збірки Docker (П127)

Один Dockerfile з кількома етапами `FROM`. Збираємо у великому образі з SDK, а потім копіюємо лише результат publish у маленький образ рантайму:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY *.csproj .
RUN dotnet restore                 # кешується, доки не зміниться файл проєкту
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /app .
USER app
ENTRYPOINT ["dotnet", "Api.dll"]
```

Результат: значно менший фінальний образ без компіляторів і вихідного коду (менша поверхня атаки, швидше завантаження) та добре кешування шарів. Можна додати й етап `test`.

## Наскрізна функціональність (П129)

- На рівні HTTP: **middleware** (логування, correlation id, обробка винятків, транзакція на запит) і **фільтри** (валідація, авторизація).
- На рівні застосунку: **декоратори** навколо інтерфейсів (`LoggingOrderService : IOrderService`), зареєстровані через `Decorate` у Scrutor; **pipeline behaviors у MediatR** (`ValidationBehavior`, `TransactionBehavior`) обгортають кожен обробник запиту.
- Вихідні виклики: `DelegatingHandler` для `HttpClient` (повтори з Polly, заголовки автентифікації, логування).
- Валідація: FluentValidation або DataAnnotations, що запускаються автоматично; логування через scope-и `ILogger` та OpenTelemetry.

## Модель зрілості REST (П130)

Модель Річардсона:
- **Рівень 0**: одна кінцева точка, RPC поверх HTTP (у стилі SOAP `POST /api`).
- **Рівень 1**: ресурси — окремі URI (`/orders/42`).
- **Рівень 2**: правильно використані HTTP-методи й коди статусу (GET/POST/PUT/DELETE, 201, 404, 409). Більшість «REST» API зупиняються тут.
- **Рівень 3**: гіпермедіа (**HATEOAS**): відповіді містять посилання на пов'язані ресурси й дозволені наступні дії, тож клієнти відкривають API самі.

## CPU-bound і IO-bound, маршалінг (П131–132)

Робота, **обмежена процесором**, упирається в обчислення (обробка зображень, хешування, стиснення): прискорюйте її паралелізмом (`Parallel.For`, `Task.Run` у клієнтських застосунках). Робота, **обмежена I/O**, чекає на диск, мережу чи базу: використовуйте асинхронне I/O, щоб під час очікування жоден потік не був зайнятий. Обгортати I/O в `Task.Run` чи робити CPU-роботу «асинхронною» не допомагає.

**Маршалінг** перетворює дані між представленнями під час перетину межі: керований ↔ некерований код для P/Invoke і COM (рядки в `char*`/`BSTR`, розкладка структур через `[StructLayout]`, `[MarshalAs]`), а також між AppDomain-ами/процесами (за значенням чи за посиланням). Blittable-типи (int, double, структури з них) не потребують перетворення; згенерований `[LibraryImport]` уникає витрат на маршалінг під час виконання.

## async/await у деталях (П133)

Компілятор переписує метод `async` у **структуру-скінченний автомат**, що реалізує `IAsyncStateMachine`, плюс `AsyncTaskMethodBuilder`:

1. Викликач викликає метод; builder створює автомат і синхронно виконує `MoveNext()` до першого `await`.
2. `await x` викликає `x.GetAwaiter()`. Якщо `IsCompleted` дорівнює true, виконання продовжується синхронно (без виділень, без перемикання потоку).
3. Інакше стан зберігається (`state = 1`, локальні змінні винесені в поля), автомат уперше **упаковується в купу**, `AwaitUnsafeOnCompleted` реєструє `MoveNext` як продовження, і метод повертає викликачу `Task` від builder-а.
4. Коли операція, на яку чекали, завершується, виконується продовження — в захопленому `SynchronizationContext`/`TaskScheduler` або на потоці пулу — і `MoveNext()` переходить до збереженого стану.
5. На `return` builder завершує `Task` результатом; винятки зберігаються в задачі й перекидаються на `await`.

**`async void`**: викликач не отримує нічого, на що можна чекати, тож не може дізнатися, коли метод завершиться, чи побачити його винятки. Виняток, що вилетів з методу `async void`, піднімається в `SynchronizationContext` або пулі потоків і **обвалює процес**. Такі методи ще й важко тестувати. Вони існують для обробників подій; деінде повертайте `Task`. Для свідомого «запустив і забув» використовуйте фонову чергу / hosted service або щонайменше `_ = Task.Run(...)` із try/catch, що логує.
