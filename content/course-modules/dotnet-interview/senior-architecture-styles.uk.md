«Окрім ООП, які практики ви застосовували?» (П122) і «Як би ви реалізували наскрізну функціональність?» (П129) зазвичай ведуть до архітектури. Знайте основні стилі, їхні компроміси й коли який обрати.

## Шарова (N-tier)

```text
Presentation (контролери) → Business logic (сервіси) → Data access (репозиторії, EF) → База даних
```

Проста й знайома. Ризик: бізнес-логіка залежить від деталей доступу до даних, усе опиняється в «сервісах», а домен стає анемічним (класи лише з властивостями).

## Чиста / «цибулева» / гексагональна (порти й адаптери)

```text
           ┌──────────── Infrastructure (EF Core, HTTP-клієнти, пошта, черги) ────────────┐
           │     ┌──────── Application (сценарії, команди/запити, інтерфейси) ──────┐     │
           │     │          ┌──── Domain (сутності, об'єкти-значення, правила) ┐     │     │
           │     │          └──────────────────────────────────────────────────┘     │     │
           │     └───────────────────────────────────────────────────────────────────┘     │
           └──────────────────── Web API / UI (composition root) ──────────────────────────┘
```

**Правило залежностей**: залежності в коді спрямовані всередину. Домен не посилається на EF Core чи ASP.NET; шар застосунку визначає інтерфейси (`IOrderRepository`, `IEmailSender` — «порти»); інфраструктура їх реалізує («адаптери»). Переваги: тестовані бізнес-правила, замінна інфраструктура. Ціна: більше проєктів, інтерфейсів і мапінгу — надмірно для CRUD-сервісу.

## Domain-Driven Design (тактичний)

- **Сутність** — має ідентичність, що зберігається (`Order #42`).
- **Об'єкт-значення** — визначається значеннями, незмінний (`Money`, `Address`) → `record` у C#.
- **Агрегат** — група, що змінюється разом через свій **корінь**, який гарантує інваріанти (`Order` зі своїми `OrderLines`: рядки додають через `order.AddLine(...)`, ніколи напряму). Одна транзакція змінює один агрегат; на інші агрегати посилаються за id.
- **Доменні події** — `OrderPaid`, яку піднімає агрегат і обробляють після транзакції (часто через outbox).
- **Обмежені контексти** (стратегічний DDD) — «Product» означає різне в Catalog і Shipping; кожен контекст має свою модель. Добрі кандидати на межі мікросервісів.

```csharp
public sealed class Order
{
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyList<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; }

    public void AddLine(Product p, int qty)
    {
        if (Status != OrderStatus.Draft) throw new InvalidOperationException("Order is locked");
        if (qty <= 0) throw new ArgumentOutOfRangeException(nameof(qty));
        _lines.Add(new OrderLine(p.Id, qty, p.Price));
    }
}
```

## CQRS

Розділіть **бік запису** (команди → агрегати → інваріанти) і **бік читання** (запити → DTO, оптимізований SQL, можливо окрема read-модель чи база). Легкий CQRS — лише окремі обробники команд і запитів в одній базі — поширений із MediatR. Повний CQRS з окремим сховищем для читання додає кінцеву узгодженість; він доречний, коли читання й записи дуже різні за формою чи масштабом.

## Архітектура вертикальних зрізів

Організація за **функціональністю**, а не за шарами: `Features/Orders/PlaceOrder.cs` містить запит, валідатор, обробник і кінцеву точку. Кожен зріз обирає власний доступ до даних (EF для записів, Dapper для важкого звіту). Менше абстракцій, зміни лишаються локальними. Добре поєднується з конвеєром медіатора для наскрізної функціональності.

## Наскрізна функціональність у конвеєрі

```csharp
public sealed class ValidationBehavior<TRequest, TResponse>(IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse> where TRequest : notnull
{
    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var failures = validators.Select(v => v.Validate(request)).SelectMany(r => r.Errors).ToList();
        if (failures.Count > 0) throw new ValidationException(failures);
        return await next();
    }
}
// Реєструються по порядку: Logging → Validation → Transaction → обробник
```

Практика будує такий конвеєр з нуля: перший зареєстрований behavior — найзовнішній, а behavior може зупинити конвеєр (валідація), не викликаючи обробник.

## Як відповідати на «яку архітектуру ви б обрали?»

Починайте з проблеми: простий CRUD-адмін → шари чи вертикальні зрізи, мінімум церемоній; складні бізнес-правила, що часто змінюються → агрегати DDD з чіткими межами; дуже різні навантаження читання й запису → CQRS; багато команд, незалежне розгортання → спершу модульний моноліт, мікросервіси — коли межі перевірені. Згадайте **ADR** (architecture decision records), щоб документувати вибір.
