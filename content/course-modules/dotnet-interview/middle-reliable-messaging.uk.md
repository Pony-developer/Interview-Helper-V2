Дві задачі на проєктування зі списку Middle стосуються того, як **не втратити дані**, коли задіяно більше ніж одну систему.

## 1. Зберегти сутність і опублікувати подію

> Сутність треба записати в базу даних і надіслати подію в брокер повідомлень. Як зробити це з мінімальним ризиком утратити дані?

Наївна версія має проблему **подвійного запису (dual write)**:

```csharp
await db.SaveChangesAsync();             // 1. закомічено
await bus.PublishAsync(new OrderPlaced()); // 2. процес падає тут → подію втрачено
```

Поміняти порядок не краще: подію опубліковано, потім коміт у БД падає, і інші сервіси реагують на замовлення, якого не існує. Розподілена транзакція (2PC / MSDTC) між БД і брокером зазвичай недоступна (більшість брокерів і хмарних сервісів її не підтримують) і зчіплює доступність обох сторін.

**Transactional outbox**:

1. У **тій самій локальній транзакції**, що й бізнес-зміна, вставте подію в таблицю `Outbox`.
2. Фоновий **ретранслятор** (hosted service, що опитує таблицю, або change data capture на кшталт Debezium) читає невідправлені рядки, публікує їх у брокер і позначає як відправлені.
3. Якщо ретранслятор упаде між «опублікував» і «позначив», він опублікує знову → доставка **щонайменше раз**, тож споживачі мусять бути **ідемпотентними**.

```csharp
await using var tx = await db.Database.BeginTransactionAsync();
db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage { Id = Guid.NewGuid(), Type = "OrderPlaced", Payload = json });
await db.SaveChangesAsync();
await tx.CommitAsync();   // або обидва, або жоден
```

Бібліотеки MassTransit, NServiceBus, CAP чи Wolverine реалізують outbox (та inbox) за вас.

## 2. Ланцюжок із трьох сервісів

> HTTP-запит приходить у сервіс A; A пише в B; B пише в C. Як гарантувати, що дані не загубляться в ланцюжку? Як запобігти дублікатам?

Щоб не втрачати дані:
- Робіть кожен крок **надійно збереженим до підтвердження**: A зберігає запит (і повідомлення в outbox) та повертає `202 Accepted`; передача в B іде через **чергу**, а не синхронний виклик, що може обірватися посередині. Так само між B і C.
- **Повтори** з експоненційною затримкою та jitter для тимчасових збоїв; **dead-letter queue** для повідомлень, що постійно падають, з алертами й повторним відтворенням.
- Якщо пізніші кроки можуть не вдатися з бізнесових причин, використовуйте **сагу**: послідовність локальних транзакцій із **компенсувальними діями** (оркестровану координатором або хореографовану подіями) замість однієї розподіленої транзакції.

Щоб запобігти дублікатам (повтори роблять їх неминучими):
- Дайте кожній операції **ключ ідемпотентності** / id повідомлення, згенерований на вході (клієнт надсилає заголовок `Idempotency-Key`) і переданий далі ланцюжком.
- Кожен сервіс записує оброблені id (таблиця **inbox**, унікальне обмеження) в тій самій транзакції, що й свою зміну, і пропускає повтори; або використовує upsert за природним бізнес-ключем.
- Надавайте перевагу операціям, що встановлюють стан (`status = Shipped`), а не інкрементам.

Згадка про компроміси додає балів: кінцева узгодженість замість миттєвої, додаткова інфраструктура (брокер, ретранслятор outbox), потреба в моніторингу та correlation id, щоб простежити один запит через усі три сервіси.
