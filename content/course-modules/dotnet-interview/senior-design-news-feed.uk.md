«Клонуйте популярну соцмережу» є в списку DOU для Senior (практична задача 16). Її серце — **стрічка новин**. Ось як її пройти.

## Вимоги й масштаб

- Користувачі підписуються на інших; публікують текст і медіа; домашня стрічка показує пости тих, на кого підписані, найновіші першими (ранжування — пізніше розширення); нескінченна прокрутка.
- Припустимо 100 млн активних користувачів на день, кожен відкриває стрічку 10 разів на день → ~12 тис. читань стрічки/с у середньому, піки ×5; 50 млн нових постів на день → ~600 записів/с; деякі акаунти мають 10 млн+ підписників.
- Затримка стрічки p99 < 300 мс; новий пост може з'явитися за кілька секунд (кінцева узгодженість прийнятна).

## Модель даних

- `users`, `follows (follower_id, followee_id)` — шардовано за id користувача.
- `posts (id, author_id, created_at, text, media_urls)` — шардовано за id автора; id постів упорядковані за часом (Snowflake / GUID v7).
- Медіа в об'єктному сховищі (Blob/S3) за CDN; пост зберігає URL.

## Два способи побудувати стрічку

**Fan-out on write (push).** Коли Аня публікує пост, фоновий воркер вставляє id поста в заздалегідь обчислену стрічку кожного її підписника (sorted set у Redis або таблиця стрічки на користувача, обмежена ~1000 записами).
- Читання тривіальне й швидке: взяти верхні N id, заповнити пости з кешу.
- Записи дорогі для знаменитостей (10 млн вставлень на пост), а стрічки неактивних користувачів — марна робота.

**Fan-out on read (pull).** Коли Борис відкриває стрічку, прочитати останні пости всіх, на кого він підписаний, і **злити** їх.
- Записи дешеві; нічого не обчислюється заздалегідь.
- Читання дороге для користувачів, підписаних на тисячі акаунтів.

**Гібрид (як роблять великі мережі):** push для звичайних авторів, pull для знаменитостей (і для неактивних користувачів, що повертаються): під час читання злити заздалегідь обчислену стрічку з останніми постами кількох знаменитостей, на яких підписаний користувач.

## Злиття

Кожне джерело (хронологія) вже відсортоване від найновішого. Взяти найновіші N із k джерел — це **k-шляхове злиття**: покласти голову кожної хронології в чергу з пріоритетом (купу), раз у раз брати найкращий і додавати наступний пост із тієї самої хронології. Ціна: O(N log k) замість об'єднання й сортування всього. Пагінація використовує **курсор** (час/id останнього показаного поста), а не номери сторінок — нові пости вгорі не повинні зсувати те, що поверне наступна сторінка. Практика реалізує саме це.

## Шлях обслуговування

```text
client → CDN/API gateway → Feed service
   1. прочитати id стрічки (sorted set у Redis, за курсором)      ~1 мс
   2. злити з хронологіями знаменитостей (кешовано)               ~5 мс
   3. заповнити пости й авторів із кешу (multi-get)               ~5 мс
   4. відфільтрувати (заблоковані, видалені, приватність) і повернути сторінку
шлях запису: Post service → БД → outbox → черга → fan-out воркери → кеші стрічок
```

## Теми для заглиблення

- **Ранжування**: замінити «найновіші першими» на модель оцінки (залученість, близькість, свіжість) — зазвичай окремий сервіс ранжування поверх генерації кандидатів.
- **Лічильники** (лайки, коментарі): шардовані лічильники або асинхронна агрегація; наближені значення прийнятні.
- **Гарячі ключі**: пост знаменитості отримує мільйони читань — реплікуйте гарячі ключі в кеші, використовуйте локальні кеші в пам'яті, CDN для медіа.
- **Узгодженість**: користувач має одразу бачити власний пост (вставити його у власну стрічку синхронно або злити на клієнті).
- **Видалення й зміни приватності**: фільтрувати під час читання; очищати стрічки ліниво.
- **Зворотний тиск**: якщо fan-out воркери відстають, черга росте — автомасштабування воркерів, деградація через переведення більшої кількості авторів на pull.

## Інші завдання на проєктування з DOU одним рядком

- **FTP / вебсервер**: обробка з'єднань, розбір протоколу, асинхронне I/O, обмеження, TLS (див. попередню лекцію про проєктування систем).
- **Хостинг зображень із правами доступу**: об'єктне сховище + CDN + підписані URL + асинхронні мініатюри.
- **Front office / back office**: окремі застосунки й периметри безпеки над спільним доменом; read-модель для звітів.
- **Лічильник партнерів у бідів**: локальна read-модель на ідемпотентних версіонованих подіях (практика в цьому модулі).
