Питання 134 («як працює `lock`?») відкриває двері до решти інструментів синхронізації. Senior має знати, для чого кожен примітив і скільки він коштує.

## Інструменти

| Примітив | Область | Для чого |
|---|---|---|
| `lock` / `Monitor` (.NET 9: `System.Threading.Lock`) | процес, прив'язаний до потоку | короткі критичні секції в синхронному коді |
| `SemaphoreSlim` | процес, N власників, `WaitAsync` | асинхронне взаємне виключення, обмеження паралелізму |
| `ReaderWriterLockSlim` | процес | багато читачів, рідкі записувачі, непросте читання |
| `Mutex` | уся ОС, може мати ім'я | один екземпляр застосунку на машині, між процесами |
| `Semaphore` | уся ОС | обмеження між процесами |
| `Interlocked` | одна змінна | лічильники, прапорці, неблокуючі CAS-цикли |
| `volatile` / `Volatile` | видимість/порядок одного поля | прапорці, які читають інші потоки |
| `ManualResetEventSlim`, `CountdownEvent`, `Barrier` | сигналізація | «чекати на готовність», «чекати на N воркерів» |
| `Channel<T>`, `BlockingCollection<T>` | продюсер/споживач | конвеєри зі зворотним тиском |
| `ConcurrentDictionary` та інші | потокобезпечні колекції | спільні кеші, лічильники за ключем |

Надавайте перевагу, по порядку: **відсутність спільного змінного стану** (незмінність, передавання повідомлень, об'єкти на запит) → потокобезпечні колекції / канали → `lock` / `SemaphoreSlim` → неблокуючий код на `Interlocked` лише на виміряних гарячих шляхах.

## Interlocked і compare-and-swap

```csharp
Interlocked.Increment(ref _count);                       // атомарний ++
Interlocked.Add(ref _total, amount);
var previous = Interlocked.Exchange(ref _state, 1);      // встановити й отримати старе значення
// Compare-and-swap: будівельний блок неблокуючих алгоритмів
int seen = Interlocked.CompareExchange(ref _value, newValue, expected);   // повертає значення до виклику
```

CAS-цикл повторює, доки ніхто не втрутився:

```csharp
int current = Volatile.Read(ref _max);
while (candidate > current)
{
    int seen = Interlocked.CompareExchange(ref _max, candidate, current);
    if (seen == current) break;   // ми виграли
    current = seen;               // хтось змінив; перевіряємо з новим значенням
}
```

Неблокуючий код уникає очікувань і взаємних блокувань, але його важко написати правильно (проблема ABA, livelock під конкуренцією) — `ConcurrentQueue` і `ConcurrentStack` з BCL уже неблокуючі, тож власний потрібен рідко. Практика реалізує стек Трайбера й атомарний `Max`.

## Модель пам'яті в одному абзаці

Компілятори, JIT і процесори можуть переставляти читання й записи та тримати значення в регістрах/кешах, доки *один* потік цього не помічає. Інший потік може побачити записи в несподіваному порядку. `lock`, `Interlocked`, `Volatile.Read/Write`, `Thread.MemoryBarrier` і межі `Task`/`await` вводять **бар'єри пам'яті**, що роблять записи видимими. На x64 обладнання досить «суворе»; на ARM (Apple silicon, Graviton, Ampere) можливих перестановок більше, тож код, що «працював на моїй машині», може зламатися. Правило: будь-яке спільне поле, до якого кілька потоків звертаються без блокування, має йти через `Volatile` або `Interlocked`.

## Класичні баги

```csharp
// 1. Блокування з подвійною перевіркою без volatile: використовуйте Lazy<T>
// 2. lock на публічному об'єкті чи рядковому літералі → чужий код може вас заблокувати
// 3. Порядок блокувань: Transfer(a, b) блокує a, потім b; Transfer(b, a) — b, потім a → deadlock; впорядкуйте за id
// 4. Виклик невідомого коду (події, колбеки) під блокуванням
// 5. Блокування на async усередині lock → голодування пулу потоків; використовуйте SemaphoreSlim.WaitAsync
// 6. «Перевір, потім дій» на ConcurrentDictionary: if (!d.ContainsKey(k)) d[k] = v;  → TryAdd / GetOrAdd / AddOrUpdate
```

## Стан, що «тече» з контекстом

- `ThreadLocal<T>` / `[ThreadStatic]` — значення на потік ОС; небезпечно з async (продовження може виконатися в іншому потоці).
- `AsyncLocal<T>` — тече разом з `ExecutionContext` через await; використовується для correlation id, `Activity.Current`, `IHttpContextAccessor`.
