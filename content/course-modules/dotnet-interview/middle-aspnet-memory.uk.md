## Винятки, яких не зупинити (П71)

- **`StackOverflowException`**: не перехоплюється, починаючи з .NET 2.0; процес завершується.
- **`ThreadAbortException`** (.NET Framework): його можна перехопити, але рантайм **автоматично кидає його знову** в кінці `catch`, якщо не викликати `Thread.ResetAbort()`. `Thread.Abort` не підтримується в .NET Core/5+.
- **`OutOfMemoryException`** перехопити можна, але безпечно зробити майже нічого не вийде. Винятки пошкодженого стану (`AccessViolationException`) у .NET Core не доходять до керованих блоків `catch`.
- `Environment.FailFast` завершує процес, не виконуючи ні `catch`, ні `finally`.

## Бібліотеки .NET Standard і .NET (Core) (П72)

**.NET Standard** — це *специфікація* API, яку мусить надавати кожна реалізація (.NET Framework, .NET Core, Mono, Xamarin, Unity). Бібліотека `netstandard2.0` працює на всіх них, але може використовувати лише спільну підмножину. Бібліотека **.NET Core / .NET 5+** (`net8.0`) націлена на один рантайм і може використовувати всі його API. Сьогодні: для нового коду — `net8.0`+, `netstandard2.0` — лише коли треба підтримувати ще й .NET Framework.

## Відкладене й негайне виконання (П73)

Більшість операторів LINQ (`Where`, `Select`, `OrderBy`, `Take`) **відкладені**: вони будують конвеєр, який виконується лише під час перебору, і виконується **знову** при кожному переборі. Оператори, що повертають одне значення чи матеріалізовану колекцію (`ToList`, `ToArray`, `ToDictionary`, `Count`, `First`, `Sum`, `Max`), виконуються **негайно**.

```csharp
var list = new List<int> { 1, 2, 3 };
var big = list.Where(x => x > 1);   // поки нічого не виконується
list.Add(10);
Console.WriteLine(big.Count());     // 3: 2, 3, 10 — виконується зараз і бачить зміну
var snapshot = big.ToList();        // виконується зараз, заморожена копія
```

Пастка: дворазовий перебір `IQueryable` з EF Core двічі звертається до бази.

## ASP.NET Core (П74–78)

- **`ConfigureServices(IServiceCollection services)`** реєструє сервіси в DI-контейнері (`AddControllers`, `AddDbContext`, власні сервіси); `Configure(IApplicationBuilder app)` будує конвеєр middleware. Починаючи з .NET 6 обидва живуть у `Program.cs`: `builder.Services.Add...` і `app.Use...`.
- **Час життя**: `AddTransient` — новий екземпляр щоразу, коли його запитують; `AddScoped` — один екземпляр на область, тобто на HTTP-запит (`DbContext` — scoped); `AddSingleton` — один екземпляр на весь застосунок. Ніколи не впроваджуйте scoped-сервіс у singleton (*captive dependency*): він житиме вічно й буде спільним для різних запитів.
- **Kestrel** — кросплатформений високопродуктивний HTTP-сервер, вбудований в ASP.NET Core. Він може дивитися просто в інтернет або стояти за зворотним проксі (IIS, Nginx, YARP), який бере на себе TLS, балансування тощо.
- **Конвеєр запиту**: Kestrel → middleware по порядку (обробник винятків, HSTS, переспрямування на HTTPS, статичні файли, маршрутизація, CORS, автентифікація, авторизація, …) → кінцева точка. Для MVC: маршрутизація обирає дію контролера → фільтри (авторизації → ресурсу → прив'язка моделі й валідація → фільтри дій → дія → фільтри винятків → фільтри результату) → результат (`IActionResult`) виконується й записується у відповідь. Кожен middleware може завершити обробку достроково або обгорнути наступний (`await next()`).
- **Кешування відповідей**: HTTP-заголовки через `[ResponseCache(Duration = 60, Location = ResponseCacheLocation.Any, VaryByQueryKeys = new[] { "page" })]` (дозволяє кешувати браузерам і проксі); серверне `AddResponseCaching()` + `UseResponseCaching()` або новіше **output caching** (`AddOutputCache`, `[OutputCache]`, .NET 7+) з тегами для інвалідації; `ETag` / `If-None-Match` → `304 Not Modified`; кешування даних через `IMemoryCache` / `IDistributedCache` (Redis).

## Стек, купа й GC (П79–80)

- **Стек**: свій у кожного потоку, за замовчуванням ~1 МБ, LIFO-кадри з локальними змінними й аргументами; виділення — це просто зсув вказівника, а звільнення відбувається автоматично після повернення з методу.
- **Керована купа**: спільна для всіх потоків; містить об'єкти типів посилань (і упаковані значення). Виділення теж швидке (зсув вказівника в Gen 0), але для звільнення потрібен GC.

**GC** запускається, коли заповнюється Gen 0 (або при нестачі пам'яті / `GC.Collect`). Він призупиняє керовані потоки, **позначає** всі об'єкти, досяжні з коренів (статичні поля, локальні змінні в стеку, регістри, GC-дескриптори, черга фіналізації), **прибирає / ущільнює** вцілілі й оновлює посилання, а тоді **підвищує** вцілілих до наступного покоління. Збирання Gen 0 і Gen 1 дешеві; збирання Gen 2 (повне) дороге. Режими: workstation і server GC, фонове (конкурентне) збирання Gen 2.

## using, Dispose і LOH (П81–82)

GC звільняє лише **пам'ять** і в непередбачуваний момент. Дескриптори файлів, сокети, з'єднання з БД, дескриптори ОС і блокування треба звільняти **детерміновано**. `using` викликає `Dispose()` у блоці `finally`:

```csharp
using var connection = new SqlConnection(cs);   // Dispose() наприкінці області видимості
```

Повний патерн Dispose складний, бо клас може володіти **некерованими** ресурсами (сирими дескрипторами), які треба звільнити, навіть якщо ніхто не викличе `Dispose` — тож потрібен **фіналізатор** як страховка, — а **керовані** disposable-поля чіпати з фіналізатора не можна (вони вже можуть бути фіналізовані):

```csharp
protected virtual void Dispose(bool disposing)
{
    if (_disposed) return;
    if (disposing) _stream.Dispose();     // керовані: лише з Dispose()
    CloseHandle(_handle);                 // некеровані: завжди
    _disposed = true;
}
public void Dispose() { Dispose(true); GC.SuppressFinalize(this); }
~MyResource() => Dispose(false);
```

Сьогодні сирі дескриптори обгортають у `SafeHandle`, і фіналізатор майже ніколи не потрібен.

**Large Object Heap**: туди потрапляють об'єкти розміром **від 85 000 байтів** (великі масиви й рядки). Логічно він є частиною Gen 2, тож збирається лише під час повних збирань і **за замовчуванням не ущільнюється** (копіювати дорого), тому фрагментується. Не виділяйте великі тимчасові буфери раз у раз: беріть їх із пулу (`ArrayPool<T>.Shared`, `RecyclableMemoryStream`) або одноразово ущільніть через `GCSettings.LargeObjectHeapCompactionMode`.
