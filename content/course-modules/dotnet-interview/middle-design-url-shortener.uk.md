Кандидатам рівня Middle дедалі частіше дають легке питання на проєктування систем. Скорочувач посилань — класика: достатньо малий для 30 хвилин і достатньо багатий, щоб обговорити API, сховище, кешування й масштабування.

## 1. Вимоги

- Функціональні: створити коротке посилання для довгого URL; перенаправляти з короткого посилання; необов'язкові власний псевдонім і термін дії; базова статистика переходів.
- Нефункціональні: перенаправлення мають бути швидкими (p99 < 50 мс) і високодоступними; читань ≫ записів (100:1); приватні посилання не повинні вгадуватися.
- Масштаб (припустимо): 10 млн нових посилань на місяць, 1 млрд перенаправлень на місяць ≈ 400 перенаправлень/с у середньому, піки ×10.

## 2. API

```http
POST /api/links        { "url": "https://…", "alias": null, "expiresAt": null }
→ 201 Created          { "code": "q0U", "shortUrl": "https://sho.rt/q0U" }

GET /q0U               → 301 Moved Permanently / 302 Found, Location: https://…
GET /api/links/q0U/stats
```

301 кешується браузерами (менше звернень, але ви втрачаєте підрахунок переходів); 302 щоразу повертається до вас.

## 3. Генерація кодів

| Підхід | Переваги | Недоліки |
|---|---|---|
| Автоінкрементний id → **Base62** | коротко, без колізій, просто | послідовні = вгадувані; один лічильник важко масштабувати (діапазони на екземпляр або id у стилі Snowflake) |
| Випадкові 7 символів | не вгадуються | перевірка колізій під час вставлення (унікальний індекс + повтор) |
| Хеш URL (перші символи SHA-256) | той самий URL → той самий код | колізії треба обробляти; персональні посилання різних користувачів відрізняються |

62⁷ ≈ 3,5 трильйона кодів — 7 символів більш ніж досить.

## 4. Сховище й кешування

- Шаблон доступу «ключ-значення»: `code → url`. Реляційна таблиця з унікальним індексом на `code` (і на `url`, якщо потрібна ідемпотентність) цілком підходить для такого масштабу; DynamoDB / Cosmos DB / Cassandra — для значно більшого.
- Поставте **кеш** (Redis плюс кеш у пам'яті процесу) попереду: більшість трафіку йде на невелику кількість «гарячих» посилань. Cache-aside: читаємо кеш → у разі промаху читаємо БД і заповнюємо кеш.
- Статистика переходів: не оновлюйте рядок-лічильник на кожному перенаправленні; публікуйте події в чергу/потік і агрегуйте асинхронно.

## 5. Масштабування й надійність

- Сервіс перенаправлень без стану за балансувальником, багато екземплярів; CDN/edge може навіть сам віддавати перенаправлення.
- Репліки бази для читання; шардинг за кодом за потреби.
- Обмеження частоти створення посилань (зловживання, спам); валідація й перевірка цільових URL (фішинг).
- Прострочені посилання: TTL у сховищі або фонова задача очищення.

## 6. Що слухає інтерв'юер

Чи спершу питаєте про масштаб, чи чіткий API, чи обґрунтований вибір генерації кодів, чи шлях читання починається з кешу, і чи знаєте компроміси (301 чи 302, вгадувані чи випадкові коди, узгодженість статистики). Практика реалізує ядро: кодування Base62 та ідемпотентний `Shorten`.
