**Головний потік** браузера виконує ваш JavaScript, обробляє введення, а також рахує стилі, розкладку й відмальовування. Задача на 300 мс (розбір великого файлу, обробка зображень, важкий пошуковий індекс, підсвічування синтаксису) блокує все це: кліки запізнюються, анімації смикаються, а Interaction to Next Paint погіршується. **Web Worker** виконує JavaScript в окремому потоці, тож сторінка лишається чуйною.

## Створення worker

```js
// main.js
const worker = new Worker(new URL("./search.worker.js", import.meta.url), { type: "module" });
worker.postMessage({ type: "query", text: "react" });
worker.onmessage = (event) => render(event.data);
worker.onerror = (event) => console.error(event.message);

// search.worker.js
self.onmessage = (event) => {
  const results = runExpensiveSearch(event.data.text);
  self.postMessage(results);
};
```

Форму `new URL(…, import.meta.url)` розуміють Vite і webpack, які збирають файл worker окремо. `worker.terminate()` негайно його зупиняє.

## Що worker може і чого не може

Worker має власну глобальну область (`self`), цикл подій і пам'ять. Він **може** використовувати `fetch`, WebSocket, IndexedDB, таймери, `crypto`, WebAssembly й `OffscreenCanvas`. Він **не може** звертатися до DOM, `window` чи `localStorage`. Уся взаємодія відбувається через повідомлення.

| Вид | Область | Типове використання |
| --- | --- | --- |
| Dedicated worker | одна сторінка | важкі обчислення для цієї сторінки |
| Shared worker | усі вкладки того самого джерела | одне спільне з'єднання чи кеш для вкладок |
| Service worker | мережевий проксі для області, працює без відкритих сторінок | офлайн-кешування, push, фонова синхронізація |

## Повідомлення: структуроване клонування й передача

`postMessage` копіює дані **алгоритмом структурованого клонування**. Він підтримує звичайні об'єкти, масиви, `Date`, `Map`, `Set`, `RegExp`, типізовані масиви, `Blob` і циклічні посилання, але **не** функції чи DOM-вузли (вони кидають `DataCloneError`), а екземпляри класів приходять як звичайні об'єкти без прототипу й методів.

Копіювання не безкоштовне: надсилання масиву на 100 МБ клонує 100 МБ у потоці-відправнику. Для двійкових даних **передавайте** володіння:

```js
const buffer = new ArrayBuffer(50_000_000);
worker.postMessage(buffer, [buffer]); // переміщено, а не скопійовано
buffer.byteLength; // 0: головний потік більше не може ним користуватися
```

Передавати можна `ArrayBuffer`, `MessagePort`, `ImageBitmap`, `OffscreenCanvas` і потоки.

## Запит/відповідь через повідомлення (RPC)

Повідомлення однобічні, тож запит/відповідь потребує протоколу: давайте кожному запиту **id**, тримайте мапу промісів, що очікують, і виконуйте той, чий id повернувся. Без id два одночасні запити можуть отримати відповіді одне одного. Додайте тайм-аути й повідомлення про помилки. **Comlink** загортає все це, тож можна писати `await api.search("react")` для worker так, ніби він локальний.

## Спільна пам'ять

`SharedArrayBuffer` дає потокам спільну пам'ять, а `Atomics` дозволяють безпечно її оновлювати й чекати, що корисно для потоків WebAssembly й аудіо в реальному часі. Після Spectre він доступний лише тоді, коли сторінка **ізольована між джерелами**: віддавайте її з `Cross-Origin-Opener-Policy: same-origin` і `Cross-Origin-Embedder-Policy: require-corp` (або `credentialless`). Перевіряйте `crossOriginIsolated` під час виконання.

## Патерни й пастки

- **Пул worker**: створіть приблизно `navigator.hardwareConcurrency - 1` worker і роздавайте задачі з черги, замість створювати worker на кожну задачу (запуск коштує десятки мілісекунд і пам'ять).
- **Прогрес частинами**: надсилайте повідомлення про прогрес для довгих задач і підтримуйте скасування (`terminate()` чи повідомлення «cancel»).
- **Не зловживайте**: для коротких задач клонування даних і координація коштують більше, ніж заощаджують. Спершу вимірюйте, потім пробуйте алгоритмічні покращення, поділ на частини з поступанням циклу чи `requestIdleCallback`.
- **Помилки** всередині worker не потрапляють у ваш `try/catch` у головному потоці: слухайте `error` і `messageerror` і явно надсилайте відповіді з помилками.
- **OffscreenCanvas** переносить рендеринг (графіки, карти, ігри) у worker: `canvas.transferControlToOffscreen()` і надішліть його в worker.

## Що перевірити перед співбесідою

- Поясніть, чому довгі задачі в головному потоці шкодять чуйності і як допомагають worker.
- Порівняйте dedicated, shared і service worker.
- Поясніть обмеження структурованого клонування й transferable-об'єкти.
- Спроєктуйте протокол запит/відповідь з id, помилками й тайм-аутами.
- Поясніть вимоги до `SharedArrayBuffer` і коли worker не варті накладних витрат.
