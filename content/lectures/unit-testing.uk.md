Хороші тести дозволяють змінювати код без страху. Інтерв'юери шукають тести, що перевіряють **поведінку**, швидкі й детерміновані та падають з однієї зрозумілої причини.

## Анатомія тесту

```ts
describe("formatPrice", () => {
  it("formats cents as a currency string", () => {
    // Arrange (підготовка)
    const cents = 123456;
    // Act (дія)
    const text = formatPrice(cents, "USD");
    // Assert (перевірка)
    expect(text).toBe("$1,234.56");
  });
});
```

- Одна поведінка на тест, а назва читається як специфікація.
- Перевіряйте граничні випадки: порожній вхід, нуль, від'ємні числа, межі, некоректні дані.
- Уникайте логіки (циклів, умов) у тестах. Обирайте таблиці `it.each`.

## Піраміда (або «кубок») тестування

Багато швидких **модульних** тестів для чистої логіки, міцний шар **інтеграційних/компонентних** тестів і кілька **наскрізних (e2e)** тестів для критичних сценаріїв (Playwright, Cypress). Статичні типи й лінтинг безкоштовно ловлять цілий клас помилок.

## Тестові дублери

| Дублер | Призначення |
| --- | --- |
| **Stub (заглушка)** | повертає заготовлені відповіді (`getUser → { id: 1 }`) |
| **Mock / spy (шпигун)** | записує виклики, щоб їх перевірити (`expect(send).toHaveBeenCalledWith(...)`) |
| **Fake (фейк)** | робоча спрощена реалізація (репозиторій у пам'яті) |

Проєктуйте код тестованим через **впровадження залежностей** (годинник, HTTP-клієнт, сховище) замість імпорту їх глибоко всередині коду:

```ts
export function isExpired(token: Token, now = Date.now) {
  return token.expiresAt < now();
}
// у тесті: isExpired(token, () => 1_000)
```

Надмірне мокання є поганою ознакою: якщо тест мокає все, він тестує моки. Мокайте на межах (мережа, час, випадковість), а не власні внутрішні функції.

## Асинхронний код і час

```ts
it("retries once", async () => {
  const fetcher = vi.fn().mockRejectedValueOnce(new Error("down")).mockResolvedValue("ok");
  await expect(loadWithRetry(fetcher)).resolves.toBe("ok");
  expect(fetcher).toHaveBeenCalledTimes(2);
});
```

Завжди використовуйте `await` (або повертайте проміс), інакше тест пройде раніше, ніж виконається перевірка. Для debounce, повторних спроб і тайм-аутів беріть фейкові таймери (`vi.useFakeTimers()`, `jest.useFakeTimers()`), щоб тести лишалися швидкими й детермінованими.

## Тестування UI

Перевіряйте те, що користувач бачить і робить, а не деталі реалізації:

```tsx
render(<Login />);
await user.type(screen.getByLabelText("Email"), "a@b.co");
await user.click(screen.getByRole("button", { name: "Sign in" }));
expect(await screen.findByText("Welcome back")).toBeInTheDocument();
```

Шукайте елементи спершу за **роллю й доступним ім'ям**, потім за міткою, потім за текстом. `data-testid` є крайнім засобом. Це ще й підштовхує до доступної розмітки. Не перевіряйте внутрішній стан чи назви CSS-класів.

## Покриття

Покриття показує, що було **виконано**, а не що було **перевірено**. Прагніть змістовного покриття бізнес-логіки, а не 100% усього.

## Чек-лист для співбесіди

- Напишіть зрозумілий тест arrange-act-assert з граничними випадками.
- Поясніть різницю між стабами, моками й фейками та впроваджуйте залежності, щоб код був тестованим.
- Тестуйте асинхронний код і таймери без нестабільності.
- Шукайте компоненти за роллю й міткою, як це робив би користувач.
