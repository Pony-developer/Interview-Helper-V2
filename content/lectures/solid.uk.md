SOLID складається з п'яти принципів проєктування коду, який легко змінювати. Їх сформулювали для класів, але вони так само стосуються функцій, модулів, хуків і компонентів. Сприймайте їх як підказки, що допомагають помітити проблеми, а не як правила, які треба застосовувати всюди.

## S: Єдиний обов'язок (Single responsibility)

Модуль повинен мати **одну причину для змін**: обслуговувати одного «актора» чи одну задачу.

```tsx
// ✗ отримує дані, валідує, форматує гроші, відстежує аналітику й рендерить
function InvoicePage() { /* 300 рядків */ }

// ✓ кожна частина змінюється зі своєї причини
const invoice = useInvoice(id);          // отримання даних
const rows = toInvoiceRows(invoice);     // чисте форматування, легко тестувати
return <InvoiceTable rows={rows} />;     // відображення
```

Перевірка: перелічіть причини, з яких код може змінитися (формат API, правила валют, дизайн). Якщо один файл змінюється через усі, розділіть його.

## O: Відкритість/закритість (Open/closed)

Код має бути **відкритим для розширення й закритим для змін**: нова можливість не повинна вимагати правок робочого коду в багатьох місцях. `switch (method)`, повторений у п'яти файлах, порушує це; реєстр стратегій (`paymentMethods[method].charge()`), пропси на кшталт `renderItem` чи хуки плагінів залишають ядро незмінним.

## L: Підстановка Лісков (Liskov substitution)

Підтип має працювати **будь-де**, де очікують базовий тип, і викликачі не повинні цього помічати. Класичне порушення: `Square extends Rectangle`: код, що задає ширину й висоту незалежно, ламається. Підкласи не повинні:

- вимагати більшого від вхідних даних (кидати помилку для аргументів, які приймала база),
- обіцяти менше у вихідних даних (повертати `null` там, де база ніколи не повертала),
- кидати «не підтримується» для успадкованих методів.

Якщо підклас не може виконати контракт, він не повинен бути підкласом.

## I: Розділення інтерфейсів (Interface segregation)

Клієнти не повинні залежати від методів, якими не користуються. Кілька невеликих зосереджених інтерфейсів кращі за один «товстий»:

```ts
interface Readable<T> { get(id: string): Promise<T | undefined> }
interface Writable<T> { save(item: T): Promise<void> }
function ProfileCard(props: { user: Pick<User, "name" | "avatarUrl"> }) { … }
```

Компонент, що приймає лише поля, які показує, легше повторно використати й протестувати, ніж той, що вимагає весь об'єкт `User`.

## D: Інверсія залежностей (Dependency inversion)

Високорівнева логіка не повинна залежати від низькорівневих деталей; **обидві залежать від абстракцій**. Замість `new PostgresRepo()` усередині сервісу приймайте інтерфейс `ReportRepo`, а конкретну реалізацію під'єднуйте на краю застосунку (провайдер в Angular, контекст у React, фабрика в `main.ts`). Тести передають фейки; продакшен може змінити сховище, не чіпаючи бізнес-логіку.

## DRY, KISS, YAGNI

- **DRY** (Don't Repeat Yourself) стосується дублювання *знань*, а не схожого на вигляд коду. Два однакові фрагменти, що змінюються з різних причин, краще лишити окремими.
- **KISS**: обирайте найпростіший дизайн, що працює.
- **YAGNI** (You Aren't Gonna Need It): не додавайте інтерфейси, фабрики й параметри під гіпотетичне майбутнє. Вводьте абстракцію, коли друга реалізація чи точка підміни для тестів справді потрібна.

## Що перевірити перед співбесідою

- Сформулюйте кожен принцип одним реченням і наведіть приклад із фронтенду.
- Поясніть, чому `Square extends Rectangle` порушує LSP.
- Покажіть, як реєстр стратегій задовольняє принцип відкритості/закритості.
- Поясніть інверсію залежностей і як вона робить код тестованим.
- Аргументуйте через YAGNI, чому SOLID не варто застосовувати надмірно.
