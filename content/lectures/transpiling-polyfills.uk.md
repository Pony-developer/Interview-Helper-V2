JavaScript розвивається щороку, але браузери ваших користувачів оновлюються не одночасно. Розрив закривають два окремі інструменти, і на співбесідах часто перевіряють, чи знаєте ви, яку проблему розв'язує кожен.

## Синтаксис проти API

- **Новий синтаксис** (стрілочні функції, `class`, optional chaining, `async`/`await`, приватні поля): старий рушій навіть не може **розібрати** файл, тож увесь скрипт падає з `SyntaxError`. Його треба **транспілювати**, тобто переписати під час збирання старішим синтаксисом.
- **Нові API** (`Array.prototype.at`, `Object.groupBy`, `structuredClone`, `Promise.withResolvers`): код розбирається, але виклик відсутньої функції кидає `TypeError` під час виконання. Їх можна **поліфілити**, тобто додати під час виконання кодом, що їх реалізує.

Деякі можливості не може повністю забезпечити жоден із них: `Proxy`, точна семантика приватних полів, `WeakRef` і деякі можливості регулярних виразів (як-от lookbehind) потребують підтримки рушія. Транспілятори приблизно емулюють деякі з них (через `WeakMap` для `#private`), ціною швидкодії й відмінностей у поведінці.

## Транспілятори

Babel, SWC, esbuild і компілятор TypeScript розбирають код в AST, перетворюють вузли, які ціль не підтримує, і знову друкують код разом із **картами коду** (source maps), щоб стеки викликів і налагоджувачі вказували на ваш початковий код.

- `optional?.chain` стає `a === null || a === void 0 ? void 0 : a.chain`.
- `async`-функції стають скінченними автоматами на генераторах (чи кодом regenerator для дуже старих цілей), що більше й повільніше за нативний код.
- Поля класів і `#private` стають присвоєннями в конструкторі й пошуком у `WeakMap`.

Налаштовуйте **цілі** замість перетворення всього: запит `browserslist` (`> 0.5%, last 2 versions, not dead`) чи явні версії кажуть інструментам, що підтримується, тож сучасні браузери не отримують роздутий код. Деякі команди збирають два бандли: сучасні ES-модулі через `<script type="module">` і застарілий бандл через `<script nomodule>`.

## Поліфіли

Поліфіл перевіряє, чи існує можливість, і встановлює реалізацію, якщо ні:

```js
if (!Array.prototype.at) {
  Object.defineProperty(Array.prototype, "at", {
    value: function at(index) {
      const len = this.length >>> 0;
      let i = Math.trunc(index) || 0;
      if (i < 0) i += len;
      return i < 0 || i >= len ? undefined : this[i];
    },
    writable: true,
    configurable: true,
    enumerable: false, // як у вбудованих, тож цикли for…in його не бачать
  });
}
```

Добрі поліфіли близько дотримуються специфікації: вони так само перетворюють аргументи, обробляють крайні випадки (від'ємні й дробові індекси, `NaN`, масивоподібні об'єкти), відповідають `name` і `length`, є **неперелічуваними** й ніколи не перезаписують нативну реалізацію. Поліфіл, що додає перелічувану властивість в `Array.prototype`, ламає кожен `for…in` по масивах, а поліфіл, що встановлює трохи іншу поведінку, може заблокувати справжню можливість (через історію «SmooshGate» `Array.prototype.flatten` став `flat`).

На практиці використовуйте **core-js** з `useBuiltIns: "usage"` у Babel (поліфілить лише те, що використовує ваш код, для ваших цілей) замість написаних вручну. **Поніфіл** (ponyfill) є альтернативою без побічних ефектів: звичайна функція, яку ви імпортуєте (`import at from "array-at"`) і яка не чіпає глобальні об'єкти; вона підходить для бібліотек.

## Визначення можливостей, а не браузера

Перевіряйте саму можливість, а не назву браузера:

```js
if ("IntersectionObserver" in window) observeLazily(images);
else loadAllImages(images);

const supportsHas = CSS.supports("selector(:has(a))");
```

Аналіз user-agent ламається, коли браузери змінюють свої рядки UA (а вони змінюють і заморожують їх), коли браузер додає можливість, і для браузерів, яких ви не перелічили. Визначення можливостей працює для будь-якого рушія. Деякі можливості не можна дешево визначити (синтаксис), тож ви або покладаєтеся на цілі збирання, або визначаєте спробою: `try { new Function("a?.b") }` (не дозволено за суворої CSP).

## Прогресивне покращення

Побудуйте базову версію, що працює всюди, а потім додавайте покращення там, де є можливості: нативне ліниве завантаження атрибутом, `<dialog>` із запасним варіантом, View Transitions лише там, де вони підтримуються. Це дешевше, ніж поліфілити все, і плавно деградує.

## Компроміси

Кожне перетворення й поліфіл коштують байтів, часу розбору, а іноді й швидкодії під час виконання, і платить за це **кожен** користувач, зокрема в сучасних браузерах, якщо ви не розділяєте збирання. Регулярно переглядайте цілі; відмова від дуже старих браузерів часто прибирає більшість витрат. Вимірюйте бандл (наприклад, аналізатором бандлів) до й після.

## Що перевірити перед співбесідою

- Поясніть різницю між синтаксисом і API і який інструмент обробляє кожне.
- Опишіть, що робить транспілятор, зокрема карти коду і як обираються цілі.
- Напишіть поліфіл і перелічіть, що робить його відповідним специфікації й безпечним.
- Поясніть, чому визначення можливостей краще за аналіз user-agent, з прикладом.
- Поясніть ціну транспіляції й поліфілів і як розділені збирання її зменшують.
