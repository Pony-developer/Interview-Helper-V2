GraphQL є мовою запитів для API. Сервер публікує типізовану **схему**; клієнти надсилають запит, що описує саме ті дані, які їм потрібні, зазвичай як `POST` на єдиний ендпоінт `/graphql`, і отримують JSON у формі запиту.

## Чому його обирають

- **Без зайвих і недостатніх даних.** Екран профілю просить лише `name` і `avatarUrl` і отримує користувача, п'ять його останніх дописів і кількість коментарів до кожного за один запит замість кількох викликів REST.
- **Типізований контракт.** Схему можна дослідити (introspection), тож інструменти генерують типи TypeScript, а редактори автодоповнюють запити.
- **Розвиток без версій.** Поля можна вільно додавати, а старі позначати `@deprecated`.

Компроміси: HTTP-кешування й CDN працюють менш природно, вартість запиту важче передбачити, а сервер потребує більше уваги (запити N+1, обмеження).

## Схема й операції

```graphql
type User {
  id: ID!
  name: String!
  email: String          # може бути null
  posts(first: Int = 10): [Post!]!
}
type Query    { user(id: ID!): User }
type Mutation { renamePost(id: ID!, title: String!): Post! }
```

`!` означає «не null». `[Post!]!` є обов'язковим списком обов'язкових дописів. Є три типи операцій: **query** (читання), **mutation** (запис, виконуються по черзі) і **subscription** (потік подій, зазвичай через WebSocket).

```graphql
query Profile($id: ID!) {
  user(id: $id) { name posts(first: 5) { id title } }
}
```

Завжди передавайте вхідні дані як **змінні** (`{ "id": "42" }`), а не вставляйте їх у текст запиту. Так ви уникаєте ін'єкцій у запит, сервер може перевірити типи, а текст запиту лишається сталим, що дає змогу використовувати збережені запити (persisted queries) і кешування.

## Резолвери й виконання

Кожне поле має **резолвер** `(parent, args, context) => value`. Виконання обходить запит: `Query.user` повертає користувача, потім `User.posts` виконується з ним як `parent` і так далі. Поля одного рівня розв'язуються паралельно.

Наївні резолвери спричиняють **проблему N+1**: один запит за 50 дописами, а потім `Post.author` виконується 50 разів і робить ще 50 запитів. Стандартне розв'язання: **DataLoader**. Протягом одного «тіку» він збирає всі виклики `load(id)`, робить один пакетний запит (`WHERE id IN (…)`) і кешує результати в межах запиту.

## Помилки й обов'язковість

Відповідь GraphQL зазвичай має HTTP-статус `200`, навіть якщо щось не вдалося:

```json
{ "data": { "user": null }, "errors": [{ "message": "…", "path": ["user", "name"] }] }
```

Клієнти мають перевіряти `errors`, а не лише код статусу. Коли падає **обов'язкове** поле, його `null` піднімається до найближчого батька, що може бути null: якщо `User.name: String!` кидає помилку, весь `user` стає `null`. Робіть поля необов'язковими там, де часткові результати прийнятні, щоб одне поле з помилкою не знищило весь екран.

## Кешування на клієнті

Apollo Client і urql (Graphcache) мають **нормалізований кеш**: кожен об'єкт зберігається один раз під ключем `__typename:id`. Мутація, що повертає `id` і змінені поля об'єкта, автоматично оновлює кожен запит, який його показує. Зі створенням і видаленням інакше: кеш не знає, які списки мають змінитися, тож ви оновлюєте їх самі (`cache.modify`, `update`) або повторно виконуєте відповідні запити. Завжди запитуйте `id`, щоб об'єкти можна було нормалізувати.

## Захист сервера

Один запит може попросити дуже багато: глибоко вкладені зв'язки (`posts { author { posts { author … } } }`) чи величезні списки. Засоби захисту:

- обмежувати **глибину** запиту й оцінену **складність/вартість**;
- обмежувати розміри списків і використовувати пагінацію (`first`, курсори `after`);
- дозволяти лише **збережені запити** (білий список відомих операцій) для власних клієнтів;
- вимикати introspection у продакшені, якщо схема приватна, і обмежувати частоту запитів за вартістю, а не лише за кількістю.

## Що перевірити перед співбесідою

- Порівняйте GraphQL і REST, зокрема щодо кешування й обробки помилок.
- Прочитайте схему: що означають `!` і `[T!]!`; query, mutation і subscription.
- Поясніть резолвери, проблему N+1 і як її розв'язує DataLoader.
- Поясніть часткові дані з `errors` і поширення null.
- Опишіть нормалізований кеш і чому нові елементи не з'являються в списках автоматично.
