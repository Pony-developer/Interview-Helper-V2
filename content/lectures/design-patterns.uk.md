Патерн проєктування є **іменованим, повторно використовуваним розв'язком типової задачі проєктування**. Його цінність у спільному словнику: «зроби це стратегією» чи «це адаптер» кажуть багато кількома словами. У JavaScript багато класичних патернів (Gang of Four) зводяться до функції чи літерала об'єкта, тож на співбесідах важливіше *впізнавати* їх і розуміти компроміси, ніж малювати UML.

## Твірні: як створюються об'єкти

- **Singleton.** Один спільний екземпляр. У JS модуль ES виконується один раз, тож `export const api = new ApiClient()` уже є синглтоном. Мінус у прихованому глобальному стані, через який тести впливають один на одного; краще передавати екземпляр явно.
- **Factory.** Функція, що вирішує, який об'єкт створити: `createLogger(env)` повертає консольний логер у розробці й віддалений у продакшені. Викликачі залежать від інтерфейсу, а не від конкретного класу.
- **Builder.** Збирає складний об'єкт крок за кроком (`new QueryBuilder().where(...).limit(10).build()`).

## Структурні: як об'єкти поєднуються

- **Adapter.** Перетворює один інтерфейс на той, якого очікує ваш код, наприклад ховає два SDK аналітики за однаковим `track(event, props)`.
- **Facade.** Простий фасад для складної підсистеми: один `uploadAvatar(file)`, що змінює розмір, отримує підписаний URL і завантажує файл.
- **Decorator.** Додає поведінку, **обгортаючи** оригінал і не змінюючи його: `withRetry(fetchJson)`, компоненти вищого порядку в React, `@decorators` у TypeScript/Angular. Обгортки комбінуються (`withCache(withRetry(fetchJson))`), а підклас на кожну комбінацію швидко множиться.
- **Proxy.** Заступник об'єкта, що контролює доступ. Вбудований у JavaScript `Proxy` перехоплює читання й запис; на ньому побудовані реактивність Vue і MobX.

```ts
const withRetry = <A extends unknown[], R>(fn: (...a: A) => Promise<R>, times = 3) =>
  async (...args: A): Promise<R> => {
    for (let i = 1; ; i++) {
      try { return await fn(...args); } catch (e) { if (i >= times) throw e; }
    }
  };
```

## Поведінкові: як об'єкти взаємодіють

- **Observer / pub-sub.** Суб'єкт сповіщає підписників: події DOM, `EventEmitter`, RxJS, підписки на стор. Завжди надавайте (і викликайте) відписку, інакше буде витік пам'яті; і перебирайте копію списку підписників на випадок, якщо хтось відпишеться під час сповіщення.
- **Strategy.** Підміна алгоритму за спільним інтерфейсом. Мапа функцій замінює `switch`, що постійно росте:

```ts
const shipping: Record<Method, (order: Order) => number> = {
  standard: (o) => 5,
  express: (o) => 15,
  free: () => 0,
};
const cost = shipping[order.method](order);
```

- **Command.** Загортає дію в об'єкт з `execute` і `undo`. Стек виконаних команд дає скасування/повтор, черги й макроси.
- **Ланцюжок відповідальності / middleware.** Запит проходить крізь список обробників, кожен з яких обробляє його, змінює або викликає `next()`: middleware в Express і Koa, middleware Redux, HTTP-інтерсептори.
- **Iterator.** Єдиний спосіб обходу колекції: `Symbol.iterator`, генератори, `for…of`.

## Впровадження залежностей (DI)

Замість того щоб створювати співпрацівників самостійно, клас отримує їх: `constructor(private http: HttpClient)`. В Angular вбудований DI-контейнер; у React ту саму роль виконують контекст і пропси. Виграш у тестованості (можна передати фейк) і змінних реалізаціях. Це «D» у SOLID: залежати від абстракцій, а не від конкретики.

## Коли патерн не потрібен

Патерни додають непрямість. Мапа стратегій для двох випадків чи фабрика, що завжди повертає один клас, лише шум. Беріть патерн, коли задача, яку він розв'язує, справжня (третій спосіб доставки вже планують, SDK справді може змінитися), і називайте його в code review, щоб намір був зрозумілим.

## Що перевірити перед співбесідою

- Впізнавайте Observer, Strategy, Decorator, Adapter, Facade, Proxy, Command і middleware в реальних API.
- Поясніть, чому синглтони на рівні модуля шкодять тестам і як допомагає DI.
- Опишіть, як реалізувати скасування/повтор через команди.
- Поясніть різницю між Adapter (змінює інтерфейс) і Facade (спрощує підсистему).
