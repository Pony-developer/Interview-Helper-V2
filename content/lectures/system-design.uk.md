На співбесіді з frontend system design вас просять за 45–60 хвилин спроєктувати щось на кшталт «стрічки новин», «автодоповнення», «Google Docs» чи «фотогалереї». Єдиної правильної відповіді немає: інтерв'юери шукають **структурований підхід**, розумні компроміси й глибину там, де це важливо. Надійний каркас: **RADIO**: Requirements (вимоги), Architecture (архітектура), Data model (модель даних), Interface (API), Optimisations (оптимізації).

## 1. Вимоги (5–10 хвилин)

Ніколи не починайте малювати одразу. Уточніть:

- **Функціональні**: основні сценарії користувача. Для стрічки: перегляд дописів, нескінченна прокрутка, вподобання, коментарі, створення допису із зображеннями.
- **Нефункціональні**: пристрої (мобільний веб?), очікуваний масштаб (дописів на сторінку, зображень), цілі продуктивності, офлайн-підтримка, доступність, інтернаціоналізація, потреби SEO.
- **Поза межами**: явно скажіть, чого не розглядатимете (алгоритм ранжування, зберігання на бекенді).

Запишіть погоджений список; це ваш чекліст на решту співбесіди.

## 2. Архітектура

Накидайте основні частини й потік даних:

```
Сервер/API ⇄ Шар даних (отримання, кеш, нормалізація)
                 ⇅
           Клієнтський стор (стан UI, оптимістичні оновлення)
                 ⇅
   View: <FeedPage> → <FeedList> → <Post> → <LikeButton>, <CommentBox>
```

Оберіть **стратегію рендерингу** й поясніть чому: серверний рендеринг чи статична генерація для SEO й швидкого першого відображення (публічні сторінки), клієнтський рендеринг для автентифікованих екранів у стилі застосунку, потокова передача/часткова гідратація там, де важливе і те, і те. Назвіть обов'язки кожного компонента й де живе стан: серверні дані в кеші запитів, стан UI локально, спільний клієнтський стан у сторі, фільтри в URL.

## 3. Модель даних

Опишіть сутності, які тримає клієнт, і як вони нормалізовані:

```ts
type Post = { id: string; authorId: string; text: string; media: Media[]; likeCount: number; likedByMe: boolean; createdAt: string };
type FeedState = { postIds: string[]; postsById: Record<string, Post>; usersById: Record<string, User>; cursor: string | null; status: "idle" | "loading" | "error" };
```

Нормалізація (сутності за id плюс списки id) означає, що вподобаний допис оновлюється всюди, де він з'являється.

## 4. Інтерфейс (API)

Визначте контракти між клієнтом і сервером:

- `GET /feed?cursor=…&limit=20` → `{ posts, users, nextCursor }`. **Пагінація з курсором** стабільна, коли з'являються нові дописи; пагінація зі зсувом дублює чи пропускає елементи.
- `POST /posts/:id/like` з **оптимістичними оновленнями**: оновити UI одразу, відкотити при помилці.
- Реальний час: нові дописи через SSE чи WebSocket, показані банером «12 нових дописів», а не зсувом списку під пальцем користувача.
- REST чи GraphQL: згадайте компроміс, якщо доречно (зайві дані проти складності кешування).

## 5. Оптимізації та поглиблення

Оберіть важливе для продукту й заглибтеся:

- **Продуктивність**: віртуалізація довгих стрічок, `srcset` для зображень, ліниве завантаження й фіксовані пропорції (без зсуву макета), розбиття коду (завантажувати редактор допису лише при відкритті), попереднє завантаження наступної сторінки ближче до кінця, debounce/throttle для пошуку й прокрутки.
- **Мережа**: кешування й дедуплікація запитів, повторні спроби з наростанням затримки, скасування запитів (`AbortController`), коли змінюються вхідні дані.
- **Стійкість**: скелетони завантаження, стани помилок із повтором, часткові збої, офлайн-черга для вподобань і коментарів.
- **Доступність**: навігація стрічкою з клавіатури, керування фокусом після підвантаження, `aria-live` для банерів нового вмісту, alt-текст для медіа.
- **Безпека**: екранування вмісту користувачів (XSS), захист мутацій від CSRF, перевірка завантажень.
- **i18n**: розширення тексту, макети RTL, дати й числа з урахуванням локалі.
- **Спостережуваність**: Web Vitals, відстеження помилок, feature flags для поступового розгортання.

## Типові завдання та їхні ключові теми

| Завдання | Ключові теми |
| --- | --- |
| Автодоповнення | debounce, скасування застарілих запитів, кешування результатів, навігація клавіатурою й ARIA combobox |
| Стрічка новин | пагінація з курсором, віртуалізація, оптимістичні вподобання, оновлення в реальному часі |
| Чат | WebSocket, порядок і id повідомлень, офлайн-черга, позначки прочитання |
| Спільний редактор | розв'язання конфліктів (CRDT чи operational transforms), присутність, скасування |
| Карусель / галерея | ліниве завантаження, адаптивні зображення, попереднє завантаження сусідніх, свайпи й клавіатура |
| Панель керування | стратегія отримання даних, опитування чи push, продуктивність графіків, збереження макета |

## Як виступити добре

- Ведіть розмову, але звіряйтеся: «Заглибитися в пагінацію чи рухатися далі?»
- Явно називайте компроміси («віртуалізація ускладнює пошук на сторінці й доступність; варто того понад кілька сотень елементів»).
- Лишайте час на поглиблення; не витрачайте 30 хвилин на дерево компонентів.
- Прив'язуйте кожне рішення до вимог, записаних на початку.

## Що перевірити перед співбесідою

- Використовуйте каркас (RADIO) і спершу уточнюйте вимоги.
- Оберіть і обґрунтуйте стратегію рендерингу.
- Спроєктуйте нормалізований клієнтський стан і API з пагінацією через курсор.
- Обговоріть оптимістичні оновлення, оновлення в реальному часі й стани помилок.
- Охопіть продуктивність, доступність і безпеку для обраного продукту.
