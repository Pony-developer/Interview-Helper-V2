Більшість вебатак використовують одне з двох: браузер виконує код, який контролює зловмисник (**XSS**), або браузер надсилає облікові дані користувача в запиті, який ініціював зловмисник (**CSRF**). Політика одного джерела (same-origin policy) є базовим захистом; усе інше зводиться до того, щоб її не підривати.

## Міжсайтовий скриптинг (XSS)

XSS означає, що скрипт зловмисника виконується **у вашому джерелі** з доступом до DOM, `localStorage` і сесії користувача. Буває три види: *збережений* (шкідливий коментар у базі даних), *відбитий* (сервер повертає його з URL) і *DOM-based* (ваш власний JavaScript записує неперевірені дані в небезпечне місце).

Небезпечні місця називають **стоками** (sinks):

| Сток | Безпечна альтернатива |
| --- | --- |
| `el.innerHTML = input`, `insertAdjacentHTML`, `document.write` | `textContent`, `createElement` |
| `location.href = input`, `<a href={input}>` | перевіряти протокол (`https:`, `http:`, `mailto:`) |
| `eval`, `new Function`, `setTimeout("рядок")` | передавати функції, ніколи рядки |
| `dangerouslySetInnerHTML` у React, `bypassSecurityTrust*` в Angular | спершу санітизувати (DOMPurify) або уникати |

**Екрануйте на виході й відповідно до контексту.** Текст у HTML потребує кодування `& < > " '`; значення в URL потребує перевірки протоколу й `encodeURIComponent`; усередині блоку `<script>` інтерполяції краще уникати взагалі. React, Angular і Vue екранують текст за замовчуванням, тож лишаються діри в значеннях `href` і явних API «обходу».

```tsx
// React екранує текст, але не це:
<a href={user.website}>{user.name}</a> // "javascript:alert(1)" виконається при кліку
```

**Екранування проти санітизації.** Екранування перетворює розмітку на безпечний текст. Санітизація зберігає *частину* розмітки (жирний шрифт, посилання) і вирізає решту; використовуйте підтримувану бібліотеку на кшталт DOMPurify, а не саморобний регулярний вираз.

## Content Security Policy

CSP є HTTP-заголовком, що каже браузеру, з яких джерел можна виконувати код. `script-src 'self'` блокує вбудовані скрипти й атрибути `on*`, вставлені через XSS, якщо ви не додали `'unsafe-inline'`. Для потрібних вбудованих скриптів використовуйте nonce або хеші, а також `object-src 'none'`, `base-uri 'none'` і `frame-ancestors 'none'` проти клікджекінгу (сучасна заміна `X-Frame-Options`). CSP є додатковим рівнем захисту, а не заміною екранування.

## CSRF і cookie

Якщо автентифікація тримається на cookie, шкідлива сторінка може змусити браузер їх надіслати: `<form action="https://bank.example/transfer" method="POST">`, яку автоматично відправляють з іншого сайту.

- `SameSite=Lax` (типове значення в сучасних браузерах) не надсилає cookie у міжсайтових підзапитах і POST; `Strict` також при переходах верхнього рівня.
- CSRF-токени або вимога власного заголовка (що змушує робити CORS preflight) захищають ендпоінти, які змінюють стан.
- Ніколи не змінюйте стан через `GET`.

Прапорці cookie: `HttpOnly` ховає cookie від JavaScript (XSS не може його **прочитати**, але може робити автентифіковані запити зі сторінки), `Secure` надсилає його лише через HTTPS, а `SameSite` обмежує міжсайтове надсилання.

## Що таке CORS (і чим він не є)

Політика одного джерела не дає сторінці **читати** відповіді з інших джерел. Заголовки CORS (`Access-Control-Allow-Origin`) дозволяють серверу **послабити** це для вибраних джерел. CORS не захищає сервер: прості запити (POST як із форми) все одно надсилаються, і сервер їх виконує. Ніколи не віддзеркалюйте будь-який `Origin` разом з `Access-Control-Allow-Credentials: true`.

## Токени і де їх зберігати

Усе в `localStorage` може прочитати будь-який скрипт на сторінці, тож одна XSS-вразливість зливає довгоживучі токени. Краще тримати короткоживучі access-токени в пам'яті, а refresh-токен у cookie з `HttpOnly; Secure; SameSite`. Так чи інакше, поки працює код зловмисника, XSS означає втрату сесії; від способу зберігання залежить лише те, чи зможе зловмисник забрати токен із собою.

## Інші ризики фронтенду

- **Відкриті перенаправлення.** `/login?next=https://evil.example` використовують для фішингу. Дозволяйте лише відносні шляхи того самого джерела: розберіть через `new URL(next, location.origin)` і порівняйте origin (`//evil.example` теж починається з `/`).
- **Reverse tabnabbing.** Посиланням з `target="_blank"` додавайте `rel="noopener noreferrer"` (сучасні браузери мають `noopener` за замовчуванням).
- **Ланцюжок постачання.** Lock-файли, `npm audit`, мінімум залежностей і Subresource Integrity (`integrity="sha384-…"`) для сторонніх скриптів.
- **Секрети в бандлі.** Усе, що потрапляє в браузер, публічне, зокрема «приховані» API-ключі.

## Що перевірити перед співбесідою

- Дайте визначення XSS, назвіть три стоки й поясніть, як фреймворки вас захищають.
- Поясніть, чому `HttpOnly` не заважає XSS діяти від імені користувача.
- Поясніть CSRF і як його зупиняють `SameSite` і токени.
- Скажіть, що контролює CORS і чому це не механізм контролю доступу.
- Правильно перевірте ціль перенаправлення й URL посилання від користувача.
