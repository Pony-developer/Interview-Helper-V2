Питання про Git перевіряють, чи вмієте ви працювати в команді, не втрачаючи роботи, і чи зможете відновитися, коли щось пішло не так.

## Модель в одному абзаці

**Коміт** є знімком проєкту разом із метаданими й посиланням на батьківський коміт(и). **Гілка** є лише рухомою назвою, що вказує на коміт. `HEAD` показує, де ви зараз. Ваша робота проходить три зони: **робоча копія** → **індекс (staging)** (`git add`) → **репозиторій** (`git commit`).

## Щоденний процес

```bash
git switch -c feature/search      # нова гілка від поточного коміту
git add -p                        # інтерактивно додати фрагменти в індекс
git commit -m "feat: add search box"
git fetch origin
git rebase origin/main            # перенести ваші коміти на свіжий main
git push -u origin feature/search # відкрити pull request
```

Робіть невеликі сфокусовані коміти з повідомленнями, що пояснюють **чому**. Conventional Commits (`feat:`, `fix:`) допомагають зі списками змін.

## Merge проти rebase

- **Merge** об'єднує історії комітом злиття. Він нічого не руйнує й точно показує, що сталося, але історія може стати захаращеною.
- **Rebase** відтворює ваші коміти поверх іншої гілки. Історія стає лінійною, але коміти отримують **нові хеші**.

Золоте правило: **не робіть rebase комітів, які вже є в інших** (спільні/публічні гілки). Rebase власної локальної гілки перед PR цілком нормальний. Squash-merge PR дає в `main` один коміт на функцію.

## Конфлікти

Конфлікти виникають, коли обидві сторони змінили ті самі рядки. Git позначає їх:

```
<<<<<<< HEAD
const limit = 10;
=======
const limit = 20;
>>>>>>> feature
```

Визначте правильний код (він може поєднувати обидві сторони), приберіть маркери, запустіть тести, потім `git add` і продовжте операцію (`git merge --continue` або `git rebase --continue`).

## Скасування змін

| Ситуація | Команда |
| --- | --- |
| Відкинути неіндексовані зміни у файлі | `git restore file` |
| Прибрати файл з індексу | `git restore --staged file` |
| Виправити останній коміт (ще не відправлений) | `git commit --amend` |
| Безпечно скасувати відправлений коміт | `git revert <sha>` (створює обернений коміт) |
| Повернути гілку назад, зберігши зміни | `git reset --soft HEAD~1` |
| Викинути коміти **локально** | `git reset --hard <sha>` (небезпечно) |
| «Я втратив коміт!» | `git reflog`, потім гілка від старого sha |

`revert` безпечний для спільної історії. `reset` її переписує. `git stash` тимчасово відкладає незавершену роботу.

## Пошук помилок

`git bisect` бінарним пошуком знаходить в історії коміт, що вніс помилку. `git blame` (або `git log -p -S "text"`) показує, коли й чому змінився рядок.

## Чек-лист для співбесіди

- Поясніть різницю між merge і rebase та золоте правило rebase.
- Розв'яжіть конфлікт і продовжте операцію.
- Оберіть між `revert` і `reset` та відновіться через `reflog`.
- Опишіть процес роботи з гілками й PR у вашій команді.
