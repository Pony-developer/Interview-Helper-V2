Більшість помилок UI є помилками стану: дві копії, що не збігаються, непомічена мутація або значення, яке слід було обчислити. Добре керування станом зводиться переважно до того, **де** стан живе і **як** змінюється.

## Види стану

| Вид | Приклади | Зазвичай живе в |
| --- | --- | --- |
| Локальний стан UI | текст поля, відкрито/закрито | стані компонента |
| Спільний клієнтський стан | кошик, тема, поточний користувач | контексті, сторі (Redux, NgRx, Zustand, сигнали) |
| Серверний стан | списки з API | кеші (TanStack Query, RTK Query, SWR), а не в написаному вручну сторі |
| Стан в URL | фільтри, сторінка, вибрана вкладка | URL (можна поділитися, переживає перезавантаження) |
| Стан форми | значення, валідація, торкнуті поля | бібліотеці форм або локальному стані |

Тримайте стан **якомога локальніше** й піднімайте його лише тоді, коли він потрібен сусіднім компонентам. Ставтеся до серверних даних як до кешу зі станами завантаження/помилки/застарілості, а не копіюйте їх у глобальний стор.

## Єдине джерело правди й похідні дані

Зберігайте мінімум, а решту обчислюйте під час рендеру чи в селекторах:

```ts
// ✗ items, total і count зберігаються окремо (вони розходяться)
// ✓ зберігайте items, решту обчислюйте
const total = items.reduce((s, i) => s + i.price * i.qty, 0);
```

Нормалізуйте реляційні дані (мапи `byId` плюс масиви id), щоб кожна сутність існувала один раз.

## Редʼюсери й незмінність

Редʼюсер є чистою функцією `(state, action) => newState`:

```ts
function cartReducer(state: Cart, action: Action): Cart {
  switch (action.type) {
    case "add": {
      const existing = state.items.find((i) => i.id === action.item.id);
      return {
        ...state,
        items: existing
          ? state.items.map((i) => (i.id === action.item.id ? { ...i, qty: i.qty + 1 } : i))
          : [...state.items, { ...action.item, qty: 1 }],
      };
    }
    default:
      return state;
  }
}
```

- **Ніколи не змінюйте стан напряму**: повертайте нові об'єкти чи масиви для всього, що змінилося, і перевикористовуйте посилання на те, що не змінилося. Саме так React, селектори Redux і Angular OnPush дешево виявляють зміни (`prev !== next`).
- Для невідомих дій повертайте той самий об'єкт стану.
- Бібліотеки на кшталт Immer (вбудованої в Redux Toolkit) дозволяють писати «мутуючий» код, що створює незмінні оновлення.

## Селектори

Селектори читають і обчислюють похідний стан (`selectCartTotal`). Мемоізовані селектори (`createSelector`) перераховуються лише при зміні вхідних даних і зберігають стабільні посилання, що позбавляє зайвих ререндерів.

## Побічні ефекти

Тримайте редʼюсери чистими. Запити, таймери й сховища розміщуйте в thunk, sagas, ефектах NgRx чи бібліотеках запитів і надсилайте дії з результатами (`loading` → `success`/`failure`).

## Вибір інструментів

- React: `useState`/`useReducer` + context для невеликого спільного стану; Zustand/Redux Toolkit для більшого клієнтського стану; TanStack Query для серверного стану.
- Angular: сервіси із сигналами чи BehaviorSubject; NgRx для великих застосунків, яким потрібні суворі патерни й devtools.

Не додавайте глобальний стор «про всяк випадок». Додавайте структуру, коли стан широко використовується, складно змінюється або потребує налагодження з «подорожжю в часі».

## Чек-лист для співбесіди

- Класифікуйте стан і вирішіть, де він має жити.
- Напишіть чистий незмінний редʼюсер і поясніть, чому важлива незмінність.
- Обчислюйте дані замість дублювання.
- Відокремлюйте серверний стан (кеш) від клієнтського.
