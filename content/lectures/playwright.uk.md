Наскрізні (end-to-end, E2E) тести керують справжнім браузером у вашому справжньому застосунку так, як це робив би користувач: відкривають сторінку, вводять текст, клацають і перевіряють, що з'явилося. Вони ловлять проблеми, недоступні модульним тестам (маршрутизація, справжній CSS, інтеграція фронтенду з бекендом), але повільніші й крихкіші, тож лишайте їх для **критичних сценаріїв користувача**: реєстрації, оформлення замовлення, головного робочого процесу. Піраміда тестування (або «кубок») ставить більшість тестів на рівень модульних та інтеграційних, а зверху тонкий шар E2E.

## Чому Playwright

Playwright керує Chromium, Firefox і WebKit через один API, запускає тести паралельно в ізольованих **контекстах браузера** (нові cookie й сховище для кожного тесту, значно дешевше за нові браузери) і **автоматично чекає**: дії чекають, доки елемент стане видимим, увімкненим і стабільним, а перевірки повторюються, доки не пройдуть чи не вийде час. Це прибирає більшість викликів `sleep`, класичне джерело нестабільності.

```ts
import { expect, test } from "@playwright/test";

test("user can add a todo", async ({ page }) => {
  await page.goto("/todos");
  await page.getByLabel("New todo").fill("Buy milk");
  await page.getByRole("button", { name: "Add" }).click();
  await expect(page.getByRole("listitem")).toHaveText(["Buy milk"]);
});
```

## Локатори: шукайте як користувач

Віддавайте перевагу локаторам на основі того, що сприймає користувач, у такому порядку:

1. `getByRole("button", { name: "Save" })`: ще й перевіряє доступність (елемент мусить мати правильну роль і назву).
2. `getByLabel("Email")`, `getByPlaceholder`, `getByText`, `getByAltText`.
3. `getByTestId("cart-total")`, коли нічого стабільного з погляду користувача немає.
4. CSS/XPath-селектори лише в крайньому разі; вони ламаються зі зміною розмітки.

Локатори ліниві й суворі: вони розв'язуються в момент дії, а дія падає, якщо локатор збігається з кількома елементами, що рано виявляє неоднозначні селектори. Звужуйте через `.filter({ hasText })` або ланцюжком від контейнера.

## Web-first перевірки

Використовуйте `await expect(locator).toBeVisible()`, `toHaveText`, `toHaveValue`, `toHaveURL`, `toHaveCount`: вони **повторюються**, доки умова не виконається. Уникайте одноразового читання значення з подальшою перевіркою (`expect(await el.textContent()).toBe(…)`): воно не чекає й спричиняє нестабільність.

## Фікстури, автентифікація й тестові дані

- **Фікстури** (`test.extend`) дають повторно використовуване налаштування: сторінку з виконаним входом, заповнену базу, page object.
- **Автентифікація**: увійдіть один раз в окремому setup-проєкті, збережіть `storageState` (cookie й локальне сховище) у файл і використовуйте його в кожному тесті замість проходження форми входу щоразу.
- **Тестові дані**: створюйте все потрібне тесту через API чи базу з унікальними назвами, щоб тести були незалежними й могли йти паралельно. Ніколи не покладайтеся на порядок тестів.

## Керування мережею

```ts
await page.route("**/api/recommendations", (route) => route.fulfill({ json: [] }));
```

`page.route` може імітувати, змінювати чи блокувати запити, що корисно для станів помилок («сервер повертає 500»), повільних відповідей чи ненадійних сторонніх сервісів. Лишайте кілька тестів, що ходять до справжнього бекенду, щоб імітації не відірвалися від реальності.

## Чекліст проти нестабільності

- Жодних фіксованих `waitForTimeout`; натомість чекайте на видимий стан.
- Ізольовані дані для кожного тесту; скидайте стан у фікстурах.
- Вимикайте анімації чи використовуйте `reducedMotion` для стабільності.
- Не перевіряйте те, що законно змінюється (часові мітки, випадкові ID); маскуйте це на знімках.
- Використовуйте **повтори** в CI лише як страховку, а мітку «flaky» вважайте багом, який треба виправити.

## Налагодження й CI

- `npx playwright test --ui` або `--debug` для покрокового проходження; `codegen` записує дії в код.
- **Трасування** (`trace: "on-first-retry"`) фіксує знімки DOM, мережу, консоль і скриншоти для кожного кроку: найшвидший спосіб налагодити падіння в CI.
- Запускайте тести паралельно й з шардингом у CI на збірці, близькій до продакшену (`webServer` у конфігурації може її запустити).

## Понад функціональні перевірки

- **Візуальна регресія**: `await expect(page).toHaveScreenshot()` порівнює з еталоном (у CI фіксуйте ОС і шрифти, щоб уникнути шуму).
- **Доступність**: запускайте `@axe-core/playwright` на ключових сторінках, щоб ловити відсутні підписи, проблеми контрасту й помилки ARIA.
- **Компонентне тестування** теж доступне, але більшість команд тестують компоненти через Vitest + Testing Library, а Playwright використовують для повних сценаріїв.

## Що перевірити перед співбесідою

- Поясніть, що покривати E2E, а що модульними й інтеграційними тестами.
- Поясніть автоочікування й web-first перевірки та чому вони зменшують нестабільність.
- Оберіть добрі локатори й поясніть, чому кращі локатори за роллю.
- Опишіть повторне використання стану автентифікації та ізоляцію тестових даних.
- Опишіть, як налагодити тест, що падає лише в CI (трасування, повтори, скриншоти).
