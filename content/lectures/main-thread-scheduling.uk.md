Головний потік браузера виконує ваш JavaScript, обчислення стилів і розмітки, малювання й обробку введення **по одній задачі за раз**. Поки задача виконується, ніщо інше не може: натискання чекають, анімації завмирають, набір тексту запізнюється. Однопотокова модель JavaScript із виконанням до завершення робить код простішим для розуміння, але означає, що вам треба **співпрацювати**: розбивати великі завдання на малі частини й давати браузеру можливість виконати власну роботу.

## Довгі задачі й чутливість

Будь-яка задача понад **50 мс** вважається **довгою задачею**. Interaction to Next Paint (**INP**), одна з Core Web Vitals, вимірює затримку від взаємодії до наступного кадру, зокрема час очікування за довгими задачами; менше 200 мс вважається «добрим». Типові винуватці: розбір величезного JSON, фільтрування чи сортування великих списків, рендер тисяч вузлів DOM і дорога синхронна робота в обробниках подій. Шукайте їх у панелі Performance у DevTools (задачі з червоною позначкою) або через `PerformanceObserver` для записів `longtask` і `long-animation-frame`.

## Розбиття на частини й поступка потоку

Розбийте роботу й **поступайтеся потоком** між частинами, щоб могли виконатися введення й рендер, що очікують:

```js
async function processAll(items, handle) {
  let deadline = performance.now() + 10;
  for (const item of items) {
    handle(item);
    if (performance.now() > deadline) {
      await yieldToMain();
      deadline = performance.now() + 10;
    }
  }
}

function yieldToMain() {
  if (globalThis.scheduler?.yield) return scheduler.yield();
  return new Promise((resolve) => setTimeout(resolve, 0));
}
```

- **`scheduler.yield()`** повертає проміс, що продовжує вашу роботу з високим пріоритетом (перед іншими задачами в черзі) після того, як браузер обробив введення.
- **`setTimeout(fn, 0)`** ставить у чергу нову задачу, але після кількох рівнів вкладеності обмежується приблизно 4 мс і потрапляє в кінець черги.
- Надсилання через **`MessageChannel`** дає швидку задачу без обмеження (його використовував планувальник React).
- **Мікрозадачі не поступаються потоком**: `await Promise.resolve()` чи `queueMicrotask` виконуються до рендеру й введення, тож цикл, що лише чекає на розв'язані проміси, все одно блокує сторінку.

Поступайтеся потоком за **бюджетом часу** (кожні кілька мілісекунд), а не кожні N елементів, бо вартість елементів різна.

## requestAnimationFrame і requestIdleCallback

- **`requestAnimationFrame(cb)`** виконує `cb` безпосередньо перед наступним малюванням, один раз на кадр (зазвичай кожні 16,7 мс при 60 Гц). Використовуйте його для візуальних оновлень і анімацій, обчислюючи прогрес за аргументом-часовою позначкою. У фонових вкладках він призупиняється. Не використовуйте його для невізуальної роботи.
- **`requestIdleCallback(cb, { timeout })`** виконує `cb`, коли браузер простоює, передаючи `deadline` з `timeRemaining()`. Він добре підходить для низькопріоритетної роботи на кшталт групування аналітики, попереднього завантаження чи прогрівання кешів. На зайнятій сторінці він може довго не виконуватися, тож задайте `timeout`, якщо робота мусить колись статися. (У Safari його немає, тож визначайте можливість і майте запасний варіант.)

## Пріоритети через `scheduler.postTask`

`scheduler.postTask(fn, { priority })` ставить роботу в чергу з пріоритетом `"user-blocking"`, `"user-visible"` (за замовчуванням) чи `"background"` і приймає `AbortSignal` (чи `TaskController` для подальшої зміни пріоритету). Використовуйте його, щоб фонова робота, як-от синхронізація чи індексування, не затримувала те, на що чекає користувач.

## Layout thrashing

Читання властивостей розмітки (`offsetHeight`, `getBoundingClientRect`, `scrollTop`, `getComputedStyle`) одразу після запису стилів змушує браузер **синхронно перераховувати розмітку**. Якщо робити це в циклі (читання, запис, читання, запис), виникає **layout thrashing**:

```js
// Погано: примусовий перерахунок розмітки на кожній ітерації
for (const el of items) el.style.height = el.offsetWidth / 2 + "px";

// Добре: спершу все прочитати, потім усе записати
const widths = items.map((el) => el.offsetWidth);
items.forEach((el, i) => (el.style.height = widths[i] / 2 + "px"));
```

Бібліотеки на кшталт fastdom групують читання й записи по кадрах. Анімуйте `transform` і `opacity` замість властивостей розмітки, щоб кадри могли компонуватися без перерахунку розмітки.

## Перенесення роботи деінде

Коли розбиття на частини не допомагає, заберіть роботу з головного потоку: **Web Workers** для важких обчислень (розбір, обробка зображень, пошукові індекси), `OffscreenCanvas` для малювання, а найперше робіть менше: віртуалізуйте довгі списки, використовуйте пагінацію, застосовуйте debounce до обробників введення й мемоїзуйте дорогі похідні значення. Конкурентні можливості React (`startTransition`, `useDeferredValue`) застосовують ту саму ідею всередині рендеру: спершу термінові оновлення, решта з можливістю переривання.

## Що перевірити перед співбесідою

- Поясніть, чому довга задача блокує введення й рендер і що вимірює INP.
- Напишіть цикл із розбиттям на частини, що поступається потоком за бюджетом часу, і поясніть, чому мікрозадачі не поступаються потоком.
- Поясніть, коли використовувати `requestAnimationFrame`, `requestIdleCallback`, `setTimeout` і `scheduler.postTask`.
- Поясніть layout thrashing і виправте його групуванням читань і записів.
- Вирішіть, коли натомість перенести роботу у Web Worker.
