Кожен фронтенд спілкується з бекендом через HTTP, а кожна бекенд-співбесіда торкається REST. Питання здебільшого стосуються семантики: що обіцяє кожна частина протоколу.

## Методи

| Метод | Використання | Безпечний | Ідемпотентний |
| --- | --- | --- | --- |
| GET | читання ресурсу | ✓ | ✓ |
| HEAD | лише заголовки | ✓ | ✓ |
| POST | створення / виконання дії | ✗ | ✗ |
| PUT | повна заміна ресурсу | ✗ | ✓ |
| PATCH | часткове оновлення | ✗ | ✗ (зазвичай) |
| DELETE | видалення | ✗ | ✓ |

**Безпечний** означає «не змінює стан». **Ідемпотентний** означає «повторне виконання має той самий ефект, що й одне», і саме це робить повторні спроби безпечними. Для повторюваних POST-запитів (платежі) використовуйте заголовок **ключа ідемпотентності**.

## Коди стану

- **2xx успіх**: `200 OK`, `201 Created` (з `Location`), `204 No Content`.
- **3xx переспрямування**: `301`/`308` постійні, `302`/`307` тимчасові (307/308 зберігають метод), `304 Not Modified` (перевірка кешу).
- **4xx помилки клієнта**: `400` некоректний запит, `401` не автентифіковано, `403` автентифіковано, але заборонено, `404` не знайдено, `409` конфлікт, `422` валідація не пройшла, `429` забагато запитів.
- **5xx помилки сервера**: `500`, `502` bad gateway, `503` недоступний (з `Retry-After`), `504` gateway timeout.

## Проєктування REST

Ресурси є іменниками, а методи є дієсловами:

```
GET    /users?role=admin&page=2     список (фільтр, пагінація)
POST   /users                       створення → 201 + Location: /users/42
GET    /users/42                    читання
PATCH  /users/42                    оновлення полів
DELETE /users/42                    видалення → 204
GET    /users/42/orders             вкладений ресурс
```

Тримайте API без стану (кожен запит несе власну автентифікацію), версіонуйте його (`/v1` або заголовок) і повертайте узгоджені тіла помилок, наприклад problem details за RFC 9457.

## Кешування

- `Cache-Control: max-age=3600` дозволяє клієнтам повторно використовувати відповідь годину. `no-cache` означає перевіряти перед кожним використанням; `no-store` означає ніколи не зберігати. Для даних конкретного користувача використовуйте `private`, для ресурсів з відбитком у назві `public, immutable`.
- Валідатори: `ETag` + `If-None-Match` або `Last-Modified` + `If-Modified-Since` дозволяють серверу відповісти `304 Not Modified` без тіла.

## CORS

Браузери не дають JavaScript читати відповіді з **іншого джерела** (схема + хост + порт), якщо сервер не дозволив цього заголовком `Access-Control-Allow-Origin`.

- **Прості запити** (GET/POST з простими заголовками) надсилаються одразу, а браузер перевіряє заголовки відповіді.
- Інші (PUT, `Content-Type` JSON, `Authorization`) спершу викликають **preflight**-запит `OPTIONS`. Сервер має відповісти дозволеними методами й заголовками.
- Облікові дані (cookies) вимагають `Access-Control-Allow-Credentials: true` і явного джерела, а не `*`.

CORS захищає дані користувачів у їхньому браузері. Це не межа безпеки на сервері: curl його ігнорує.

## HTTP/2 і HTTP/3

Вони мультиплексують багато запитів в одному з'єднанні й стискають заголовки. HTTP/3 працює поверх QUIC (UDP). Шардинг доменів і спрайти більше не потрібні.

## Чек-лист для співбесіди

- Поясніть різницю між безпечним та ідемпотентним методом і чому PUT ідемпотентний, а POST ні.
- Обирайте правильний код стану (401 проти 403, 400 проти 422).
- Спроєктуйте REST-ендпоінт з пагінацією та помилками.
- Поясніть CORS preflight і як правильно виправити помилку CORS (на сервері).
