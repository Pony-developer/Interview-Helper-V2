Прогресивний вебзастосунок (PWA) є сайтом, що поводиться як встановлений застосунок: миттєво завантажується при повторних відвідинах, працює офлайн чи в поганій мережі, встановлюється на домашній екран або робочий стіл і може отримувати push-сповіщення. Він складається з трьох інгредієнтів: **HTTPS**, **маніфесту вебзастосунку** і **service worker**.

## Маніфест

```json
{
  "name": "Assay Interview Prep",
  "short_name": "Assay",
  "start_url": "/",
  "display": "standalone",
  "theme_color": "#0b5a43",
  "background_color": "#f7f5ef",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any maskable" }
  ]
}
```

Підключений через `<link rel="manifest" href="/manifest.webmanifest">`, він каже браузеру, як виглядає й відкривається встановлений застосунок: назва, іконки (зокрема maskable для Android), початковий URL і `display: standalone` (без інтерфейсу браузера).

## Service worker

Service worker є скриптом, що виконується **окремо від сторінки**, у фоні, і стоїть між сторінкою й мережею як програмований проксі:

```js
// сторінка
if ("serviceWorker" in navigator) navigator.serviceWorker.register("/sw.js");

// sw.js
self.addEventListener("fetch", (event) => {
  event.respondWith(caches.match(event.request).then((hit) => hit ?? fetch(event.request)));
});
```

Він не має доступу до DOM, керується подіями (браузер зупиняє його в простої, тож не тримайте стан у змінних), працює лише через HTTPS (або на localhost) і контролює сторінки в межах своєї **області дії** (scope: папки, з якої його віддано).

## Життєвий цикл (і пастка оновлень)

1. **install**: попередньо закешуйте «оболонку» застосунку (HTML, JS, CSS, іконки).
2. **waiting**: нова версія встановлюється, але **чекає**, доки хоч одна вкладка використовує стару, щоб застосунком ніколи не керували дві версії одночасно.
3. **activate**: новий worker бере керування; тут видаляйте старі кеші.

Саме через крок очікування користувачі часто бачать стару версію, доки не закриють усі вкладки. Типові підходи: показати підказку «Доступне оновлення, перезавантажити» й викликати `skipWaiting()`, коли користувач погодиться, або одразу викликати `skipWaiting()` + `clients.claim()`, якщо змішування версій безпечне. Ніколи надовго не кешуйте сам `sw.js` (віддавайте його з `Cache-Control: no-cache`).

## Стратегії кешування

| Стратегія | Як працює | Для чого |
| --- | --- | --- |
| Спершу кеш (cache first) | кеш, інакше мережа | хешованих статичних ресурсів, шрифтів, іконок |
| Спершу мережа (network first) | мережа, інакше кеш | HTML-сторінок, даних API, що часто змінюються |
| Stale-while-revalidate | одразу віддати кеш, оновити його у фоні | аватарів, некритичних відповідей API |
| Лише мережа | ніколи не кешувати | POST-запитів, платежів, автентифікованих приватних даних |
| Лише кеш | попередньо закешовані файли | офлайн-сторінки |

Версіонуйте кеші (`static-v3`) і прибирайте старі під час activate. Обмежуйте кеші під час роботи за кількістю записів чи віком, щоб сховище не росло вічно. Бібліотеки на кшталт **Workbox** (або PWA-плагіни для Vite/Next.js на її основі) генерують маніфести попереднього кешування й реалізують ці стратегії.

## Офлайн-досвід

- Попередньо закешуйте **офлайн-сторінку** й повертайте її, коли запит навігації не вдається.
- Зберігайте дані користувача в **IndexedDB** (а не в `localStorage`, який синхронний і недоступний у worker).
- **Background Sync** повторює запити з черги (надіслане повідомлення, форму), коли з'єднання повертається, там, де це підтримується.
- Показуйте стан з'єднання (`navigator.onLine` плюс події `online`/`offline`), але пам'ятайте, що він знає лише про локальну мережу, а не про доступність вашого сервера.

## Встановлення й push

Браузери пропонують встановлення, коли критерії виконано (маніфест з іконками й початковим URL, HTTPS, а в деяких браузерах і service worker). Можна перехопити `beforeinstallprompt` (Chromium) і показати власну кнопку встановлення; на iOS встановлюють через «Поділитися» → «На початковий екран». **Web Push** (Push API + Notifications) працює на Android, десктопі та на iOS 16.4+ для встановлених застосунків. Просіть дозвіл лише після дії користувача, що пояснює користь.

## Пастки

- Кешування HTML за стратегією «спершу кеш» може залишити користувачів на старій версії, що посилається на видалені JS-файли: для навігації краще «спершу мережа».
- Закешовані автентифіковані відповіді можуть потрапити до інших користувачів на спільних пристроях; очищайте кеші під час виходу.
- Непрозорі міжсайтові відповіді (`no-cors`) усе одно займають квоту сховища, і їх не можна перевірити.
- Тестуйте життєвий цикл у DevTools → Application (оновлення при перезавантаженні, офлайн-режим, сховище).

## Що перевірити перед співбесідою

- Назвіть три вимоги до PWA і що містить маніфест.
- Пройдіть шлях install → waiting → activate і поясніть, як розгортати оновлення.
- Оберіть стратегію кешування для HTML, хешованих ресурсів і даних API та обґрунтуйте її.
- Поясніть, як зробити офлайн-заглушку й де зберігати офлайн-дані.
- Опишіть підказки встановлення й дозволи на push.
