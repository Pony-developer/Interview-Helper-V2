Next.js є React-фреймворком, що додає маршрутизацію, серверний рендеринг, отримання даних і збірку. Сучасні застосунки використовують **App Router** (каталог `app/`), побудований на React Server Components. Старіші застосунки використовують Pages Router (`pages/`, `getServerSideProps`); варто знати, що він існує, але на співбесідах зараз зосереджуються на App Router.

## Маршрути задає файлова система

```
app/
  layout.tsx            ← кореневий макет (обгортає всі сторінки, зберігає стан між переходами)
  page.tsx              ← "/"
  dashboard/
    layout.tsx          ← вкладений макет для /dashboard/*
    page.tsx            ← "/dashboard"
    loading.tsx         ← fallback для Suspense, поки сегмент завантажується
    error.tsx           ← межа помилок (клієнтський компонент)
  blog/[slug]/page.tsx  ← "/blog/hello-world", params: { slug }
  shop/[...path]/       ← catch-all: "/shop/a/b" → { path: ["a", "b"] }
  docs/[[...slug]]/     ← необов'язковий catch-all: також відповідає "/docs"
  (marketing)/about/    ← група маршрутів: впорядковує файли, у URL не потрапляє
  api/users/route.ts    ← Route Handler (GET, POST, …)
```

Папка стає сегментом URL лише тоді, коли в ній є `page.tsx` (або `route.ts`). Статичні сегменти мають пріоритет над динамічними, тож `blog/new` переважає `blog/[slug]`. У поточних версіях `params` і `searchParams` є **промісами**: `const { slug } = await params`. Переходьте через `<Link href="/blog">`: він робить попереднє завантаження й переходи на клієнті.

## Серверні й клієнтські компоненти

Компоненти в `app/` за замовчуванням є **серверними** (Server Components). Вони виконуються лише на сервері, можуть бути `async`, можуть читати базу даних чи секрети напряму й **не відправляють JavaScript** у браузер.

Файл, що починається з `"use client"`, позначає межу **клієнтського компонента**. Клієнтські компоненти попередньо рендеряться на сервері й гідратуються в браузері, і лише в них можна використовувати стан, ефекти, обробники подій і браузерні API.

```tsx
// app/products/page.tsx (серверний компонент)
export default async function Products() {
  const products = await db.product.findMany();
  return <ProductList products={products} />; // клієнтський компонент
}
```

Правила межі:

- Опускайте `"use client"` якомога нижче в дереві (кнопка, а не вся сторінка).
- Пропси, що переходять у клієнтський компонент, мають бути **серіалізованими**: звичайні дані, JSX, проміси й Server Actions підходять; звичайні функції й екземпляри класів ні.
- Клієнтський компонент не може імпортувати серверний, але може відрендерити його, отримавши як `children`.
- У браузер потрапляють лише змінні оточення з префіксом `NEXT_PUBLIC_`. Додавайте `import "server-only"` у модулі, які ніколи не мають потрапити в клієнтський бандл.

## Отримання даних і кешування

Отримуйте дані там, де вони потрібні, у серверних компонентах через `async`/`await`; запити в паралельних компонентах не блокують один одного, а обгортка повільних частин у `<Suspense>` (або файл `loading.tsx`) **транслює потоком** решту сторінки першою. У нових версіях кешування явне: `fetch` за замовчуванням не кешується, а ви вмикаєте кеш директивою `"use cache"` (з увімкненими Cache Components) або параметрами маршруту на кшталт `export const revalidate = 3600`. Сторінки без даних часу запиту можна попередньо відрендерити під час збірки.

## Зміни даних: Server Actions

```tsx
async function createPost(formData: FormData) {
  "use server";
  const user = await requireUser(); // завжди перевіряйте на сервері
  const title = z.string().min(1).parse(formData.get("title"));
  await db.post.create({ data: { title, authorId: user.id } });
  revalidatePath("/blog"); // або updateTag / revalidateTag
}
// <form action={createPost}>…</form>
```

Server Action є функцією, яку клієнт може викликати через мережу. Next.js відкриває її як **публічний POST-ендпоінт**, тож автентифікуйте, авторизуйте й валідуйте всередині дії, а не лише ховайте кнопку. Після запису інвалідуйте закешовані сторінки чи дані, щоб користувачі побачили зміни.

## Route Handlers і proxy

- `app/api/**/route.ts` експортує функції з назвами HTTP-методів для вебхуків, публічних API чи клієнтів не на React.
- `proxy.ts` (до Next.js 16 називався `middleware.ts`) виконується до маршрутизації для перенаправлень, переписувань, визначення мови й дешевих перевірок автентифікації. Тримайте його швидким і не покладайтеся на нього як на єдиний рівень авторизації.

## Що перевірити перед співбесідою

- Зіставте URL і файли, зокрема динамічні, catch-all і необов'язкові catch-all сегменти та групи маршрутів.
- Поясніть різницю між серверними й клієнтськими компонентами, що робить `"use client"` і що може перетинати межу.
- Опишіть потокову передачу з `loading.tsx` і `<Suspense>`.
- Напишіть Server Action, що валідує дані, перевіряє авторизацію й робить ревалідацію.
- Поясніть, чому секрети в серверних компонентах у безпеці і як працює `NEXT_PUBLIC_`.
