Redux зберігає спільний клієнтський стан застосунку в **одному сторі** й змінює його лише через **дії** (actions), які обробляють **чисті редʼюсери**. Тому кожна зміна явна, її можна залогувати й відтворити, і саме тому Redux DevTools уміють «подорожувати в часі».

## Три принципи

1. **Єдине джерело правди.** Усе дерево стану живе в одному об'єкті стору.
2. **Стан доступний лише для читання.** Змінити його можна тільки через `dispatch` дії: звичайного об'єкта на кшталт `{ type: "todos/added", payload: todo }`.
3. **Зміни роблять чисті функції.** Редʼюсер `(state, action) => newState` ніколи не змінює вхідні дані, не має побічних ефектів і повертає той самий стан для дій, яких не обробляє.

## Потік даних

```ts
const store = createStore(rootReducer);
store.subscribe(() => render(store.getState()));
store.dispatch({ type: "counter/incremented" });
```

`dispatch` пропускає дію крізь **ланцюжок middleware**, потім викликає кореневий редʼюсер, замінює стан і сповіщає всіх підписників. `combineReducers({ todos, filter })` будує кореневий редʼюсер: кожен редʼюсер слайсу бачить і повертає лише свою частину стану, а об'єкт-результат новий лише тоді, коли змінився хоч один слайс.

## Middleware

Middleware обгортає `dispatch` і має сигнатуру `store => next => action => result`. Саме тут місце побічним ефектам:

```ts
const logger = (store) => (next) => (action) => {
  console.log("before", store.getState());
  const result = next(action);
  console.log("after", store.getState());
  return result;
};
```

**redux-thunk** дозволяє надсилати замість об'єкта функцію `(dispatch, getState) => …`. Так зазвичай пишуть асинхронну роботу: завантажити дані, а потім надіслати `succeeded` або `failed`. Для складних сценаріїв є альтернативи: саги та listeners.

## Redux Toolkit (RTK)

Сучасний Redux пишуть на RTK, який прибирає більшість шаблонного коду:

```ts
const todosSlice = createSlice({
  name: "todos",
  initialState: [] as Todo[],
  reducers: {
    added(state, action: PayloadAction<Todo>) {
      state.push(action.payload); // Immer перетворює це на незмінне оновлення
    },
  },
});
export const { added } = todosSlice.actions;
```

- `configureStore` додає thunk, DevTools і перевірки в режимі розробки: на мутації та несеріалізовані значення.
- `createSlice` генерує творці дій і рядки типів та використовує **Immer**: можна «мутувати» чернетку *або* повернути нове значення, але не обидва одразу.
- `createAsyncThunk` сам надсилає дії `pending`, `fulfilled` і `rejected`.
- **RTK Query** керує серверним станом (кешування, дедуплікація, інвалідація). Не копіюйте відповіді API в саморобні слайси.

## Читання стану: селектори

Компоненти читають стан через `useSelector(selector)`. Він перерендерює компонент, коли вибране значення змінилося за `===`, тож селектор, що щоразу будує новий масив (`state.todos.filter(...)`), спричиняє рендер після **кожної** дії. Вибирайте примітиви чи стабільні значення або мемоізуйте похідні дані через `createSelector` (Reselect): він переобчислює результат лише тоді, коли змінилися вхідні дані.

## Тримайте стор маленьким

- Зберігайте лише серіалізовані дані: без екземплярів класів, промісів чи DOM-вузлів.
- Нормалізуйте колекції (`ids` плюс `entities`, див. `createEntityAdapter`).
- Локальний стан UI (текст у полі, чи відкритий список) тримайте в компонентах.
- Обчислюйте, а не зберігайте суми, відфільтровані списки й прапорці, які можна вивести.

## Що перевірити перед співбесідою

- Поясніть, чому редʼюсери мають бути чистими і що зламається, якщо вони мутують стан (посилання не зміниться, тож `useSelector` і React пропустять оновлення).
- Пройдіть шлях `dispatch` → middleware → редʼюсер → підписники.
- Опишіть thunk middleware одним реченням: якщо дія є функцією, викликати її з `dispatch` і `getState`.
- Порівняйте Redux і Context: Context є способом передати значення вниз, а не стором, і всі його споживачі перерендерюються, коли значення змінюється.
