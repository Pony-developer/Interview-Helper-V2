Більшість стану у вебзастосунку насправді не належить застосунку: це копія даних, що живуть на сервері. Копія може застаріти, її використовують кілька компонентів, а завантажується вона асинхронно. TanStack Query (раніше React Query) керує саме цим: отриманням, кешуванням, оновленням і зміною серверних даних, тож компоненти не повторюють ці правила через `useEffect` і `useState`.

## Серверний стан — не клієнтський

Клієнтський стан (чи відкрите вікно, яка вкладка вибрана) існує лише в браузері й завжди актуальний. **Серверний стан** — це знімок, який може застаріти в момент отримання. Змішування обох у одному сховищі — часте джерело помилок. Серверні дані тримайте в кеші запитів, а клієнтський стан інтерфейсу — у `useState` або в невеликому сховищі.

## Запити й ключі

```ts
const { data, isPending, error } = useQuery({
  queryKey: ["orders", { status: "open" }],
  queryFn: () => fetchOrders({ status: "open" }),
});
```

**Ключ запиту** ідентифікує кешовані дані. Два компоненти, що запитують один ключ, ділять один запит і один запис кешу. Вмикайте в ключ кожне значення, від якого залежить результат, і нічого зайвого: якщо ключ `["orders"]`, а дані залежать від фільтра, відфільтровані й невідфільтровані результати перезаписують одне одного.

## Stale time і збирання сміття

- **`staleTime`** (за замовчуванням 0) показує, скільки дані вважаються свіжими. Свіжі дані не запитуються повторно під час монтування чи фокусу. Збільште його для даних, що змінюються рідко.
- **`gcTime`** (за замовчуванням 5 хвилин) показує, скільки невикористовувані дані лишаються в пам'яті після того, як останній компонент перестав їх використовувати.

Запит повторно завантажується при фокусі вікна, відновленні з'єднання і монтуванні, якщо його дані застаріли. Це зазвичай правильна поведінка за замовчуванням, і користувачі бачать свіжі дані без коду оновлення.

## Мутації та інвалідація

Записи виконуються через `useMutation`. Після успішного запису позначте відповідні запити як застарілі, щоб вони завантажились знову:

```ts
const queryClient = useQueryClient();
const addOrder = useMutation({
  mutationFn: createOrder,
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ["orders"] }),
});
```

Для швидкого інтерфейсу оновлюйте кеш **оптимістично**: запишіть очікуваний результат у кеш в `onMutate`, зберігши попереднє значення для відкату, і відновіть його в `onError`. Інвалідуйте знову в `onSettled`, щоб кеш відповідав серверу.

## Типові помилки

- **Копіювання даних запиту в локальний стан**: копія ніколи не оновлюється. Читайте результат запиту напряму або обчислюйте з нього.
- **Нестабільні ключі запитів**: ключ, побудований з нового об'єкта на кожному рендері, — це нормально (бібліотека хешує його), але ключ з міткою часу запитуватиме дані безкінечно.
- **Забуте `enabled`**: запит, що залежить від ідентифікатора, якого ще немає, має задавати `enabled: Boolean(id)`, а не викликати API з `undefined`.
- **Використання для даних, які на сервері ніколи не змінюються**: статичну конфігурацію місце в бандлі або з довгим `staleTime`.
- **Вважати `isLoading` єдиним станом**: запит з кешованими даними може оновлюватися у фоні. Для «даних ще немає» читайте `isPending`, а для «оновлюється» — `isFetching`.

## Що перевірити перед співбесідою

- Поясніть різницю між серверним і клієнтським станом, з прикладом кожного.
- Поясніть ключі запитів і чому вони мають містити кожен вхід, від якого залежить результат.
- Поясніть `staleTime` проти `gcTime` і коли запит завантажується повторно.
- Опишіть інвалідацію після мутації і коли варто використовувати оптимістичне оновлення.
- Назвіть дві типові помилки, що призводять до застарілих екранів.
