Справжні застосунки запускають багато асинхронної роботи, яка перестає бути важливою: користувач ввів ще одну літеру, перейшов на іншу сторінку чи закрив діалог. Якщо ця робота продовжується, вона марнує трафік і батарею, а гірше того, її **запізнілі результати перезаписують новіші**. Скасування є способом сказати «зупинись і не повідомляй результат».

## Проміси не скасовуються

Проміс представляє результат, а не операцію, що його створює, і той, хто його тримає, може лише спостерігати. `promise.cancel()` немає. Ігнорування результату (наприклад, через `Promise.race` з тайм-аутом) не зупиняє запит чи обчислення під ним; воно лише зупиняє ваше очікування.

## AbortController і AbortSignal

Відповідь платформи: окремий об'єкт-**сигнал**, який передають операції:

```js
const controller = new AbortController();
fetch(url, { signal: controller.signal })
  .then((res) => res.json())
  .then(render)
  .catch((err) => {
    if (err.name === "AbortError") return; // скасовано навмисно: не помилка для звіту
    showError(err);
  });

controller.abort(); // fetch відхиляється з DOMException на ім'я "AbortError"
```

- `controller.abort(reason)` встановлює `signal.aborted = true`, зберігає `signal.reason` і запускає подію `abort`, один раз.
- Багато API приймають сигнал: `fetch`, `addEventListener` (скасування видаляє слухача), потоки, `fs` у Node, `setTimeout` у `timers/promises` і більшість HTTP-клієнтів.
- `AbortSignal.timeout(ms)` створює сигнал, що скасовується з `TimeoutError`, а `AbortSignal.any([a, b])` поєднує сигнали (скасовується, коли скасовано будь-який), наприклад «скасування користувачем або тайм-аут 10 секунд».
- `signal.throwIfAborted()` кидає причину, якщо сигнал уже скасовано.

## Як зробити власні функції скасовуваними

Приймайте сигнал, перевіряйте його **перед** початком і **між** кроками й слухайте `abort` під час очікування:

```js
function sleep(ms, { signal } = {}) {
  return new Promise((resolve, reject) => {
    signal?.throwIfAborted();
    const id = setTimeout(() => {
      signal?.removeEventListener("abort", onAbort);
      resolve();
    }, ms);
    function onAbort() {
      clearTimeout(id);
      reject(signal.reason);
    }
    signal?.addEventListener("abort", onAbort, { once: true });
  });
}
```

Передавайте той самий сигнал кожній вкладеній операції, прибирайте таймери й слухачів на обох шляхах (скасування й успіх) і відхиляйте з `signal.reason`, щоб той, хто викликає, міг відрізнити скасування від збою.

## Стани гонитви із застарілими відповідями

Класична помилка: поле пошуку надсилає запит на кожне натискання клавіші. Відповіді можуть прийти **не по порядку**, тож результат для «re» може прийти після результату для «react» і перезаписати його. Виправлення:

- **Скасовуйте попередній запит**, коли починається новий (перемагає останній). Це ще й економить трафік.
- **Ігноруйте застарілі результати**: тримайте лічильник запитів чи прапорець `cancelled` і застосовуйте результат, лише якщо він досі найновіший. Ефекти React використовують цей шаблон із функцією очищення, що встановлює `ignore = true`.
- Поєднуйте з **debounce**, щоб надсилати менше запитів узагалі.

## Стратегії паралельності

Коли новий тригер надходить під час роботи, свідомо оберіть стратегію (назви з RxJS у дужках):

| Стратегія | Поведінка | Типове використання |
| --- | --- | --- |
| Перемагає останній (`switchMap`) | скасувати поточну задачу й запустити нову | пошук, автодоповнення, дані маршруту |
| Черга (`concatMap`) | виконувати задачі одна за одною, по порядку | збереження змін, надсилання повідомлень чату |
| Ігнорувати, доки зайнято (`exhaustMap`) | ігнорувати нові тригери, доки поточна задача не завершиться | кнопки «Надіслати» й «Оновити» |
| Паралельно (`mergeMap`) | виконувати все, можливо з обмеженням | завантаження багатьох файлів |

## Канали й координація

Окрім окремих запитів, асинхронний код часто потребує співпраці **виробників і споживачів**: краулер створює URL для воркерів, відправник журналів групує події. **Канал** (з CSP, communicating sequential processes, як у Go) є чергою, де `send` чекає, коли буфер заповнено, а `receive` чекає, коли він порожній. Це безкоштовно дає **зворотний тиск** (backpressure): швидкі виробники сповільнюються, а не заповнюють пам'ять. Асинхронні ітератори роблять споживання каналів зручним (`for await (const job of channel)`), а закриття каналу завершує такі цикли.

## Що перевірити перед співбесідою

- Поясніть, чому проміси не можна скасувати і як працює `AbortController`.
- Напишіть скасовуваний `sleep` чи `fetchWithTimeout` з `AbortSignal.timeout` і `AbortSignal.any`.
- Поясніть і виправте стан гонитви із застарілими відповідями в полі пошуку чи ефекті React.
- Оберіть між «перемагає останній», чергою, «ігнорувати, доки зайнято» і паралельністю для конкретної дії в інтерфейсі.
- Поясніть, що таке канал і як він дає зворотний тиск.
