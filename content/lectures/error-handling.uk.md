Добра обробка помилок полягає в **рішеннях**: які збої ви очікуєте й можете від них відновитися, які з них є помилками в коді й мають гучно все зупинити, і яка інформація знадобиться тому, хто налагоджуватиме систему о третій ночі. JavaScript дає інструменти; правила мови навколо них мають кілька пасток.

## Типи помилок

| Тип | Типове значення |
| --- | --- |
| `TypeError` | хибний тип: виклик не-функції, читання властивості `null`, запис у заморожений об'єкт у строгому режимі |
| `ReferenceError` | неоголошена змінна чи використання `let`/`const`/`class` у TDZ |
| `RangeError` | значення поза допустимим діапазоном: `new Array(-1)`, `toFixed(200)`, переповнення стеку |
| `SyntaxError` | некоректний код чи `JSON.parse` на хибних даних |
| `URIError`, `EvalError` | рідкісні |
| `AggregateError` | кілька помилок одразу: `Promise.any` чи ваші пакетні операції |
| `DOMException` | API браузера: `AbortError`, `NotAllowedError`, `QuotaExceededError` (перевіряйте `.name`) |

Кинути (`throw`) можна будь-яке значення, але завжди кидайте об'єкти `Error`: лише вони мають **стек викликів**, а код, що читає `err.message`, ламається на кинутому рядку.

## Власні помилки й причини

```js
class HttpError extends Error {
  constructor(status, message, options) {
    super(message, options);           // options.cause підтримує сам Error
    this.name = "HttpError";
    this.status = status;
  }
}

try {
  await saveOrder(order);
} catch (err) {
  throw new Error(`Couldn't save order ${order.id}`, { cause: err });
}
```

- Давайте помилкам `name` і поля для програм (`status`, `code`), щоб обробники могли розгалужуватися через `instanceof` чи `err.code`, а не розбирати повідомлення.
- Загортайте низькорівневі помилки з **контекстом** через `{ cause }`, а не втрачайте оригінал чи склеюйте повідомлення. DevTools і Node виводять увесь ланцюжок причин.
- Повідомлення для людей, коди для програм, і ніколи не кладіть секрети ні в те, ні в інше.

## Правила try / catch / finally

- `catch (err)` перехоплює **все**, що кинуто в `try`, зокрема помилки в коді. Перехоплюйте вузько: перевірте тип і знову кидайте те, що не можете обробити.
- Необов'язкове зв'язування в catch: `catch { … }`, коли помилка не потрібна.
- `finally` виконується завжди: після звичайного завершення, `return`, `break` чи винятку.
- `return` (чи `throw`) усередині `finally` **перекриває** результат `try`/`catch`, зокрема й ковтає виняток. Уникайте керування потоком у `finally`.
- Значення `return` у `try` обчислюється **до** виконання `finally`, тож зміна поверненої змінної у `finally` не змінює результат (а зміна поверненого об'єкта змінює).
- `try/catch` перехоплює лише синхронні помилки й відхилення, на які чекають через `await`. Помилка, кинута пізніше в колбеку `setTimeout`, чи проміс без `await` його оминають.

## Помилки в асинхронному коді

- **Колбеки** використовують конвенцію Node `(err, result)`. Помилки треба передавати, а не кидати, бо на той момент стеку того, хто викликав, уже немає.
- **Проміси** перетворюють винятки на відхилення. Обробляйте їх через `.catch` у кінці кожного ланцюжка.
- **`async`-функції**: `await` перетворює відхилення на виняток, тож звичайний `try/catch` працює. Але `return promise` усередині `try` без `await` дає відхиленню оминути ваш `catch`, тож там використовуйте `return await`.
- **Паралельність**: `Promise.all` відхиляється на першій невдачі (інші операції продовжують виконуватися без нагляду), а `Promise.allSettled` повідомляє кожен результат. Обирайте свідомо.
- **Обробники подій і потоки** повідомляють про помилки через події `error`: слухайте їх, бо необроблена подія `error` на `EventEmitter` у Node кидає виняток.

## Глобальні обробники

Обробники останньої лінії призначені для **журналювання й звітів**, а не для відновлення:

- Браузер: `window.addEventListener("error", …)` для неперехоплених винятків і ресурсів, що не завантажилися, `unhandledrejection` для промісів.
- Node: `process.on("uncaughtException")` і `unhandledRejection`. Після неперехопленого винятку стан процесу невідомий, тож запишіть у журнал і завершіть процес, а перезапуск залиште супервізору.
- Фреймворки додають власні рівні, як-от межі помилок (error boundaries) у React для помилок рендеру.

## Проєктування обробки помилок

- **Очікувані збої** (валідація, «не знайдено», відхилений платіж) є частиною предметної області. Повертайте їх як значення (`{ ok: false, error }`, тип `Result`) чи кидайте конкретні класи помилок, але обробляйте близько до місця виникнення.
- **Неочікувані збої** (помилки в коді, порушені інваріанти) мають **швидко** й гучно зупиняти роботу з достатнім контекстом для налагодження. Не ковтайте їх мовчки через `catch`, продовжуючи в некоректному стані.
- **Тимчасові збої** (тайм-аути мережі, 503, конфлікти блокувань) можна **повторювати** з експоненційною затримкою й випадковим розкидом, обмеженою кількістю спроб і лише для ідемпотентних операцій.
- Обробляйте кожну помилку **один раз**: або запишіть у журнал, або знову киньте з контекстом, але не обидва на кожному рівні.
- На межах (обробник HTTP, споживач черги, дія в інтерфейсі) перетворюйте помилки на відповідь: код стану, зрозуміле повідомлення й ідентифікатор кореляції, а подробиці йдуть у журнали.

## Що перевірити перед співбесідою

- Назвіть вбудовані типи помилок і коли кожен виникає.
- Напишіть власний клас помилки з `name`, додатковими полями й `cause`.
- Поясніть, як `return` взаємодіє з `finally` і що `try/catch` не може перехопити.
- Поясніть обробку помилок у колбеках, промісах і `async`-функціях, зокрема `return await`.
- Поясніть очікувані, неочікувані й тимчасові збої та для чого потрібні глобальні обробники.
